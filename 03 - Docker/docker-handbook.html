Core Concepts & Mental Model

What Docker really is, how it works at the kernel level, and why thinking in layers changes everything

What Docker Actually Is

Docker is not magic virtualization. It's a tool that uses Linux kernel features (namespaces + cgroups) that have existed since 2006 to create isolated process groups that share the host OS kernel. Understanding this changes how you reason about every Docker problem.

💡
The Core Insight A Docker container is just a normal Linux process — but one that believes it has its own filesystem, network, user tree, and PID namespace. There's no guest OS. The kernel you see in docker run ubuntu uname -r is your host kernel.

The Docker Object Model

Docker has five core object types. Understanding how they relate is the foundation of everything else.

📐 Docker Object Model — Layered View
⚠️
Container filesystem is ephemeral When you docker rm a container, its writable layer is gone. Anything written inside the container (database files, uploaded files, logs) is lost unless you use a Volume or Bind Mount. This is the #1 Docker gotcha for beginners.

How Daemon, CLI & Registry Interact

The Docker CLI you type commands into is just a thin HTTP client. It talks to the Docker daemon (dockerd), which does the actual work. The daemon then talks to registries to pull/push images.

📐 Docker Client / Server / Registry Flow

The daemon socket at /var/run/docker.sock is why adding your user to the docker group gives them root-equivalent access — anything that can talk to that socket can instruct the daemon to mount host paths, run privileged containers, etc.

The Image Layer Cache System

Every Dockerfile instruction creates a layer. Docker caches each layer by a hash of its instruction + inputs. On rebuild, if nothing changed above that layer, Docker reuses the cache — making rebuilds fast.

📐 Layer Stacking — How OverlayFS Works
🎯
The Golden Rule of Dockerfile Layer Order Put instructions that change least often at the top, and instructions that change most often at the bottom. This maximizes cache hits. Always COPY package.json → RUN npm install → COPY . . — never copy source first.

Installation & Setup

Install Docker Engine on Ubuntu 24, post-install hardening, and understanding the CLI structure

Install Docker Engine on Ubuntu 24.04

On a VPS, you want Docker Engine (the server daemon), not Docker Desktop (which is a GUI app for local dev on Mac/Windows). Here's the exact install sequence from Docker's official repository — do not use Ubuntu's default docker.io package, it's outdated.

bash Ubuntu 24.04 — Official Docker Engine Install 
# Step 1: Remove any old/conflicting packages
sudo apt remove -y docker docker-engine docker.io containerd runc 2>/dev/null || true

# Step 2: Install prerequisites
sudo apt update
sudo apt install -y ca-certificates curl gnupg lsb-release

# Step 3: Add Docker's official GPG key (verifies packages are authentic)
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

# Step 4: Add Docker's repository
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# Step 5: Install Docker Engine + Compose plugin
sudo apt update
sudo apt install -y \
  docker-ce \          # Docker Engine daemon
  docker-ce-cli \      # Docker CLI
  containerd.io \      # Container runtime
  docker-buildx-plugin \ # BuildKit (faster builds)
  docker-compose-plugin   # docker compose v2 (note: no hyphen)

# Step 6: Verify installation
docker --version         # Docker version 26.x.x
docker compose version   # Docker Compose version v2.x.x
sudo docker run hello-world
ℹ️
docker-compose vs docker compose The old docker-compose (with hyphen, Python-based) is v1 and deprecated. The new docker compose (space, Go-based, installed as a plugin) is v2. Use v2. All examples in this handbook use docker compose.

Post-Install Setup

Run Docker Without sudo

By default, the Docker socket (/var/run/docker.sock) is owned by root:docker. Only root or members of the docker group can use it. Let's fix that:

bash Post-install: no-sudo & enable on boot 
# Create docker group (may already exist)
sudo groupadd docker 2>/dev/null || true

# Add your current user to the docker group
# ${USER} expands to your username automatically
sudo usermod -aG docker ${USER}

# Apply group changes without logging out (for current session only)
# For permanent effect, log out and back in, or reboot
newgrp docker

# Enable Docker daemon to start on boot
sudo systemctl enable docker.service
sudo systemctl enable containerd.service

# Start Docker now (it's probably already running after install)
sudo systemctl start docker

# Confirm Docker starts without sudo
docker run --rm hello-world
⚠ Security Warning

The docker group grants root-equivalent access. Any user in this group can mount host paths, run privileged containers, and escalate to root. On multi-user systems, only add trusted accounts. On production VPS with single-user access, it's fine.

Dockerfile — Every Instruction Explained

A Dockerfile is a recipe. Docker reads it top-to-bottom, executes each instruction, and commits the result as a layer. Here's every instruction you'll use, with real context for Node.js/Next.js developers:

dockerfile Dockerfile — Annotated Reference 
# ── FROM ─────────────────────────────────────────────────────────
# Sets the base image. Everything starts here.
# Always pin to a specific version tag in production (not :latest)
# alpine = minimal (~5MB), slim = smaller but Debian-based
FROM node:20-alpine        # good
FROM node:20-alpine3.19   # better — pinned minor version
FROM node:latest           # bad — breaks silently on updates

# ── ARG ──────────────────────────────────────────────────────────
# Build-time variable. NOT available at runtime.
# Pass with: docker build --build-arg NODE_ENV=production
# Use for: versions, build-time feature flags
ARG NODE_VERSION=20
ARG APP_VERSION=1.0.0
FROM node:${NODE_VERSION}-alpine  # ARG can be used in FROM

# ── ENV ──────────────────────────────────────────────────────────
# Runtime environment variable. Available when container runs.
# Also available during subsequent RUN steps in Dockerfile.
# Override at runtime: docker run --env PORT=4000
ENV NODE_ENV=production
ENV PORT=3000
ENV NEXT_TELEMETRY_DISABLED=1

# ── WORKDIR ──────────────────────────────────────────────────────
# Sets the working directory for all subsequent commands.
# Creates the directory if it doesn't exist.
# Think of it as: cd /app — but persistent across all RUN/COPY/CMD
WORKDIR /app

# ── COPY ─────────────────────────────────────────────────────────
# Copies files from build context (your project folder) into image.
# Syntax: COPY <src-on-host> <dest-in-image>
# --chown sets file ownership — critical for non-root user setup
COPY package.json package-lock.json ./
COPY --chown=node:node . .

# ── ADD ──────────────────────────────────────────────────────────
# Like COPY but also: auto-extracts .tar.gz, supports URLs.
# Prefer COPY unless you specifically need extraction.
ADD archive.tar.gz /data/   # extracts automatically

# ── RUN ──────────────────────────────────────────────────────────
# Executes a shell command during build and commits result as a layer.
# Chain commands with && to keep them in ONE layer (reduces image size).
# Use \ for line continuation (readability)
RUN npm ci --only=production

# Multi-line RUN (one layer, best practice):
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl && \
    rm -rf /var/lib/apt/lists/*  # Always clean apt cache in same layer!

# ── USER ─────────────────────────────────────────────────────────
# Switch to a non-root user for all subsequent commands.
# node:alpine images come with a built-in 'node' user (uid 1000).
# CRITICAL for production security.
RUN addgroup --system appgroup && adduser --system --ingroup appgroup appuser
USER appuser

# Or use the built-in node user:
USER node

# ── EXPOSE ───────────────────────────────────────────────────────
# Documents which port the app listens on.
# This is DOCUMENTATION ONLY — it doesn't actually open the port.
# You still need -p 3000:3000 or ports: in compose to expose it.
EXPOSE 3000

# ── VOLUME ───────────────────────────────────────────────────────
# Declares a mount point. Docker creates an anonymous volume here
# if no volume is explicitly mounted. Rarely used in Dockerfiles —
# prefer explicit volumes in docker-compose.yml instead.
VOLUME ["/app/data"]

# ── CMD ──────────────────────────────────────────────────────────
# The default command when container starts.
# Can be overridden at runtime: docker run myimage node other.js
# Use exec form (JSON array) — avoids shell wrapping, handles signals better
CMD ["node", "server.js"]         # exec form ✓ preferred
CMD node server.js                   # shell form ✗ PID 1 wraps in /bin/sh

# ── ENTRYPOINT ───────────────────────────────────────────────────
# Like CMD but harder to override. Sets the executable.
# CMD then acts as default arguments to ENTRYPOINT.
# Use ENTRYPOINT for containers that should always run a specific binary.
ENTRYPOINT ["node"]
CMD ["server.js"]   # → runs: node server.js
                      # Override: docker run myimage other.js → node other.js

# ── HEALTHCHECK ──────────────────────────────────────────────────
# Docker periodically runs this to determine if container is healthy.
# --interval: how often to check (default 30s)
# --timeout: how long to wait for response (default 30s)
# --retries: how many fails before marking unhealthy (default 3)
# --start-period: grace period at startup before counting failures
HEALTHCHECK --interval=30s --timeout=10s --retries=3 --start-period=5s \
  CMD curl -f http://localhost:3000/api/health || exit 1
⚠️
CMD exec form vs shell form Always use exec form CMD ["node", "server.js"] in production. Shell form CMD node server.js wraps in /bin/sh -c, making sh PID 1. This means SIGTERM from docker stop is sent to sh, which may not forward it to Node.js, causing a 10-second grace period timeout before SIGKILL.

Multi-Stage Builds

Multi-stage builds let you use one image to build your app and a different, smaller image to run it. You only copy the final output between stages. The build tools (TypeScript compiler, webpack, etc.) never end up in your production image.

dockerfile Dockerfile — Next.js Production Multi-Stage 
# ── Stage 1: deps ─────────────────────────────────────────────
# Install ALL deps (including dev) needed for the build.
# Label with AS to reference this stage later.
FROM node:20-alpine AS deps
RUN apk add --no-cache libc6-compat  # needed for some native modules on alpine
WORKDIR /app

# Copy ONLY package files first (cache optimization)
# If package.json hasn't changed, npm ci layer is reused
COPY package.json package-lock.json* ./
RUN npm ci  # ci = clean install (uses lockfile exactly, faster than npm install)

# ── Stage 2: builder ──────────────────────────────────────────
# Build the Next.js app. Has access to all deps from stage 1.
FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .  # Copy source code

# Build-time env vars — next.config.js can use these
# These are embedded in the build, not read at runtime
ARG NEXT_PUBLIC_API_URL
ENV NEXT_PUBLIC_API_URL=${NEXT_PUBLIC_API_URL}

ENV NEXT_TELEMETRY_DISABLED=1
RUN npm run build  # runs: next build

# ── Stage 3: runner (final, smallest image) ───────────────────
# Only copies the built output. No source, no dev deps, no build tools.
FROM node:20-alpine AS runner
WORKDIR /app

ENV NODE_ENV=production
ENV NEXT_TELEMETRY_DISABLED=1

# Create non-root user for security
RUN addgroup --system --gid 1001 nodejs
RUN adduser --system --uid 1001 nextjs

# Copy only what Next.js needs to run
# next.config.js — runtime config
COPY --from=builder /app/public ./public
COPY --from=builder /app/next.config.js ./

# Standalone output mode copies server + minimal deps.
# Requires: output: 'standalone' in next.config.js
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static

USER nextjs

EXPOSE 3000

ENV PORT=3000
ENV HOSTNAME="0.0.0.0"

# In standalone mode, Next.js compiles to server.js
CMD ["node", "server.js"]
🎯
Enable standalone mode in next.config.js Add output: 'standalone' to your next.config.js. This tells Next.js to create a self-contained .next/standalone folder with only the minimal server files needed. Reduces final image size from ~1GB to ~200MB.
jsnext.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'standalone',  // enables standalone build for Docker
  // ... rest of your config
}

module.exports = nextConfig

# Stage 1: Install all deps for build
FROM node:20-alpine AS deps
WORKDIR /app
COPY package*.json ./

# Stage 2: Final production image
FROM node:20-alpine AS runner
WORKDIR /app

# Install only production deps fresh (no devDeps)
COPY package*.json ./

# Copy source (after deps, so code changes don't bust npm cache)

HEALTHCHECK --interval=30s --timeout=10s --retries=3 \

# Stage 1: Build TypeScript → JavaScript
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json tsconfig*.json ./
RUN npm ci                   # includes typescript
COPY src/ ./src/
RUN npm run build             # runs: tsc → outputs to dist/

# Stage 2: Runtime — no TypeScript, no source

WORKDIR /app

COPY package*.json ./

# Only copy compiled JS, not TypeScript source
COPY --from=builder /app/dist ./dist/

RUN addgroup -S appgroup && adduser -S appuser -G appgroup

bash Image commands

# Build an image from a Dockerfile

docker images -q

docker run — Deep Dive

docker run is actually a shortcut for docker create + docker start. It's the command you'll use most — every flag here matters for real usage.

bash docker run — every important flag 
# ── Basic run ────────────────────────────────────────────────────
# docker run [OPTIONS] IMAGE [COMMAND] [ARG...]

# -d = detached (background). Without it, logs stream to your terminal.
docker run -d nginx

# -it = interactive + tty. For shells, REPLs, interactive commands.
# Without -i: stdin closed. Without -t: no terminal formatting.
docker run -it node:20-alpine sh
docker run -it ubuntu:24.04 bash

# --rm = auto-remove container when it exits.
# Use for one-shot commands — prevents container accumulation.
docker run --rm -it node:20-alpine node -e "console.log('hello')"

# --name = give the container a fixed name (instead of random adjective_noun).
# Named containers are easier to reference in scripts and logs.
docker run -d --name my-postgres postgres:16-alpine

# ── Port mapping: -p ─────────────────────────────────────────────
# -p HOST_PORT:CONTAINER_PORT
# HOST_PORT  = port on your machine (or 0.0.0.0 for public)
# CONTAINER_PORT = port the app listens on inside the container
docker run -p 3000:3000 my-app        # host:3000 → container:3000
docker run -p 8080:3000 my-app        # host:8080 → container:3000 (port remapping)
docker run -p 127.0.0.1:5432:5432 postgres  # only accessible from localhost!

# ── Volume and bind mounts: -v ────────────────────────────────────
# -v NAMED_VOLUME:CONTAINER_PATH   → named volume (managed by Docker)
# -v /host/path:CONTAINER_PATH     → bind mount (your actual directory)
docker run -v postgres-data:/var/lib/postgresql/data postgres:16
docker run -v $(pwd)/src:/app/src my-app  # mount current dir's src folder
docker run -v $(pwd):/app -v /app/node_modules my-app  # exclude node_modules

# Read-only bind mount (container can't write to your source)
docker run -v $(pwd)/src:/app/src:ro my-app

# ── Environment variables: --env / -e ────────────────────────────
docker run -e NODE_ENV=production -e PORT=3001 my-app
docker run --env-file .env.production my-app  # load from file

# ── Network: --network ────────────────────────────────────────────
docker run --network my-app-network my-app
docker run --network host my-app           # use host network directly
docker run --network none my-app           # no network access

# ── Restart policy: --restart ─────────────────────────────────────
docker run --restart unless-stopped my-app  # best for production services
docker run --restart on-failure:5 my-app   # retry up to 5 times

# ── Resource limits ───────────────────────────────────────────────
# --memory limits RAM (k/m/g suffix)
# --cpus limits CPU (1.5 = 1.5 cores)
docker run --memory 512m --cpus 1.0 my-app
docker run --memory 2g --memory-swap 2g my-app  # disable swap

# ── Working directory: -w ─────────────────────────────────────────
docker run -w /app/scripts my-app node migrate.js

# ── Full real-world example ───────────────────────────────────────
docker run \
  -d \                                       # run in background
  --name my-next-app \                       # named container
  -p 3000:3000 \                             # expose port
  --network app-network \                    # join network
  -e DATABASE_URL=postgresql://... \         # env var
  --memory 1g \                              # RAM limit
  --restart unless-stopped \                # auto-restart policy
  ghcr.io/myorg/my-app:1.2.0               # image:tag
💡
Why -p 127.0.0.1:5432:5432 for databases? Without the IP prefix, Docker binds to 0.0.0.0, exposing the port on ALL network interfaces, including public ones. For databases, bind to 127.0.0.1 (localhost only) so they're only accessible from the host, not the internet.

Exec, Logs, Stats & More

bash Container operations 
# ── docker exec ──────────────────────────────────────────────────

Networking

Bridge, host, none networks — Docker DNS, port binding, and why containers find each other by name

Docker Network Types

📐 Docker Network Drivers Comparison

Default Bridge vs User-Defined Bridge

Docker has a default bridge network (docker0). Never use it in real projects. User-defined bridge networks have container DNS — containers find each other by service name, not by hardcoded IP. This is non-negotiable for multi-container apps.

✗ Default Bridge (Bad)
# Containers CAN'T talk by name
# Must use IP addresses which change
docker run -d postgres
# Container IP: 172.17.0.2
docker run -d my-app
# Must hardcode: 172.17.0.2 ← BREAKS when postgres restarts

# env in app:
DATABASE_URL=postgresql://172.17.0.2:5432/mydb
# This breaks if postgres restarts with new IP
✓ User-Defined Bridge (Good)
# Containers CAN talk by container name!
docker network create app-network

docker run -d --name postgres --network app-network postgres
docker run -d --name my-app --network app-network my-app

# env in app:
DATABASE_URL=postgresql://postgres:5432/mydb
# "postgres" is the container name — Docker DNS resolves it!

Container DNS — How Containers Find Each Other

Docker runs an embedded DNS server at 127.0.0.11 inside each container. When your app does pg.connect('postgres:5432'), Docker's DNS resolves postgres to the container's internal IP. In Docker Compose, the service name IS the hostname.

Database & Service Management

PostgreSQL, Redis, MongoDB — understanding every line so you can write it yourself

First: Understand WHERE PostgreSQL Puts Your Data

Before writing a single line of compose, you must understand one thing: PostgreSQL stores everything — your tables, your indexes, your WAL logs — inside one directory on the filesystem. That directory inside the official Docker image is:

path Where PostgreSQL data lives inside the container 
/var/lib/postgresql/data

# Breaking down the path:
# /var/lib/          ← Linux standard location for persistent application data
# postgresql/        ← the application name (set by the postgres image)
# data/              ← postgres' data directory (PGDATA env variable points here)

# This one directory contains:
# ├── base/           ← your actual databases (one folder per DB)
# ├── global/         ← cluster-wide tables (users, etc.)
# ├── pg_wal/         ← Write-Ahead Log (transaction journal)
# ├── pg_hba.conf     ← authentication rules
# └── postgresql.conf ← main configuration file
⚠️
The Fatal Mistake: Containers are ephemeral. Every docker compose down destroys the container filesystem. If you don't mount a volume at /var/lib/postgresql/data, your entire database disappears. This is the #1 Docker beginner mistake. A named volume at this exact path is not optional.

Now that you know where data lives, here's how to protect it:

yaml The critical volume mount — why this exact path 
volumes:
  - postgres-data:/var/lib/postgresql/data
#   ↑               ↑
#   Named volume    The directory inside the container
#   (Docker manages where this lives on your HOST,
#    usually /var/lib/docker/volumes/postgres-data/_data/)
#
# Docker merges: container's /var/lib/postgresql/data
#                ← maps to → host's named volume
# Result: data survives container deletion forever

The PGDATA Subdirectory Trick

There's one subtle issue: if you mount a volume at /var/lib/postgresql/data and the host filesystem has a lost+found directory there (which Linux sometimes creates on ext4 volumes), PostgreSQL will refuse to start because the directory "isn't empty." The fix is to add one env var:

yaml PGDATA env var — avoid the lost+found error 
environment:
  PGDATA: /var/lib/postgresql/data/pgdata
#         ↑
# Tell postgres to initialize inside a SUBDIRECTORY called pgdata/
# Now the volume root can have lost+found — postgres ignores it
# Postgres data lives at: /var/lib/postgresql/data/pgdata/
# The volume still mounts at: /var/lib/postgresql/data

Init Scripts — Automatic Setup on First Boot

The PostgreSQL Docker image has a special feature: any .sql or .sh file you place inside /docker-entrypoint-initdb.d/ runs automatically when the database is first created. "First created" means when the data directory is empty — i.e., the very first docker compose up, or after a docker compose down -v.

yaml How to mount init scripts 
# Your project folder structure:
# myproject/
# ├── docker-compose.yml
# ├── .env
# └── db/
#     └── init/                ← your init scripts folder
#         ├── 01-extensions.sql
#         └── 02-seed.sql

volumes:
  - ./db/init:/docker-entrypoint-initdb.d:ro
#   ↑              ↑                        ↑
# your host path  target path in container  read-only
#
# The path "./db/init" is RELATIVE to docker-compose.yml.
# If compose file is at /home/user/myproject/docker-compose.yml,
# then "./db/init" resolves to /home/user/myproject/db/init/
#
# Files run in alphabetical order: 01-... before 02-... before 03-...
# This is why you prefix files with numbers.
sql db/init/01-extensions.sql — enable UUID and stats 
-- This runs once when the DB container is first created.
-- It runs AS the POSTGRES_USER you set in environment variables.

-- Enable UUID generation (Prisma uses this for @default(uuid()))
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
-- "IF NOT EXISTS" makes this idempotent — safe to run again

-- Enable query performance tracking
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Create a read-only user for analytics/reporting tools
CREATE USER readonly_user WITH ENCRYPTED PASSWORD 'readonlypass123';
GRANT CONNECT ON DATABASE myapp TO readonly_user;
GRANT USAGE ON SCHEMA public TO readonly_user;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly_user;
-- Note: GRANT above applies to tables that CURRENTLY exist.
-- For future tables, Prisma/migrations need to GRANT again.
sql db/init/02-seed.sql — development seed data 
-- WARNING: This only runs on first-ever database initialization.
-- After that, even if you change this file, it won't re-run.
-- To re-run: docker compose down -v && docker compose up

-- Use ON CONFLICT DO NOTHING to make inserts idempotent
INSERT INTO users (email, name, role, created_at) VALUES
  ('admin@example.com', 'Admin User', 'admin', NOW()),
  ('test@example.com',  'Test User',  'user',  NOW())
ON CONFLICT (email) DO NOTHING;
-- "ON CONFLICT (email) DO NOTHING" means: if a row with this email
-- already exists, skip the insert instead of throwing an error.
-- This requires a UNIQUE constraint on email in your schema.
⚠️
Init scripts only run ONCE: On first database initialization, never again — even if you modify the SQL file. This is intentional: you don't want your database reset every time you restart the container. If you need to re-run them, you must destroy the volume: docker compose down -v (WARNING: deletes all data). For regular schema changes, use migrations (Prisma, Flyway, etc.).

Prisma Migrations in Docker — The Correct Pattern

This is where most people get stuck. The problem: your app container starts, tries to connect to the database and run migrations, but PostgreSQL isn't ready yet. The naive solution (depends_on: postgres) doesn't work because depends_on only waits for the container to start, not for PostgreSQL to be ready to accept connections.

The correct, production-safe pattern uses three services in a dependency chain:

📐 Migration Dependency Chain — 3-Step Pattern
yaml docker-compose.yml — Prisma migration pattern (full example) 
services:

  # ── STEP 1: Database ─────────────────────────────────────────────
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
      PGDATA: /var/lib/postgresql/data/pgdata
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 30s
      # ↑ interval: 5s = check every 5 seconds (faster feedback in dev)
      #   retries: 10 = tolerate up to 10 failures before "unhealthy"
      #   start_period: 30s = don't count failures in first 30 seconds
    networks: [app-network]
    restart: unless-stopped

  # ── STEP 2: Migrations ───────────────────────────────────────────
  migrate:
    build:
      context: .
      #   ↑ "context: ." means Docker's build context is the current folder
      #     (where docker-compose.yml lives). The Dockerfile will be found here.
      target: builder
      #   ↑ Use the "builder" stage from your multi-stage Dockerfile.
      #     This stage has all devDependencies including Prisma CLI.
      #     Your production runner stage won't have prisma CLI — that's OK.
    command: ["npx", "prisma", "migrate", "deploy"]
    #     ↑ "prisma migrate deploy" (not "migrate dev"):              
    #       - Applies all pending migrations from prisma/migrations/
    #       - Silent (no prompts) — safe for CI/automated environments
    #       - Fails with exit code 1 if anything is wrong (schema drift, etc.)
    #       - Does NOT generate new migrations (only applies existing ones)
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}
      #            ↑ Format: postgresql://USER:PASS@HOST:PORT/DBNAME
      #                                              ↑
      #                                 "postgres" = service name in compose
      #                                 Docker DNS resolves this to container IP
      #                                 NOT "localhost" — that would be the
      #                                 migrate container itself!
    depends_on:
      postgres:
        condition: service_healthy
        # ↑ Only start migrate AFTER postgres healthcheck passes.
        #   "service_healthy" requires a healthcheck to be defined on postgres.
        #   Without this, migrate starts before postgres is ready → connection refused.
    restart: "no"
    #     ↑ CRITICAL: run once and exit. Never restart this service.
    #       If it's done successfully, we're done. If it fails, we want
    #       the error to be visible — not retried in a loop.
    networks: [app-network]

  # ── STEP 3: Application ──────────────────────────────────────────
  app:
    build:
      context: .
    depends_on:
      migrate:
        condition: service_completed_successfully
        # ↑ Only start app AFTER migrate exits with code 0.
        #   "service_completed_successfully" = the container ran and exited cleanly.
        #   This guarantees: by the time app starts, ALL migrations have run.
      postgres:
        condition: service_healthy
        # ↑ Also depend directly on postgres being healthy (belt and suspenders).
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}
      NODE_ENV: production
    networks: [app-network]
    restart: unless-stopped

volumes:
  postgres-data:

networks:
  app-network:
    driver: bridge
💡
Why migrate deploy not migrate dev?
prisma migrate dev is interactive — it prompts you, generates new migration files, can reset the DB. It's for your local machine.
prisma migrate deploy is automated — it reads migration files from prisma/migrations/ (which you committed to git) and applies them one by one. It never resets data. If migrations are up to date, it exits 0 immediately. This is the correct command for Docker, CI, and production.

Redis — Caching & Session Storage

Redis stores data in RAM which makes it extremely fast. It's used for caching (store DB query results so you don't re-query every request), session storage (keep login sessions), rate limiting (count API calls per user), and job queues.

Understanding Redis Data Persistence

Redis has two persistence modes you can combine:

yaml docker-compose.yml — Redis fully annotated 
services:
  redis:
    image: redis:7-alpine
    #     ↑ Pin to major version 7. Alpine = smaller image.
    #       Redis 7 has important security and performance improvements.

    container_name: myapp-redis
    restart: unless-stopped

    command: >
      redis-server
      --maxmemory 256mb
      #     ↑ Hard cap on Redis memory. If it exceeds this, old keys are evicted.
      #       Without this, Redis can consume ALL server RAM and crash your host.
      --maxmemory-policy allkeys-lru
      #     ↑ Eviction policy when maxmemory is hit:
      #       allkeys-lru = evict Least Recently Used keys from ALL keys.
      #       Other options: volatile-lru (only keys with TTL set),
      #       allkeys-random, noeviction (errors instead of evicting)
      --requirepass ${REDIS_PASSWORD}
      #     ↑ Enable password authentication. Without this, anyone who can
      #       reach the port has full Redis access. Always set a password.
      --appendonly yes
      #     ↑ Enable AOF persistence. Every write is logged to appendonly.aof.
      #       This file is stored in the volume at /data/appendonly.aof.
      --appendfsync everysec
      #     ↑ Flush AOF to disk every second. Balance of performance vs durability.
      #       "always" = max durability, slow. "no" = fastest, risk data loss.
      --save 60 100
      #     ↑ RDB snapshot: if 100 or more keys changed in 60 seconds, save.
      #       Produces dump.rdb in /data/. Format: --save SECONDS CHANGES
      #       You can add multiple: --save 900 1 --save 300 10 --save 60 100

    volumes:
      - redis-data:/data
      #     ↑ The /data directory is where Redis writes BOTH:
      #       - appendonly.aof  (AOF log file)
      #       - dump.rdb        (RDB snapshot file)
      #       Mount a named volume here so both persist across restarts.

    ports:
      - "127.0.0.1:6379:6379"
      #   ↑ 6379 is Redis' default port. Bind to 127.0.0.1 ONLY.
      #     Redis has no TLS by default. Exposing it publicly is a major
      #     security risk — attackers scan for open Redis ports.
      #     Inside Docker, your app connects via redis:6379 (no host port needed).

    healthcheck:
      test: ["CMD", "redis-cli", "-a", "${REDIS_PASSWORD}", "ping"]
      #     ↑ Run redis-cli ping inside the container.
      #       "-a PASSWORD" is required because we enabled --requirepass.
      #       If Redis is healthy, redis-cli returns "PONG" and exits 0.
      interval: 10s
      timeout: 5s
      retries: 3

    networks: [app-network]

volumes:
  redis-data:

// Connection URL format: redis://:PASSWORD@HOSTNAME:PORT
//   Notice: no username before the colon — Redis uses only password auth

  url: `redis://:${process.env.REDIS_PASSWORD}@redis:6379`
});

client.on('connect', () => console.log('Redis connected'));

await client.set('key', 'value', { EX: 3600 });  // set with 1-hour TTL

Development Mode

Hot reload, the node_modules gotcha, and a dev environment that doesn't fight you

The Core Concept — Why Dev Mode Is Different

In production, your source code is baked into the image during the build. The container is self-contained.

In development, baking code into the image would mean rebuilding the image every time you save a file. That's 30-60 seconds per change — completely unusable. Instead, dev mode uses a bind mount to connect your host's source files directly into the container. Your code editor writes to files on your laptop; the container reads those same files in real time; the dev server (Next.js dev mode, nodemon, ts-node-dev) detects the change and reloads.

📐 Production vs Development — How Code Gets In

Step 1: Write a Minimal Dev Dockerfile

The dev Dockerfile only needs Node.js and your dependencies installed. It does NOT copy source code — that comes via bind mount at runtime.

dockerfile Dockerfile.dev — annotated line by line 
FROM node:20-alpine
# ↑ Node 20 LTS on Alpine Linux. Alpine is small (~5MB base).
#   For dev, size matters less — prioritize compatibility.
#   If you have native modules that need glibc (some npm packages do),
#   use "node:20-slim" (Debian-based) instead of alpine.

WORKDIR /app
# ↑ All subsequent commands run from /app inside the container.
#   Also, when you do "docker exec -it container sh", you land here.
#   Why /app? Convention. Could be /usr/src/app — doesn't matter,
#   just be consistent between Dockerfile and compose volumes.

COPY package.json package-lock.json ./
# ↑ Copy ONLY the package files first (before source code).
#   Why? Docker layer caching: this layer is cached until package.json
#   changes. If you copy everything first, any file change invalidates
#   the npm install cache, making every build slow.
#   The "./" means "copy into the current WORKDIR" = /app/

RUN npm ci
# ↑ Install dependencies from package-lock.json (lockfile-exact).
#   "npm ci" (clean install) vs "npm install":
#   - npm ci: reads package-lock.json exactly, fails if it doesn't match
#   - npm install: may update package-lock.json (unpredictable in Docker)
#   Always use npm ci in Dockerfiles.
#   This installs ALL dependencies including devDependencies
#   (we need them in dev: TypeScript, ESLint, nodemon, etc.)

# DO NOT: COPY . .    ← Don't copy source code here

      #     "." = same folder as docker-compose.dev.yml

      #   ↑ Explicit: use Dockerfile.dev, not the default "Dockerfile"

      - .:/app

      #     "." = the folder containing docker-compose.dev.yml
      #     "/app" = the WORKDIR you set in Dockerfile.dev

      #     the container at /app/. No rebuild needed.

      #     The bind mount "- .:/app" copies EVERYTHING including node_modules.
      #     But your host's node_modules was installed for YOUR OS (macOS/Windows).
      #     The container runs Linux — OS-specific binaries won't work.
      #     OR: you may not have node_modules on host at all (you only run in Docker).
      #     This line creates an ANONYMOUS VOLUME at /app/node_modules.
      #     Anonymous volumes take priority over bind mounts for the same path.
      #     Result: container uses the node_modules from Dockerfile RUN npm ci,
      #     host's node_modules is ignored for this path.

      - /app/.next

      #     Polling = check files every N milliseconds (slower but works everywhere).

      CHOKIDAR_USEPOLLING: "true"

      WATCHPACK_POLL_INTERVAL: "500"
      #   ↑ How often to poll, in milliseconds. 500ms = check twice per second.
      #     Lower = faster detection but more CPU. 300-500ms is a good balance.

    env_file:
      - .env.local
      #   ↑ Load .env.local for dev-specific values (local DB passwords, etc.)

Lean images, secure containers, and everything that actually matters in prod

Choose the Right Base Image

Your base image choice determines your final image size, security surface, and compatibility. Here's the real-world comparison for Node.js:

Base ImageTypical SizeOSUse When
node:20~1.1 GBDebian (full)Never in production — enormous
node:20-slim~240 MBDebian (minimal)When native modules need glibc (bcrypt, sharp)
node:20-alpine~55 MBAlpine LinuxMost apps — best production default
gcr.io/distroless/nodejs20~100 MBDistroless (no shell)Maximum security — no shell to exploit
ℹ️
Alpine vs Slim — the glibc question: Alpine uses musl libc instead of glibc. Most pure JavaScript packages work fine. But native modules that compile against glibc (like bcrypt, sharp, some Prisma engines) may fail on Alpine. If you see errors about missing libraries or GLIBC_2.x not found, switch to node:20-slim.

The solution for big apps: use multi-stage builds. Use the full image for building, then copy only the result into the small final image. Let's build a complete production Dockerfile step by step.

Complete Production Dockerfile — Built Step by Step

We'll build a Next.js production image. The same pattern applies to Express/Fastify/any Node.js app.

Step 1: Install only production dependencies

dockerfile Dockerfile — Stage 1: deps 
# ── Stage 1: Install production dependencies ──────────────────────
FROM node:20-alpine AS deps
# ↑ "AS deps" gives this stage a name. We'll reference it later with
#   "COPY --from=deps". This is just an identifier — name it anything.

RUN apk add --no-cache libc6-compat
# ↑ "apk" is Alpine's package manager (like apt for Ubuntu).
#   "libc6-compat" provides glibc compatibility shims for Alpine.
#   Some npm packages (like Prisma's query engine) need this on Alpine.
#   If your app doesn't need it, you can remove this line.

WORKDIR /app
# ↑ All commands below run from /app. Creates the directory if missing.

COPY package.json package-lock.json ./
# ↑ Copy ONLY package files first for layer caching.
#   "./" = current WORKDIR = /app/
#   Now package.json is at /app/package.json inside the container.

RUN npm ci --only=production
# ↑ "--only=production" installs only dependencies from "dependencies"
#   in package.json. Skips "devDependencies" (TypeScript, ESLint, etc.)
#   This keeps node_modules smaller for the production image.
#   Result: /app/node_modules/ with only production packages.

Step 2: Build the application

dockerfile Dockerfile — Stage 2: builder 
# ── Stage 2: Build the Next.js application ───────────────────────
FROM node:20-alpine AS builder
# ↑ A fresh Alpine image. Nothing from Stage 1 carries over automatically.
#   We'll copy what we need using COPY --from=deps.

RUN apk add --no-cache libc6-compat

WORKDIR /app

# Install ALL deps (including devDeps) for the build
COPY package.json package-lock.json ./
RUN npm ci
# ↑ No "--only=production" here. We need devDependencies:
#   TypeScript compiler, @types/* packages, next (the build tool), etc.

# Generate Prisma client BEFORE building
COPY prisma ./prisma/
RUN npx prisma generate
# ↑ Prisma generate creates type-safe DB client code from schema.prisma.
#   Must run BEFORE "npm run build" because your TypeScript imports
#   from "@prisma/client" which doesn't exist until generated.
#   We copy prisma/ folder first so this layer is cached separately
#   from your application source code.

# Now copy ALL source code
COPY . .
# ↑ Copy everything: src/, public/, next.config.js, tsconfig.json, etc.
#   This comes AFTER npm ci so changing source code doesn't re-run npm ci.

# Build environment variables (public ones only)
ARG NEXT_PUBLIC_API_URL
ENV NEXT_PUBLIC_API_URL=${NEXT_PUBLIC_API_URL}
# ↑ Next.js "NEXT_PUBLIC_*" vars are inlined at build time into JS bundles.
#   Must be provided as build args: docker build --build-arg NEXT_PUBLIC_API_URL=...
#   Private vars (DATABASE_URL, etc.) are NOT set here — they come at runtime.

ENV NEXT_TELEMETRY_DISABLED=1
# ↑ Disable Next.js telemetry (anonymous usage stats). Good practice in CI/Docker.

RUN npm run build
# ↑ Runs "next build" which compiles TypeScript, bundles JavaScript,
#   optimizes images, and generates the .next/ directory.
#   Output: .next/standalone/ (when output: 'standalone' is set in next.config.js)

Step 3: Minimal production runner

dockerfile Dockerfile — Stage 3: runner (final image) 
# ── Stage 3: Minimal production runner ───────────────────────────
FROM node:20-alpine AS runner
# ↑ Fresh Alpine — only ~55MB. Nothing from previous stages.
#   We'll copy only the built artifacts we actually need to run.

WORKDIR /app

ENV NODE_ENV=production
ENV NEXT_TELEMETRY_DISABLED=1

# Security: create a dedicated non-root user and group
RUN addgroup --system --gid 1001 nodejs \
 && adduser  --system --uid 1001 nextjs
# ↑ Why non-root? By default Docker runs as root (UID 0).
#   If an attacker exploits your app, they get root inside the container.
#   With container escapes (rare but possible), root in container = root on host.
#   Running as UID 1001 limits damage significantly.
#   "--system" = system account (no home directory, no login shell)
#   "--gid/--uid 1001" = specific IDs (consistent across containers)

# Copy ONLY what's needed to run Next.js standalone
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
# ↑ "--from=builder" = copy from the builder stage, not your host filesystem.
#   "--chown=nextjs:nodejs" = set file ownership to our non-root user.
#   "/app/.next/standalone" = Next.js standalone output (server.js + minimal node_modules)
#   "./" = copy into current WORKDIR (/app)
#   The standalone output includes a minimal server.js that doesn't need
#   the full next package installed in the final image.

COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
# ↑ Static assets (JS chunks, CSS, fonts) must be served by the Next.js server.
#   Copy them into .next/static/ inside the final image.

COPY --from=builder --chown=nextjs:nodejs /app/public ./public
# ↑ The public/ folder (favicon.ico, robots.txt, images) must be in the final image.

# Add curl for the HEALTHCHECK command
RUN apk add --no-cache curl
# ↑ curl isn't in Alpine by default. We need it to hit the health endpoint.

USER nextjs
# ↑ Drop to non-root. All subsequent operations (and CMD) run as nextjs user.
#   Must come AFTER all COPY commands (which need to set ownership).

EXPOSE 3000

ENV PORT=3000
ENV HOSTNAME=0.0.0.0
# ↑ HOSTNAME=0.0.0.0 tells Next.js server to listen on all network interfaces.
#   Without this, it might listen on 127.0.0.1 only (inside the container),
#   making it unreachable from outside the container.

HEALTHCHECK --interval=30s --timeout=10s --start-period=30s --retries=3 \
  CMD curl -f http://localhost:3000/api/health || exit 1
# ↑ Docker will run this command every 30 seconds.
#   "curl -f" = fail (exit 1) if HTTP response is 4xx or 5xx.
#   "|| exit 1" = if curl fails for any reason, explicitly exit 1.
#   Docker checks this to mark container healthy/unhealthy.
#   Compose uses this for "condition: service_healthy".

CMD ["node", "server.js"]
# ↑ The standalone output creates server.js at /app/server.js.
#   We run it directly with node — no next CLI needed in the final image.
#   This is why the image is small: no next package, just node + server.js.
⚠️
Required: output: 'standalone' in next.config.js
Without this, .next/standalone/ doesn't get created and the runner stage has nothing to copy. Add this to your Next.js config before building: 
// next.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'standalone',  // ← this is required for Docker
  // ... rest of your config
};
module.exports = nextConfig;

Health Check Endpoint

Docker's HEALTHCHECK needs something to call. Implement a /api/health endpoint that checks your real dependencies:

typescript src/app/api/health/route.ts — Next.js App Router 
import { NextResponse } from 'next/server';
import { db } from '@/lib/db';  // your Prisma client

export async function GET() {
  const checks: Record<string, string> = {};
  let healthy = true;

  // Check database connectivity
  try {
    await db.$queryRaw`SELECT 1`;
    checks.database = 'ok';
  } catch (err) {
    checks.database = 'error';
    healthy = false;
  }

  // Return 200 if healthy, 503 if not
  // Docker marks container healthy/unhealthy based on HTTP status code
  return NextResponse.json(
    {
      status: healthy ? 'ok' : 'error',
      timestamp: new Date().toISOString(),
      uptime: process.uptime(),
      checks,
    },
    { status: healthy ? 200 : 503 }
    // ↑ 503 Service Unavailable = curl -f sees this and exits with error
    #   Docker HEALTHCHECK sees the non-zero exit and marks container unhealthy
  );
}

CI/CD with GitHub Actions

Build, push to GHCR, and auto-deploy to your VPS — understanding every step

What the Pipeline Does

The goal: you push code to main → GitHub automatically builds your Docker image, pushes it to the GitHub Container Registry (GHCR), then SSHs into your VPS and pulls the new image. Zero manual steps after git push.

📐 CI/CD Pipeline — Every Step

The Complete Workflow File — Every Line Explained

yaml .github/workflows/deploy.yml — fully annotated 
name: Build and Deploy
# ↑ Display name shown in the GitHub Actions UI

on:
  push:
    branches: [main]
    # ↑ Trigger this workflow on every push to the "main" branch.
    #   Pushes to other branches (feature/*, dev) do NOT trigger this.
  pull_request:
    branches: [main]
    # ↑ Also trigger on PRs targeting main. This lets you see if
    #   the Docker build passes before merging. The deploy job won't
    #   run for PRs (we guard it with "if: github.event_name == 'push'").

permissions:
  contents: read
  packages: write
  # ↑ REQUIRED for pushing to GHCR (GitHub Container Registry).
  #   "packages: write" allows GITHUB_TOKEN to push images to ghcr.io/YOUR_ORG.
  #   Without this, the push step fails with a 403 error.

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}
  # ↑ github.repository = "yourusername/yourrepo" (lowercase).
  #   Final image URL: ghcr.io/yourusername/yourrepo:tag

jobs:
  build:
    runs-on: ubuntu-latest
    # ↑ Run on GitHub's Ubuntu runner (free for public repos, metered for private).
    #   "ubuntu-latest" = most recent Ubuntu LTS. Has Docker pre-installed.

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
        # ↑ Clone your repository into the runner's workspace.
        #   Without this, the runner has no access to your files.
        #   "v4" = use version 4 of the checkout action.

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3
        # ↑ Installs Docker Buildx, an extended builder with:
        #   - Multi-platform builds (build for linux/arm64 on x86 runners)
        #   - Advanced caching (type=gha requires Buildx)
        #   - BuildKit features (--mount=type=secret, etc.)
        #   REQUIRED for the cache-from/cache-to in the build step to work.

      - name: Log in to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          # ↑ Which registry to authenticate with. "ghcr.io" = GitHub's registry.
          username: ${{ github.actor }}
          # ↑ github.actor = the GitHub username that triggered the workflow.
          password: ${{ secrets.GITHUB_TOKEN }}
          # ↑ GITHUB_TOKEN is automatically created by GitHub for each workflow run.
          #   You don't set this up — GitHub injects it. Has access to push packages
          #   because we set "permissions: packages: write" above.

      - name: Extract image metadata (tags and labels)
        id: meta
        uses: docker/metadata-action@v5
        # ↑ This action generates image tags and OCI labels based on git context.
        #   Saves you from manually constructing tag strings.
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=ref,event=branch
            # ↑ On push to main: generates tag "main"
            #   Result: ghcr.io/user/repo:main
            type=ref,event=pr
            # ↑ On PR: generates tag "pr-42" (PR number)
            #   Result: ghcr.io/user/repo:pr-42
            type=sha,prefix=sha-,format=short
            # ↑ Always: generates tag from git commit SHA (first 7 chars)
            #   Result: ghcr.io/user/repo:sha-a1b2c3d
            #   Used for rollbacks: you can always pull a specific commit's image.
            type=raw,value=latest,enable=${{ github.ref == 'refs/heads/main' }}
            # ↑ Only on pushes to main branch: also tag as "latest"
            #   Result: ghcr.io/user/repo:latest (only for main, not PRs)

      - name: Build and push Docker image
        uses: docker/build-push-action@v6
        with:
          context: .
          # ↑ Build context = current directory (your repo root after checkout).
          #   Docker sends all files in "." to the build daemon.
          #   Use .dockerignore to exclude unnecessary files (node_modules, .git, etc.)
          push: ${{ github.event_name != 'pull_request' }}
          # ↑ Only push to registry on actual commits (not on PR builds).
          #   On PRs, we still BUILD (to validate) but don't push (saves storage).
          #   This evaluates to "true" for pushes, "false" for PRs.
          tags: ${{ steps.meta.outputs.tags }}
          # ↑ Use the tags generated by the metadata-action step above.
          #   "steps.meta" = the step with id: meta.
          labels: ${{ steps.meta.outputs.labels }}
          # ↑ OCI labels (author, version, source URL) for the image metadata.
          cache-from: type=gha
          # ↑ READ Docker layer cache from GitHub Actions Cache.
          #   "type=gha" = GitHub Actions cache backend.
          #   On subsequent builds, Docker reuses unchanged layers instead of rebuilding.
          #   This cuts build time from 3-5 minutes to 30-60 seconds on cache hits.
          cache-to: type=gha,mode=max
          # ↑ WRITE all layers to GitHub Actions Cache after the build.
          #   "mode=max" = cache ALL stages including intermediate ones.
          #   (default "mode=min" only caches the final stage — worse cache hit rate)
          #   NOTE: As of April 2025, GitHub Cache API v1 is shut down.
          #   Only v2 is supported. The actions above (v3+) use v2 automatically.
          build-args: |
            NEXT_PUBLIC_API_URL=${{ vars.NEXT_PUBLIC_API_URL }}
            # ↑ Pass build-time arguments from GitHub Actions Variables
            #   (Settings → Secrets and variables → Actions → Variables tab).
            #   "vars." = variables (non-secret). "secrets." = secrets (encrypted).
            #   NEXT_PUBLIC_* must be provided here because they're baked into the JS bundle.

  deploy:
    runs-on: ubuntu-latest
    needs: build
    # ↑ "needs: build" = only start this job AFTER the build job succeeds.
    #   If build fails, deploy never runs. Safety guarantee.
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    # ↑ Only deploy on actual pushes to main. NOT on PRs.
    #   Both conditions must be true (&&).
    #   github.ref == 'refs/heads/main' = pushed to main branch
    #   github.event_name == 'push' = it's a push, not a PR

    steps:
      - name: Deploy to production VPS via SSH
        uses: appleboy/ssh-action@v1
        # ↑ Popular GitHub Action that SSHes into a server and runs commands.
        with:
          host: ${{ secrets.VPS_HOST }}
          # ↑ Your VPS IP address or domain name.
          #   Stored in GitHub Secrets: Settings → Secrets and variables → Actions
          username: ${{ secrets.VPS_USER }}
          # ↑ SSH username on your server (e.g., "ubuntu", "root", "deploy")
          key: ${{ secrets.VPS_SSH_KEY }}
          # ↑ The PRIVATE SSH key content (not the .pub file).
          #   How to set up: see next section below.
          script: |
            cd /opt/myapp
            # ↑ Change to your project directory on the VPS.
            #   Create this beforehand: sudo mkdir -p /opt/myapp

            echo ${{ secrets.GITHUB_TOKEN }} | \

Ollama — What It Is and How It Works

Ollama is a local LLM server. It downloads and runs open-source language models (Llama 3, Mistral, Gemma, Qwen) on your own hardware and exposes an OpenAI-compatible API on port 11434. This means you can use the standard openai npm package to talk to it.

Ollama in Docker lets you add a local AI inference server to any compose stack, with the model files persisted in a named volume so you don't re-download on restart.

CPU-only mode works anywhere — no NVIDIA drivers, no toolkit. A 7B model (4-bit quantized) needs ~4 GB RAM and produces ~5-10 tokens/second on a modern CPU. Fine for development or light usage.

yaml docker-compose.yml — Ollama CPU 
services:
  ollama:
    image: ollama/ollama:latest
    # ↑ Official Ollama image. "latest" is fine here — Ollama maintains
    #   backwards compatibility and model files are stored in a volume.
    container_name: ollama
    restart: unless-stopped

    volumes:
      - ollama-models:/root/.ollama
      # ↑ /root/.ollama is where Ollama stores:
      #   - Downloaded model files (can be 4-20+ GB each)
      #   - Model configuration
      #   CRITICAL: mount a named volume here or all models re-download on restart.

    ports:
      - "127.0.0.1:11434:11434"
      # ↑ 11434 is Ollama's API port. Bind to 127.0.0.1 (localhost only).
      #   If you're building a web app that calls Ollama, it connects via
      #   the Docker network (ollama:11434), not through this host port.
      #   This port is only for testing/debugging from your host machine.

    environment:

import OpenAI from 'openai';
// ↑ Yes, the official OpenAI npm package works with Ollama.
//   Ollama's API is designed to be OpenAI-compatible.
//   Install: npm install openai

const ollama = new OpenAI({
  baseURL: 'http://ollama:11434/v1',
  // ↑ "ollama" = Docker service name (works when this code runs inside Docker).
  //   If you're calling from outside Docker (localhost): 'http://localhost:11434/v1'
  //   The "/v1" path is Ollama's OpenAI-compatible API prefix.
  apiKey: 'ollama',
  // ↑ Ollama doesn't require an API key, but the OpenAI client requires
  //   the field to be non-empty. Any string works here.
});

export async function generateText(prompt: string): Promise<string> {
  const response = await ollama.chat.completions.create({
    model: 'llama3.2',
    // ↑ Must match a model you've pulled: docker exec ollama ollama pull llama3.2
    messages: [
      { role: 'system', content: 'You are a helpful assistant.' },
      { role: 'user',   content: prompt }
    ],
    stream: false,
  });
  return response.choices[0].message.content ?? '';
}

export async function streamText(prompt: string) {
  const stream = await ollama.chat.completions.create({
    model: 'llama3.2',
    messages: [{ role: 'user', content: prompt }],
    stream: true,    // ← enables streaming (token by token)
  });
  for await (const chunk of stream) {
    process.stdout.write(chunk.choices[0]?.delta?.content ?? '');
  }
}

MCP with Docker

Run Model Context Protocol servers as isolated containers in your AI stack

What Is MCP and Why Docker?

MCP (Model Context Protocol) is Anthropic's open standard for connecting AI agents to external tools — databases, file systems, APIs, and more. Each MCP server is a small process that exposes a set of "tools" the AI can call. Your AI agent orchestrates which tools to use based on the user's request.

Docker is perfect for MCP servers because each server is isolated: if the filesystem server crashes, the database server keeps running. You can version, restart, and scale each server independently. And Docker networking means the AI agent connects to mcp-filesystem:3001 internally — nothing is exposed to the internet.

yaml docker-compose.yml — AI agent + MCP servers 
services:

  # ── Your AI-powered application ──────────────────────────────────
  app:
    build:
      context: .
    environment:
      # MCP server URLs — connect via Docker service names (internal DNS)
      MCP_FILESYSTEM_URL: http://mcp-filesystem:3001
      MCP_POSTGRES_URL:   http://mcp-postgres:3002
      OLLAMA_URL:         http://ollama:11434
      # ↑ All "hostnames" here are Docker service names.
      #   Docker DNS resolves them to container IPs automatically.
      #   No need to know the actual IPs — they change on each restart anyway.
    depends_on:
      - mcp-filesystem
      - mcp-postgres
      - ollama
    networks: [ai-network]
    ports:
      - "3000:3000"

  # ── MCP Server: File System Access ───────────────────────────────
  mcp-filesystem:
    image: node:20-alpine
    working_dir: /srv
    command: npx -y @modelcontextprotocol/server-filesystem /data
    # ↑ "npx -y" downloads and runs the MCP filesystem server.
    #   "/data" = the directory this server exposes to the AI agent.
    #   The AI can read/write files in /data (mounted from your host below).
    volumes:
      - ./ai-data:/data:ro
      #   ↑ Mount your local ai-data/ folder into the container.
      #     ":ro" = read-only. AI agent can only READ these files, not modify.
      #     Remove ":ro" if you want the agent to be able to write files.
    networks: [ai-network]
    # No ports: — this server only needs to be reachable by the app container.
    restart: unless-stopped

  # ── MCP Server: PostgreSQL Query Access ──────────────────────────
  mcp-postgres:
    image: node:20-alpine
    working_dir: /srv
    command: npx -y @modelcontextprotocol/server-postgres
    environment:
      POSTGRES_CONNECTION_STRING: >-
        postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}
      # ↑ The MCP postgres server connects to your postgres service.
      #   "postgres" = service name, Docker resolves it to the DB container.
      #   The AI agent can query your DB via natural language through this server.
    depends_on:
      postgres:
        condition: service_healthy
    networks: [ai-network]
    restart: unless-stopped

  # ── LLM Backend ──────────────────────────────────────────────────
  ollama:
    image: ollama/ollama:latest
    volumes:
      - ollama-models:/root/.ollama
    environment:
      OLLAMA_KEEP_ALIVE: "24h"
    networks: [ai-network]
    restart: unless-stopped

  # ── Database ─────────────────────────────────────────────────────
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
      PGDATA: /var/lib/postgresql/data/pgdata
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER}"]
      interval: 10s
      retries: 5
      start_period: 30s
    networks: [ai-network]
    restart: unless-stopped

volumes:
  ollama-models:
  postgres-data:

networks:
  ai-network:
    driver: bridge

Understanding Docker Disk Usage

Docker accumulates four types of data on disk. Left unchecked, they will fill your VPS storage:

TypeWhat It IsWhen It GrowsSafe to Remove?
ImagesDownloaded + built imagesEvery docker pull / docker build✅ If not in use by any container
ContainersStopped containers still on diskAfter docker stop without --rm✅ All stopped ones
VolumesNamed + anonymous volume dataAny write inside mounted volume⚠️ Only if you don't need the data
Build cacheCached Dockerfile layersEvery docker build✅ Yes — Docker rebuilds on next build

# Summary of Docker disk usage

# Output:
# TYPE            TOTAL   ACTIVE  SIZE      RECLAIMABLE
# Images          23      5       4.2GB     3.1GB (73%)
# Containers      3       2       48kB      0B
# Local Volumes   8       4       2.1GB     890MB
# Build Cache     47      0       1.8GB     1.8GB
#
# "RECLAIMABLE" = safe to remove (not currently used by running containers)

# Detailed breakdown — see EACH image/volume/container
docker system df -v
bash Step 2: Clean up (from safe to aggressive) 
# ── SAFE: Remove specific categories ────────────────────────────

docker container prune -f
# Remove all STOPPED containers (not running ones).
# "-f" = force (don't ask for confirmation).
# Running containers are NOT affected.

docker image prune -f
# Remove "dangling" images — images with no tag AND not used by any container.
# These are leftover build layers from previous builds.
# Does NOT remove images you're using or images with tags.

docker image prune -a -f
# Remove ALL unused images — even tagged ones not used by any container.
# ↑ More aggressive: removes images for services that are stopped.
#   After this, "docker compose up" will re-pull images — may be slow.

docker builder prune -f
# Remove ALL build cache. Next build is slower (full rebuild) but disk is free.

docker builder prune --keep-storage 1GB -f
# Remove build cache but KEEP 1GB of the most recent cache.
# Balances disk usage and build speed.

# ── DANGEROUS: Nuclear option ────────────────────────────────────
docker system prune -af --volumes
# Removes EVERYTHING unused:
# - All stopped containers
# - All unused images
# - All unused networks
# - ALL VOLUMES (--volumes flag!) — this DELETES database data if the
#   DB container is not currently running. USE WITH EXTREME CAUTION.
# Never run on a production server with live database volumes.

Dockerfile Instruction Reference

dockerfile Every instruction with explanation 
FROM node:20-alpine AS stage-name
# Start from a base image. "AS name" creates a named stage for multi-stage builds.
# Always pin a version. "node:20-alpine" not "node:latest".

ARG BUILD_ENV=production
# Build-time variable. Passed with: docker build --build-arg BUILD_ENV=dev
# Only exists DURING the build, not at runtime. Except NEXT_PUBLIC_* (inlined in JS).

ENV NODE_ENV=production
# Runtime environment variable. Baked into the image and available when container runs.
# Apps read these with process.env.NODE_ENV.

WORKDIR /app
# Set the working directory for all subsequent instructions.
# Creates the directory if it doesn't exist. Like: mkdir -p /app && cd /app

COPY package*.json ./
# Copy files from build context (your project folder) into the image.
# "./". = current WORKDIR = /app/
# "package*.json" matches: package.json AND package-lock.json

ADD archive.tar.gz /app/extracted/
# Like COPY but: auto-extracts .tar.gz files. Can also copy from URLs.
# Prefer COPY for regular files — ADD's auto-extract is easy to miss.

RUN npm ci && npx prisma generate
# Execute commands. Each RUN creates a new image layer.
# Combine multiple commands with && to minimize layers and image size.

USER appuser
# Switch to a non-root user for security.
# All subsequent RUN/CMD/ENTRYPOINT run as this user.

EXPOSE 3000
# Documentation only. Does NOT publish ports. Just metadata.
# Port mapping happens in compose (-p HOST:CONTAINER) or docker run.

VOLUME ["/data"]
# Declare a mount point. Documentation — tells readers "mount something here".
# Does NOT create an actual volume binding (compose does that).

HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD curl -f http://localhost:3000/api/health || exit 1
# Docker runs this command to check if the container is healthy.
# Exit 0 = healthy. Exit 1 = unhealthy. Compose uses this for depends_on.

ENTRYPOINT ["node"]
# The FIXED command. Cannot be overridden by "docker run image somearg".
# Use for containers that always run the same program.

CMD ["server.js"]
# Default arguments. If ENTRYPOINT is set, these are arguments to it.
# CAN be overridden: docker run image other-args
# Exec form (array) is required for correct signal handling (Ctrl+C, SIGTERM).

COPY --from=builder --chown=appuser:appgroup /app/dist ./dist
# Multi-stage: copy files FROM a previous stage.
# "--chown=user:group" sets file ownership (required when using USER).
# "/app/dist" = source path in the builder stage.
# "./dist" = destination in current stage (relative to WORKDIR).
