Platform overview — which tool, when, and why

Before writing a single workflow, you need to understand the landscape. These platforms fall into two categories: general automation platforms (Zapier, Make, n8n, Activepieces, Pipedream) that connect apps and trigger actions, and AI-native flow builders (Langflow, Flowise) that are purpose-built for chaining LLM calls, tools, and memory.

Foundation steps
  1. Pick one platform to start with. Recommendation: n8n on your KVM VPS (free, self-hosted, dev-friendly) or Make cloud (fastest to test). Don't try multiple at once.
  2. Install n8n via Docker Compose on your VPS: docker compose up -d. Access the editor at http://your-vps:5678.
  3. Build the classic "Hello World" automation: trigger on a webhook → do something (send email, write to Postgres, call an API) → respond.
  4. Add your first AI step: in n8n use the "AI Agent" node, or in Make add an "OpenAI / Claude" module. Send it a message and see the response.
  5. Connect your Anthropic API key in the credentials panel. Understand how the platform stores secrets (encrypted credential store, not env vars).
  6. Build a simple "question → Claude → answer" workflow exposed as a webhook. This is your first AI-powered API.
  7. In Flowise: install via Docker, create a "Basic LLM Chain" flow, connect Claude, and get the embedded chat widget working on a test page.
✅

Checkpoint: n8n running on VPS behind Nginx. One working webhook → Claude → response workflow. Flowise chat widget embedded on a test HTML page.

n8n credential storage (how it works)

n8n stores credentials encrypted in its database using a N8N_ENCRYPTION_KEY you set. Never hardcode API keys in workflow nodes — always use the Credentials panel. The key is encrypted at rest, decrypted only at execution time.

# n8n docker-compose env — set this ONCE, never change it environment: N8N_ENCRYPTION_KEY: "your-32-char-random-string-here" N8N_BASIC_AUTH_ACTIVE: "true" N8N_BASIC_AUTH_USER: "admin" N8N_BASIC_AUTH_PASSWORD: "your-strong-password"

⚠️ If you change N8N_ENCRYPTION_KEY after storing credentials, all stored credentials become unreadable. Set it once and back it up securely.

Best practices for Phase 0
Store all keys in the platform's credential store — never in workflow nodes
Set usage limits on your Anthropic key (console → Settings → Limits) Create a separate key per platform/project Never commit .env files to git

Phase 1 — Junior

AI agent nodes + MCP integration

n8n AI Agent node · tool-calling workflows · MCP as workflow tool · Flowise agents · 3–4 weeks

🧭
Concepts — AI agent nodes in automation platforms

At Phase 1, you graduate from "call Claude and return the result" to "let Claude decide what tools to call". Every major platform now has an AI Agent node that runs a ReAct loop internally — you just configure the tools it can use.

In n8n, the "AI Agent" node connects to an LLM (Claude, GPT, Gemini) and a set of "tools" — which can be other n8n nodes, HTTP requests, database queries, or MCP servers. The agent loop runs inside n8n. You see each tool call in the execution log.

In Flowise, the "Agent" flow type chains a ReAct agent with a toolset. Tools are pre-built (Calculator, Web Browser, Custom Function) or your own API calls. The agent reasons, picks tools, and assembles the final answer.

The key insight: your MCP server from Phase 1 code work can plug directly into n8n as an MCP Tool node. This means code-built tools and visual-workflow agents can share the same tool backend.

🔢
Steps
  1. In n8n, create a new workflow. Add an "AI Agent" node. Connect it to Claude via the Anthropic credential. Set a system prompt.
  2. Add a "Calculator" tool, a "Wikipedia" tool, and a custom "HTTP Request" tool to the agent. Test multi-step reasoning.
  3. Connect your Phase 1 MCP server as an MCP Tool node (n8n v1.88+ has native MCP support): set the URL to https://mcp.yourdomain.com/mcp.
  4. In Flowise, build a "ReAct Agent" flow: LLM node → Tools (Calculator + Custom API Tool) → Memory (Buffer) → Chat output.
  5. Build a "triage" workflow: webhook receives a support ticket → Claude classifies it (billing/tech/other) → routes to different sub-workflows based on classification.
  6. Add error-handling branches to every AI node: if the AI fails (timeout, rate limit), route to a fallback node that returns a default response.
  7. Expose your Flowise agent flow as a REST API and call it from an n8n workflow — composing two platforms.
✅

Checkpoint: n8n AI Agent using your MCP server tools. Flowise ReAct agent with memory. Triage workflow routing to sub-workflows. Both deployed on VPS.

Connecting your MCP server to workflow platforms

Your code-built MCP server (from the main guide Phase 1) can plug directly into n8n as a tool source. This is the most powerful integration: you get the visual workflow orchestration of n8n plus the custom TypeScript tools of your MCP server.

n8n MCP Tool node setup
# In n8n AI Agent node → Add Tool → MCP Client # Settings: Server URL: https://mcp.yourdomain.com/mcp Auth header: x-api-key: YOUR_MCP_API_KEY Timeout: 30000ms # n8n will call listTools() at workflow activation # and make the discovered tools available to the agent
Flowise — Custom Tool pointing to MCP
// In Flowise: Add "Custom Tool" node Name: "mcp_search" Description: "Search the web using the MCP server tool" Schema: { "query": { "type": "string", "description": "search query" } } Function: async ({ query }) => { const res = await fetch('https://mcp.yourdomain.com/tools/search_web', { method: 'POST', headers: { 'x-api-key': process.env.MCP_API_KEY }, body: JSON.stringify({ query }) }); return (await res.json()).result; }
Make (Integromat) — HTTP module to MCP
Module: HTTP → Make a request URL: https://mcp.yourdomain.com/tools/search_web Method: POST Headers: x-api-key: {{connection.mcp_api_key}} Content-Type: application/json Body: { "query": "{{1.message}}" }

💡 Any automation platform with an HTTP node (Make, Zapier, Pipedream, Activepieces) can call your MCP server's tools directly over its REST API — you don't need native MCP protocol support. MCP is just HTTP+JSON under the hood.

Phase 2 — Intermediate

Multi-step agents + memory + real integrations

Orchestration in n8n · Langflow agent chains · memory nodes · sub-workflows · CI/CD for workflows · 4–6 weeks

🧭
Concepts — orchestration in visual platforms

At Phase 2, you build workflows that mimic the multi-agent patterns from your code work — but entirely (or partially) in visual tools. n8n's "Execute Workflow" node lets one workflow call another, creating an orchestrator-subagent pattern visually.

In Langflow, you can chain multiple agent flows: an orchestrator flow that calls subagent flows via HTTP, each with different tool sets. Langflow's "Sub Flow" component makes this native. Memory is a first-class node (buffer memory, Postgres memory, Redis memory).

The key skill at this phase is deciding what belongs in code vs visual tools. Rule of thumb: business logic and integrations → visual platforms. Custom tools, data transformation, performance-critical paths → code (your MCP server). Don't fight the platform's strengths.

🔢
Steps
  1. Build an orchestrator workflow in n8n that calls multiple sub-workflows in parallel using the "Execute Workflow" node with "Execute in parallel" mode.
  2. Add a Postgres memory node in Flowise: configure it to store conversation history per session_id. Test that memory persists across chat sessions.
  3. Build a "research pipeline" workflow: webhook → Claude outlines subtasks → parallel web search sub-workflows → Claude synthesizes results → respond.
  4. Connect your MCP server's pgvector memory to Flowise as an "External Memory" node using its REST API.
  5. Add Zapier/Make webhook triggers that feed into your n8n workflows (e.g. new form submission in Typeform → n8n → AI processing → save to Postgres).
  6. Version-control your n8n workflows: use n8n's export API to dump all workflow JSONs to a git repo on every change.
  7. Build a Langflow multi-agent flow: Orchestrator agent → calls 2 sub-flows (researcher + writer) → assembles output.
✅

Checkpoint: Orchestrator n8n workflow delegates parallel tasks to sub-workflows. Flowise agent with Postgres memory. Workflow JSONs version-controlled in git.

Deployment — CI/CD for workflows

At Phase 2, you should treat your n8n workflow JSONs as infrastructure code. Export them to git, review changes like PRs, and deploy them programmatically.

Workflow version control script
#!/bin/bash # export-workflows.sh — run via cron or GitHub Actions N8N_URL="https://n8n.yourdomain.com" N8N_KEY="your-n8n-api-key" # Export all workflows curl -s -H "X-N8N-API-KEY: $N8N_KEY" \ "$N8N_URL/api/v1/workflows" | \ jq -r '.data[] | "\(.id) \(.name)"' | \ while read id name; do curl -s -H "X-N8N-API-KEY: $N8N_KEY" \ "$N8N_URL/api/v1/workflows/$id" \ > "workflows/$(echo $name | tr ' ' '_').json" done cd workflows && git add -A && git commit -m "Auto-export $(date)" && git push
Import workflows on deploy (n8n API)
#!/bin/bash # import-workflow.sh — deploy a workflow JSON to n8n curl -X POST \ -H "X-N8N-API-KEY: $N8N_KEY" \ -H "Content-Type: application/json" \ -d @workflows/my_workflow.json \ "$N8N_URL/api/v1/workflows"

Phase 3 — Senior

Production workflows — reliability, security, scale

Queue-backed execution · auth hardening · multi-tenant workflows · monitoring · zero-downtime updates · 6–8 weeks

🧭
Concepts — production-grade workflow platforms

At Phase 3, your workflows are serving real users. The concerns shift to: what happens when an AI call fails mid-workflow? How do you ensure one tenant's heavy workflow doesn't affect another? How do you update workflows without dropping in-flight executions?

n8n queue mode: instead of running workflows in the main process, n8n can push executions to a Redis-backed queue and run them in separate worker processes. This gives you horizontal scaling, retry-on-crash, and isolation between executions.

Workflow auth: by default, n8n webhooks are public (with a random path). In production, add authentication: Webhook node → Authentication → Header Auth (require x-api-key header). Treat webhook URLs as secrets.

🔢
Steps
  1. Switch n8n to queue mode: add Redis as a queue backend, deploy n8n main + n8n worker as separate containers. Worker count = CPU cores available.
  2. Add webhook authentication to all public-facing n8n webhooks: Header Auth with an x-api-key that clients must include.
  3. Implement multi-tenant workflow routing: a single entry webhook reads tenantId from the request, looks up tenant config in Postgres, and routes to tenant-specific sub-workflows.
  4. Set up n8n with Langfuse integration: use n8n's custom HTTP node to log every AI execution to Langfuse for cost and quality tracking.
  5. Add a dead-letter workflow: any workflow that fails 3 times sends a Slack/Telegram alert with full execution context.
  6. Configure n8n workflow-level rate limiting: use a Redis counter before the AI node to enforce per-tenant request limits.
  7. Export and test workflow rollback: keep the last 3 versions of every workflow JSON in git so you can redeploy a previous version in under 2 minutes.
✅

Checkpoint: n8n in queue mode with Redis. All webhooks authenticated. Multi-tenant routing live. Execution costs visible in Langfuse. Dead-letter alerting working.

// Code node: verify Stripe/GitHub webhook signature const crypto = require('crypto'); const secret = $credentials.webhookSecret; const payload = JSON.stringify($input.body); const signature = $input.headers['x-hub-signature-256']; const expected = 'sha256=' + crypto .createHmac('sha256', secret) .update(payload) .digest('hex'); if (signature !== expected) throw new Error('Invalid signature'); return $input.all();

Expert-level concepts

At expert level, the workflow platform itself becomes part of your product. You build custom n8n nodes for your specific integrations, operate n8n clusters on Kubernetes for thousands of workflow executions per day, and potentially offer "workflow builder" capabilities to your own users (white-label n8n or Flowise).

Custom n8n nodes are npm packages that add new trigger/action types to n8n. You build them when the built-in HTTP node isn't enough — complex OAuth flows, binary data handling, streaming responses, or deep integration with your MCP server protocol.

Workflow-as-product: n8n's self-hosted version can be embedded in a SaaS product. Each tenant gets their own workflow environment, isolated credentials, and workflow templates. This is how Retool, Zapier, and similar platforms work under the hood.

🔢
Steps
  1. Build a custom n8n node for your MCP server: implement INodeType with proper credential types, operation definitions, and execute function.
  2. Publish the node to npm as n8n-nodes-your-product. Install it in your n8n instance via N8N_CUSTOM_EXTENSIONS env var.
  3. Deploy n8n on Kubernetes: separate deployments for n8n-main and n8n-worker, HPA on worker pods based on Redis queue depth.
  4. Set up workflow monitoring at scale: push n8n execution metrics to Prometheus → Grafana dashboard (execution rate, error rate, p99 latency, cost/hour).
  5. Build a workflow template system: maintain a library of workflow JSON templates for common use cases. Deploy to new tenant environments via the n8n API on tenant signup.
  6. Implement a multi-tenant Flowise deployment: one Flowise instance per tenant namespace, or single instance with tenant-isolated chatflow IDs and API keys.
  7. Build an LLM cost attribution pipeline: parse Anthropic API responses in your workflow platform, attribute token costs to tenant + workflow + step, store in Postgres, expose in a billing dashboard.
✅

Checkpoint: Custom n8n node published and installed. n8n on K8s with HPA. Grafana dashboard for workflow metrics. Workflow templates auto-deployed on tenant signup. Cost attribution live.

import { IExecuteFunctions, INodeType, INodeTypeDescription } from 'n8n-workflow'; export class MyMcpTool implements INodeType { description: INodeTypeDescription = { displayName: 'My MCP Tool', name: 'myMcpTool', group: ['transform'], version: 1, properties: [ { displayName: 'Tool Name', name: 'toolName', type: 'options', options: [ { name: 'Search Web', value: 'search_web' }, { name: 'Get Weather', value: 'get_weather' }, ], default: 'search_web', }, { displayName: 'Query', name: 'query', type: 'string', default: '', } ], }; async execute(this: IExecuteFunctions) { const toolName = this.getNodeParameter('toolName', 0) as string; const query = this.getNodeParameter('query', 0) as string; const creds = await this.getCredentials('myMcpApi'); const res = await this.helpers.httpRequest({ method: 'POST', url: `${creds.serverUrl}/tools/${toolName}`, headers: { 'x-api-key': creds.apiKey as string }, body: { query }, json: true, }); return this.helpers.returnJsonArray(res); } }
