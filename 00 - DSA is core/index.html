Brute force first, out loud. Then optimize. Never jump to clever.
Ask: which data structure makes this one operation O(1)?

Articulate your thinking. The interview is about your process.

01
HashMap / HashSet
Time O(n) · Space O(n) · Converts O(n²) brute force to O(n)
Core Concept

Trade space for time. Store what you have already seen so future lookups are O(1) instead of re-scanning. The key question every time: what do I store as the key, and what as the value?

The complement trick: instead of looking for "who matches x", store "what you still need" so the next element can check itself.

Analogy — Library catalogInstead of scanning every shelf for a book, you look it up in the catalog and go directly to the shelf. One O(1) lookup instead of O(n) search. The catalog costs space to build, but every query is instant.
Analogy — DB indexSELECT WHERE id=5 without index: full table scan O(n). With a hash index: O(1). You pay O(n) space once; every query is free. Same tradeoff you make in code.

3 Mental Models

Complement store

Store what you need, not what you have. Next element checks if it IS what someone needed. Two Sum, Three Sum family.

Frequency map

Counter(arr) gives {val: count}. Group anagrams, top-K, majority element all use this shape.

Deduplicate

x in set is O(1). x in list is O(n). Always convert to set before membership checks.

Group by property

Sort each word → use sorted word as key. All anagrams share the same key and land in the same bucket.

02
Two Pointer
Time O(n) · Space O(1) · Two variants: opposite-ends + fast/slow
Core Concept

Use two indices instead of one to eliminate nested loops. Opposite-ends: on sorted arrays, start both ends and move inward — sorted order tells you exactly which direction to move. Fast/Slow: fast moves 2 steps, slow moves 1. If there's a cycle, they must eventually meet.

Analogy — Squeeze a sorted bagLooking for a pair summing to target. Hold both ends. Sum too small → push left hand right (increase sum). Sum too big → push right hand left (decrease sum). Never need to check all O(n²) pairs.
Analogy — Tortoise and hare (Floyd's)On a circular track, the faster runner will eventually lap the slower one. If they meet, there's a cycle. If fast reaches null first, no cycle. Detects cycle in O(n), O(1) space — better than using a visited set.

Edge Cases — Always Check
  • Array length ≤ 1 — trivially true or no work needed
  • All same: [3,3,3] target=6 — skip duplicates carefully in 3Sum
  • Fast/slow: check fast and fast.next before fast.next.next
  • 3Sum dedup: after picking pivot, skip same pivot values; inside window, skip same L/R values
  • Trapping Rain Water: track max_left and max_right as you move pointers
Tips & Tricks
  • Must sort first if not already sorted — two-pointer only works on monotonic sequences
  • 3Sum: fix outer element O(n), two-pointer inner O(n) → total O(n²) vs O(n³) brute
  • In-place removal: write pointer w marks next write position. Read pointer r scans. arr[w++] = arr[r] when valid
  • Finding cycle start: after slow/fast meet, reset slow to head. Move both one step at a time. They meet at cycle start
  • Palindrome: skip non-alphanumeric with while l<r and not s[l].isalnum(): l+=1

03
Sliding Window
Time O(n) · Space O(k) · Each element enters and exits the window exactly once
Core Concept

Maintain a subarray window [l, r]. Expand right to add elements. Shrink left when a constraint is violated. Never recompute from scratch — just subtract what left and add what entered. Total work: O(n) because each element is processed at most twice (once enter, once leave).

Fixed size: window = k. Slide by removing arr[r-k] as you add arr[r]. Variable size: expand until constraint breaks, then shrink until valid again.

Analogy — Train windowYou look out at scenery through a fixed-width window as the train moves. New scenery enters on the right, old exits on the left. You don't re-observe everything — you only process the change at each edge. O(1) update vs O(k) recompute.

Edge Cases — Always Check

  • All same characters — window expands to entire string

Tips & Tricks

  • "At least K" trick: atLeast(k) = atMost(k) - atMost(k-1) — used in #930, #992

Prefix Sum
Build O(n) once · Query O(1) · Space O(n) — pay once, answer many
Core Concept

Pre-compute cumulative sums. Any range sum arr[l..r] = prefix[r+1] - prefix[l]. You pay O(n) space and build time once; every subsequent range query is O(1). The DB equivalent: precomputed aggregates on indexed columns.

Analogy — Car odometerYour odometer shows total distance from start. To know how far you drove today, subtract yesterday's reading. No need to replay every kilometre — just subtract two numbers. Prefix sums are your odometer readings.
Analogy — Bank balanceprefix[i] = total deposits through day i. "How much from day 3 to day 7?" = prefix[7] - prefix[2]. No need to add those 5 transactions — just subtract two numbers.

Binary Search
Time O(log n) · Space O(1) · Works on sorted arrays AND answer spaces
Core Concept

On any monotonic (sorted) space, eliminate half the possibilities each step. Everyone knows array binary search. The power move: binary search the answer itself. If you can write a feasible(x) function that returns true/false, you can binary search x across valid range.

Analogy — Dictionary lookupYou don't scan every page for a word. You open the middle, decide "before or after", then repeat on half the space. Max log₂(1,000,000) = 20 lookups for any word regardless of dictionary size.
Analogy — Binary search on answer (Koko Eating Bananas)"Min speed k to eat all piles in H hours?" Try every k? O(max_pile × n). Instead: write feasible(k) = can finish at speed k? Then binary search k ∈ [1, max_pile]. O(n log max_pile) — much faster.

Stack / Monotonic Stack
Time O(n) amortized · Space O(n) · Each element pushed and popped exactly once
Core Concept

A stack gives O(1) access to the most recently seen element. A monotonic stack maintains elements in sorted order — when a new element violates the order, pop elements until it's restored. Each popped element has just found its answer (the element that caused it to be popped).

Analogy — Browser historyBack button = top of stack. The page you just came from is always instantly accessible. Function calls = call stack. The most recent frame is always at top. O(1) access to the "most recent" is the value stacks provide.
Analogy — Monotonic stack as bouncerBouncer only lets in people shorter than the last person in line (decreasing stack). When a taller person arrives, kick out everyone shorter — those kicked-out people just found their "next taller person" the moment they got ejected.

BFS / DFS on Graphs & Trees
Time O(V+E) · BFS → shortest path · DFS → all paths, cycles, ordering
Core Concept

BFS uses a queue — explores level by level. Every node at distance d is visited before any node at distance d+1. Use when you need the shortest path in an unweighted graph, or want nearest X to Y.

DFS uses a stack or recursion — goes as deep as possible before backtracking. Use for: all paths, cycle detection, topological sort, connected components, flood fill.

Analogy — Ripple vs. divingBFS = stone dropped in water. Ripples expand evenly outward — every point at radius 1 before radius 2. DFS = diving deep into one lane of the pool before surfacing and trying the next lane.
Analogy — npm install (topological sort)Package A needs B. B needs C. DFS finds finish order (post-order = topological order = install order). If DFS finds a back-edge to a currently-visited node, it's a circular dependency = error.

BFS uses deque (queue). Multi-source BFS: add ALL starting points before the loop begins.
DFS: mark visited BEFORE adding to queue/stack — prevents processing same node twice.
Grid BFS: 4 directions = [(0,1),(0,-1),(1,0),(-1,0)]. Check bounds before accessing cell.

  • Disconnected graph — outer loop over all unvisited nodes
  • Grid bounds — 0 <= r < rows and 0 <= c < cols
  • Cycle in directed graph: use 3 states — unvisited, in-stack, done
  • Empty graph / single node — handle before traversal

1D Dynamic Programming
Time O(n) · Space O(n) or O(1) optimized · Overlapping subproblems
Core Concept

DP applies when: (1) the problem has optimal substructure — the optimal solution uses optimal solutions to subproblems, and (2) overlapping subproblems — the same smaller problem appears multiple times. Store each subproblem result once.

Two approaches: Tabulation (bottom-up: fill table from base cases) and Memoization (top-down: recurse + cache). Same complexity; tabulation usually cleaner in interviews.

Framework — 4 steps every DP problem1) Define dp[i] in plain English. 2) Write the transition: dp[i] depends on which previous values? 3) Set base cases dp[0], dp[1]. 4) Return dp[n] or max(dp). Never start coding without step 1.

4 DP Problem Shapes

Count ways

dp[i] = number of ways to reach state i. Climbing stairs: dp[i] = dp[i-1] + dp[i-2]. Answer adds up paths.

Optimize value

dp[i] = max/min achievable. House robber, coin change. At each step: take or skip, pick the better one.

Boolean feasibility

dp[i] = True/False. Word break: dp[i] = any dp[j] where word[j..i] is in the dictionary.

Space optimization

If dp[i] only uses dp[i-1] and dp[i-2], replace the array with two variables. O(n) → O(1) space.

Edge Cases — Always Check
  • Array length 0 or 1 — dp may not have index 1; handle explicitly

  • LIS: answer is max(dp), not dp[-1] — LIS can end at any position

Sort First / Interval Problems
Time O(n log n) dominated by sort · O(n) scan after sorting
Core Concept

Sorting converts a chaotic problem into a structured one where greedy logic works. Most interval problems become trivial once sorted by start time: each interval only needs to be compared with the last one in the output — you never need to go back further.

Analogy — Calendar scheduling10 meetings with random start times. Sorted by start: scan once, merging any that overlap the last booked meeting. O(n) scan after O(n log n) sort. No need to compare every pair — that would be O(n²).

Edge Cases — Always Check
  • Single interval — return as-is, no merging
  • Touching intervals [1,4] and [4,6] — clarify: overlap or adjacent? (<= vs <)
  • Fully contained: [1,10] contains [3,5] — always use max(last_end, end)
  • Insert interval: 3 regions (before, overlapping, after). Process each separately.
  • Meeting Rooms II: need min-heap of end times, not just sort
Tips & Tricks
  • Merge problems: sort by start. Scheduling / greedy: sort by end time (keep earliest-ending intervals)
  • Meeting Rooms II (#253): min-heap of end times. If heap[0] <= current start, reuse that room (pop, push new end). Else new room.
  • Non-overlapping (#435): greedy — always keep the interval with the earlier end time. Leaves maximum room for future intervals.
  • Custom sort: intervals.sort(key=lambda x: (x[0], x[1])) or functools.cmp_to_key for complex comparisons
  • Largest Number (#179): sort by comparing b+a vs a+b as strings — non-obvious but elegant
