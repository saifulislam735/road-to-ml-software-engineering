Database Fundamentals

🔴 CRITICAL — Foundation of everything. Learn this before any SQL.

Before touching any SQL, you need to understand what a database actually is and the rules that govern how it protects your data. These concepts explain why PostgreSQL works the way it does — and why you should care.

What is a Database? (For Complete Beginners)

A database is an organized, persistent store of structured data managed by software (a DBMS — Database Management System). Think of it as a super-powered spreadsheet that can:

🔒
Store safely
Data survives crashes, power failures, and restarts. Unlike a variable in your code.
⚡
Query fast
Find 1 row out of 100 million in milliseconds using indexes.
👥
Serve many users
100 users reading/writing simultaneously without corrupting each other's data.
🔗
Relate data
A customer links to their orders, which link to products — all connected.
📌 Real-World Analogy

Imagine a bank. Your account balance isn't stored in a text file someone opens. It lives in a database that: locks your row when you're transferring money so no one else changes it mid-transfer, rolls back if the transfer fails halfway, and logs every change permanently. That's what a database gives you that a plain file cannot.

ACID Properties — The 4 Guarantees

ACID is the set of promises a database makes about every transaction. Without ACID, your data can become corrupted in ways that are nearly impossible to detect or fix. Every serious database — including PostgreSQL — upholds all four.

A
Atomicity — "All or Nothing"

Every operation in a transaction either all succeed together or all fail together. There is no partial success. Think of it as: a transaction is an atom — it cannot be split.

Real analogy: You're transferring $500 from Account A to Account B. There are two steps: deduct from A, add to B. Atomicity guarantees: if step 2 crashes after step 1, the $500 is returned to A. You never lose money to a void.

Atomicity in action
sql
BEGIN;  -- Start transaction

  UPDATE accounts SET balance = balance - 500 WHERE id = 'account_A';
  UPDATE accounts SET balance = balance + 500 WHERE id = 'account_B';
  -- If anything crashes here, BOTH updates are undone automatically

COMMIT;  -- Only now are changes permanent
-- If an error occurs instead → ROLLBACK happens automatically
C
Consistency — "Rules Always Enforced"

The database moves from one valid state to another valid state. It will never allow a transaction that breaks your defined rules (constraints, foreign keys, checks).

Real analogy: You define a rule: "account balance can never be negative." Even if a bug in your code tries to make it negative, the database refuses the operation and returns an error. The rule is enforced at the DB level — not just in your application.

Consistency via constraints
sql
CREATE TABLE accounts (
  id      UUID PRIMARY KEY,
  balance NUMERIC(12,2) CHECK (balance >= 0)  -- Rule: never negative
);

-- Try to violate the rule:
UPDATE accounts SET balance = -100 WHERE id = 'A';
-- ERROR: new row violates check constraint "accounts_balance_check"
-- Database REFUSES the update — consistency maintained!
I
Isolation — "Concurrent Users Don't Interfere"

When 100 users are reading/writing the database at the same time, each transaction behaves as if it's the only one running. Intermediate states are invisible to others.

Real analogy: Two people book the last concert ticket simultaneously. Isolation ensures only ONE gets it — the other sees "sold out." Neither sees the ticket as "being booked" — they only see final states.

Isolation — booking the last seat
sql
-- User A and User B both try to book ticket #42 simultaneously

-- Transaction A:
BEGIN;
SELECT * FROM tickets WHERE id = 42 FOR UPDATE; -- LOCKS the row
UPDATE tickets SET booked_by = 'userA', status = 'booked' WHERE id = 42;
COMMIT;

-- Transaction B (arrives at same time):
-- It WAITS for A's lock to release
-- When A commits, B sees status='booked' → cannot double-book
-- PostgreSQL's MVCC handles this automatically
How PostgreSQL Does This
PostgreSQL uses MVCC (Multi-Version Concurrency Control): instead of locking rows for reads, it shows each transaction a snapshot of the data from when the transaction started. This means readers never block writers and writers never block readers — only writer vs writer conflicts create locks.
D
Durability — "Committed = Permanent"

Once a transaction is committed, that data is permanently saved — even if the server crashes, the power goes out, or the disk is ejected a millisecond later. The data will be there when the server restarts.

Real analogy: When your bank app shows "Transfer Successful" — that's a commit. Even if the bank's servers all crash 1 second later, your money is still transferred. It's written to disk via the WAL (Write-Ahead Log) before the confirmation is sent.

How WAL ensures durability
sql
-- Under the hood when you COMMIT:
-- 1. PostgreSQL writes the change to WAL (Write-Ahead Log) on disk
-- 2. Only THEN returns "success" to your application
-- 3. Data is GUARANTEED durable even if server dies after step 2

-- You can see WAL in action:
SELECT pg_current_wal_lsn();   -- current WAL position
SELECT pg_walfile_name(pg_current_wal_lsn());  -- current WAL file

-- WAL files live here (do NOT delete manually!):
-- /var/lib/postgresql/16/main/pg_wal/
CAP Theorem — The Distributed Systems Trade-off

When your database runs across multiple servers (distributed system), you can only guarantee 2 out of these 3 properties at the same time. This is a mathematical theorem — not a limitation that better software can solve.

PropertyWhat It Means (Plain English)Example
ConsistencyEvery read gets the most recent write. All nodes see the same data at the same time.You deposit money → everyone checking your balance immediately sees the new amount
AvailabilityEvery request gets a response (not necessarily the latest data). System never refuses a request.Even if one server is down, others keep responding — maybe with slightly old data
Partition ToleranceSystem keeps working even if network communication between servers breaks.Server A and Server B can't talk to each other, but both keep serving requests
📌 Where PostgreSQL Sits

PostgreSQL is a CP system (Consistency + Partition Tolerance). It prioritizes correctness over availability. If a network split happens, PostgreSQL will pause rather than serve potentially incorrect data. For most business applications, this is exactly what you want — wrong data is worse than a brief outage.

Many NoSQL databases (MongoDB, Cassandra, DynamoDB) sacrifice ACID for scale. They follow BASE instead:

How Data Flows in a PostgreSQL Query

Here's exactly what happens, step by step, when your app sends a query to PostgreSQL:

1
App sends SQL

Your Node.js/Python/Go app sends SELECT * FROM users WHERE email = $1 over a TCP connection (or Unix socket).

2
Parser

PostgreSQL parses the SQL text into a parse tree — checks syntax. Fails here if you have a typo like SELEKT.

3
Analyzer / Rewriter

Resolves table and column names. Checks permissions. Applies view rewriting if needed.

4
Query Planner / Optimizer

Generates multiple execution plans. Picks the cheapest one using table statistics. This is where index usage is decided.

5
Executor

Runs the chosen plan. Reads data from shared_buffers (RAM cache) or disk. Applies filters, joins, sorts.

6
Returns results

Rows are sent back to your app. For writes, WAL is written first to guarantee durability before confirming.

Practice — Understand Before You Code
Write on paper: describe ACID to someone who has never coded. Use a bank transfer as your example.
In psql: run BEGIN; UPDATE accounts SET balance = -1 WHERE ...; ROLLBACK; — observe that the change is undone.
Create a table with a CHECK constraint. Try to INSERT a row that violates it. Read the error message.
Run SELECT pg_current_wal_lsn(); before and after an INSERT — notice the LSN advances (WAL was written).

Local PostgreSQL Setup

🔴 CRITICAL — You need a running database before writing a single query

Setting up PostgreSQL locally means installing it on your own machine. Every command is explained so you know exactly what it does — not just how to copy-paste it.

Ubuntu / Debian — Complete Step-by-Step
1
Update your package list

This fetches the latest list of available software from the internet. Always run before installing anything so you get the newest version.

bash
sudo apt update
# sudo = run as administrator
# apt = package manager (Advanced Package Tool)
# update = refresh the list of available packages (does NOT install anything yet)
2
Install PostgreSQL + contrib extensions

postgresql = the core database engine. postgresql-contrib = bonus extensions: uuid generation, password hashing (pgcrypto), performance stats (pg_stat_statements). You will need these later.

bash
sudo apt install -y postgresql postgresql-contrib
# -y = answer "yes" to all install prompts automatically
# This installs PostgreSQL 14/15/16 depending on your Ubuntu version
# Data directory created at: /var/lib/postgresql/VERSION/main/
3
Start and enable the service

PostgreSQL runs as a background service. You must start it now AND enable it so it auto-starts after every reboot.

bash
sudo systemctl start postgresql     # start right now
sudo systemctl enable postgresql    # auto-start on every reboot
sudo systemctl status postgresql    # check it is running
# You should see: Active: active (running) - shown in GREEN
# If you see "failed": run  sudo journalctl -u postgresql -n 30  to see errors
4
Connect as the postgres superuser

PostgreSQL creates a Linux system user called postgres during install. This user maps to the database superuser. We temporarily become that user to do initial setup.

bash
sudo -u postgres psql
# sudo -u postgres = switch to the postgres Linux user temporarily
# psql = open the PostgreSQL interactive terminal
# Prompt changes to:  postgres=#
# The # means you are a superuser inside PostgreSQL
5
Set a password for the postgres superuser

By default, the postgres user uses "peer authentication" (no password needed from the same machine). Set a password so GUI tools and remote connections work.

sql
-- Run this INSIDE the psql shell (note the semicolon!)
ALTER USER postgres PASSWORD 'YourStrongPassword123!';
-- Expected output: ALTER ROLE
-- Now quit psql:
\q
6
Create your app database and user

Important principle: never use the postgres superuser in your app. Create a dedicated database and a limited user who can only access that database. This limits damage if credentials are ever exposed.

sql
-- Back in psql as postgres superuser:
sudo -u postgres psql

-- 1. Create the database
CREATE DATABASE myapp_db;

-- 2. Create a user (role) for your app
CREATE USER myapp_user WITH PASSWORD 'AppPassword456!';

-- 3. Give the user full access to the database
GRANT ALL PRIVILEGES ON DATABASE myapp_db TO myapp_user;

-- 4. Connect to the database and grant schema access
\c myapp_db
GRANT ALL ON SCHEMA public TO myapp_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT ALL ON TABLES TO myapp_user;
7
Connect as your app user and verify
bash
psql -U myapp_user -d myapp_db -h localhost
# -U myapp_user  = use this database username
# -d myapp_db    = connect to this database
# -h localhost   = connect via TCP (triggers password auth)
# Enter your password when prompted
# Success: you should see  myapp_db=>  (not # because not superuser)

-- Verify inside psql:
SELECT current_user;        -- should show: myapp_user
SELECT current_database();  -- should show: myapp_db
\conninfo                   -- shows full connection details
Connection string for your app
postgresql://myapp_user:AppPassword456!@localhost:5432/myapp_db
Store this in a .env file as DATABASE_URL — never hardcode it in source code.

Docker PostgreSQL Setup

🟠 HIGH — Best way to run Postgres in development teams

Docker lets you run PostgreSQL in an isolated container — no installation needed on the host. The exact same container runs on your laptop, your teammate's Mac, and your CI/CD pipeline. No more "works on my machine" problems.

How Docker Works (Quick Mental Model)
📦
Image
A read-only template. Like a recipe. postgres:16 is the official image from Docker Hub.
🏃
Container
A running instance of an image. Like a house built from a blueprint. You can have many containers from one image.
💾
Volume
Persistent storage outside the container. When container stops/deletes, volume data survives.
🖥️
Port Mapping
-p 5432:5432 maps host port to container port. Your app connects to localhost:5432.
Option A: Quick Single Container

Use this for fast experiments. One command, database is running in seconds.

1
Run a PostgreSQL container
bash
bash
docker run -d \
  --name my-postgres \
  -e POSTGRES_USER=admin \
  -e POSTGRES_PASSWORD=secret123 \
  -e POSTGRES_DB=myapp \
  -p 5432:5432 \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16
# -d = run in background (detached)
# --name = give the container a name you can reference
# -e = set environment variables (configuration)
# -p 5432:5432 = map host port 5432 to container port 5432
# -v pgdata:/var/... = named volume so data persists when container stops
# postgres:16 = official PostgreSQL 16 image from Docker Hub
2
Verify it is running
bash
docker ps                      # should show my-postgres in the list
docker logs my-postgres        # should end with: "database system is ready to accept connections"
3
Connect with psql
bash
# Connect FROM INSIDE the container (no psql needed on host):
docker exec -it my-postgres psql -U admin -d myapp

# Connect from your HOST machine (if psql is installed):
psql -U admin -d myapp -h localhost -p 5432
4
Stop, start, and remove
bash
docker stop my-postgres        # stop (data preserved in volume)
docker start my-postgres       # start again (data still there)
docker rm my-postgres          # delete container (data still in volume!)
docker volume rm pgdata        # delete volume AND all data (DANGER)
Option B: Docker Compose (Recommended for Projects)

For real projects, use Docker Compose. It defines your entire stack in one file so anyone on your team can run docker compose up and have an identical environment.

1
Create a .env file for secrets

Never hardcode passwords in docker-compose.yml — it gets committed to git. Store secrets in .env and add .env to .gitignore.

.env
DB_USER=admin
DB_PASSWORD=secret123
DB_NAME=myapp
2
Create docker-compose.yml
docker-compose.yml
yaml
version: '3.9'

services:
  postgres:
    image: postgres:16                        # use official image
    container_name: myapp_postgres
    restart: unless-stopped                   # auto-restart if crash
    environment:
      POSTGRES_USER: ${DB_USER}              # reads from .env file
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: ${DB_NAME}
    ports:
      - "5432:5432"                           # host:container
    volumes:
      - pgdata:/var/lib/postgresql/data       # named volume for persistence
      - ./init:/docker-entrypoint-initdb.d    # .sql files run on first start
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
      interval: 10s
      timeout: 5s
      retries: 5

  pgadmin:                                    # optional: web GUI for the DB
    image: dpage/pgadmin4
    container_name: myapp_pgadmin
    environment:
      PGADMIN_DEFAULT_EMAIL: admin@example.com
      PGADMIN_DEFAULT_PASSWORD: pgadmin
    ports:
      - "8080:80"                             # open browser: localhost:8080
    depends_on:
      postgres:
        condition: service_healthy            # wait until postgres is ready

volumes:
  pgdata:                                     # Docker manages this volume
3
Start the stack
bash
docker compose up -d
# NOTE: The 'version:' field is optional in Docker Compose v2+ (current default).
# It still works fine with v1 compatibility. You can safely remove it.
# -d = run in background
# First run: downloads postgres:16 image (~100MB), takes ~30 seconds
# Subsequent runs: starts in ~2 seconds

# Watch logs to confirm ready:
docker compose logs -f postgres
# Look for: "database system is ready to accept connections"
# Press Ctrl+C to stop watching logs (container keeps running)
4
Connect and use
bash
# Connect via psql inside the container:
docker compose exec postgres psql -U admin -d myapp

# Run a SQL file against the database:
docker compose exec -T postgres psql -U admin -d myapp < schema.sql

# Backup the database:
docker compose exec postgres pg_dump -U admin myapp > backup_$(date +%Y%m%d).sql

# Restore a backup:
cat backup.sql | docker compose exec -T postgres psql -U admin -d myapp

# Open pgAdmin GUI:
# Browser: localhost:8080 → login → Add Server: host=postgres, port=5432
5
Stop safely (data preserved)
bash
docker compose down              # stop and remove containers (data preserved in volume)
docker compose down -v          # DANGER: also deletes volumes (all data gone!)
docker compose restart postgres # restart just the database service
🚨 Never use -v in production
docker compose down -v deletes ALL named volumes including your database data. Use plain docker compose down to stop safely.

✅ Pros of Docker

  • Identical environment for entire team
  • Easy to test different PostgreSQL versions
  • One command to start, one to stop
  • Named volumes persist data across restarts
  • Matches CI/CD environment exactly
  • Easy to reset to clean state (recreate container)

❌ Cons of Docker

  • Requires Docker Desktop (Windows/Mac) — uses RAM
  • Slight I/O overhead on Windows/Mac (negligible on Linux)
  • docker compose down -v destroys all data
  • Extra layer to debug if something goes wrong
  • Not production-ready without additional HA setup
Practice
Run the single-container command. Verify with docker ps and docker logs. Connect and run SELECT version();
Create the docker-compose.yml. Run docker compose up -d. Access pgAdmin at localhost:8080 and add the server.
Create a table, insert 5 rows. Run docker compose down then docker compose up -d. Verify data persists.
Create an init/ folder with a 01_schema.sql file containing a CREATE TABLE. Destroy and recreate the stack — watch the init script run automatically.

PostgreSQL Data Types

🔴 CRITICAL — Every column needs a type. Wrong type = bugs, wasted space, slow queries

Every column in PostgreSQL must have a data type. The type determines: what values are valid, how much storage is used, what operations you can perform, and how fast queries run. Choosing wrong (e.g. using TEXT for money, or VARCHAR where TEXT works) causes real problems in production.

Numeric Types — Which to Choose and Why

PostgreSQL has multiple numeric types. The key decision: do you need exact numbers or approximate numbers?

TypeSizeRangeUse When
smallint2 bytes-32,768 to 32,767Small counters: age, rating (1-5), small codes
integer / int4 bytes-2.1 billion to 2.1BDefault for whole numbers. Row counts, quantities, scores
bigint8 bytes-9.2 quintillion to 9.2QIDs in high-traffic apps, file sizes, epoch timestamps in ms
numeric(p,s)VariableExact decimal, p=digits, s=after decimalMoney, financial calculations. Never loses precision
real4 bytes6 decimal digit precisionScientific data where approx is OK (GPS, sensors)
double precision8 bytes15 decimal digit precisionCalculations needing more precision than real
💰 Never use FLOAT or REAL for money
Floating point cannot represent most decimal values exactly. 0.1 + 0.2 in float = 0.30000000000000004. Use NUMERIC(10,2) for any monetary value. This is a real bug that has caused real financial losses.
Syntax
sql
-- SYNTAX: column_name  data_type  [constraints]
age          SMALLINT
user_count   INTEGER
file_size    BIGINT
price        NUMERIC(10, 2)   -- up to 99999999.99
salary       NUMERIC(12, 2)   -- up to 9999999999.99
temperature  DOUBLE PRECISION
Real example
sql
-- Demonstrating why NUMERIC matters for money:
SELECT 0.1::FLOAT + 0.2::FLOAT;       -- 0.30000000000000004 (WRONG!)
SELECT 0.1::NUMERIC + 0.2::NUMERIC;   -- 0.3 (CORRECT!)

-- Real column example:
CREATE TABLE products (
  quantity  INTEGER        NOT NULL DEFAULT 0,     -- whole number
  price     NUMERIC(10,2)  NOT NULL,               -- exact: 99999999.99 max
  rating    SMALLINT       CHECK (rating BETWEEN 1 AND 5),
  lat       DOUBLE PRECISION,                       -- GPS coordinate
  lon       DOUBLE PRECISION
);
Text Types — The Simple Rule

PostgreSQL has three text types but in practice you use mostly just one.

TypeLimitUsePerformance
textUnlimitedDefault choice for everythingSame as varchar in PostgreSQL
varchar(n)n characters maxWhen you want DB to enforce max lengthSame as text (no speed difference)
char(n)Exactly n charactersFixed-width codes (country code, ISO codes)Pads with spaces — rarely useful
The Rule in PostgreSQL
Use TEXT for everything unless you genuinely need the database to enforce a maximum length constraint (e.g. usernames max 30 chars). There is zero performance difference between TEXT and VARCHAR in PostgreSQL — they are stored identically.
Syntax
sql
name        TEXT           NOT NULL         -- unlimited, use for most text
bio         TEXT                            -- can be NULL (no NOT NULL)
username    VARCHAR(30)    NOT NULL         -- enforces max 30 chars
country     CHAR(2)                          -- exactly 2 chars: "BD", "US"
Real example
sql
CREATE TABLE users (
  username    TEXT        NOT NULL UNIQUE,        -- TEXT is fine
  email       TEXT        NOT NULL UNIQUE,
  bio         TEXT,                               -- nullable, no limit
  country_code CHAR(2)                             -- exactly "BD", "US" etc
);
Date & Time Types — Always Use timestamptz

Timezone handling is one of the most common sources of bugs in applications. PostgreSQL's timestamptz type stores everything as UTC and converts automatically.

TypeStoresUse When
dateYear, month, day onlyBirthdays, calendar dates, no time needed
timeHour, minute, second onlyStore a time of day without a date
timestampDate + time, NO timezoneOnly if you are certain timezone is irrelevant
timestamptzDate + time WITH timezone (stored as UTC)Use this for 99% of timestamps. Prevents timezone bugs
intervalA duration: "3 days", "2 hours 30 min"Duration fields, scheduling offsets
Syntax
sql
birthday     DATE
opens_at     TIME
created_at   TIMESTAMPTZ   NOT NULL DEFAULT NOW()
expires_at   TIMESTAMPTZ
duration     INTERVAL
Real example — timezone in action
sql
-- timestamptz stores as UTC, shows in your session timezone
SET timezone = 'Asia/Dhaka';
SELECT NOW();              -- shows in Dhaka time (UTC+6)

SET timezone = 'UTC';
SELECT NOW();              -- same moment, shown as UTC

-- Interval arithmetic examples:
SELECT NOW() + INTERVAL '7 days';           -- 7 days from now
SELECT NOW() - INTERVAL '1 month';          -- 1 month ago
SELECT '2024-12-31'::date - '2024-01-01'::date; -- 365 (days between)

-- Real use: find accounts created in the last 30 days
SELECT * FROM users
WHERE created_at > NOW() - INTERVAL '30 days';

sql

  balance      NUMERIC(12,2) NOT NULL DEFAULT 0.00,

JSONB — Flexible Data Inside PostgreSQL

JSONB lets you store and query schemaless data inside a PostgreSQL column. It's stored in binary format, fully indexable, and supports rich querying operators.

JSONB operators and queries
sql
-- Insert JSONB data
INSERT INTO users (username, email, metadata)
VALUES ('alice', 'alice@mail.com', '{"plan": "pro", "theme": "dark", "notifications": true}');

-- Query JSONB fields:
-- -> returns JSON value (preserves type)
-- ->> returns TEXT value (useful for comparison)
SELECT metadata->'plan'      FROM users;    -- returns: "pro" (JSON string)
SELECT metadata->>'plan'     FROM users;    -- returns:  pro  (plain text)
SELECT metadata->>'theme'    FROM users WHERE username = 'alice';  -- dark

-- Filter by JSONB field:
SELECT * FROM users WHERE metadata->>'plan' = 'pro';

-- Contains operator @>  (does left contain right?)
SELECT * FROM users WHERE metadata @> '{"plan": "pro"}'::jsonb;

-- Update a JSONB field
UPDATE users
SET metadata = metadata || '{"plan": "enterprise"}'::jsonb
WHERE username = 'alice';

-- Index JSONB for fast queries (GIN index)
CREATE INDEX idx_users_metadata ON users USING gin(metadata);

DDL — Tables, Schemas & Databases

🔴 CRITICAL — DDL is how you define and change your database structure

DDL (Data Definition Language) is the group of SQL commands that create, modify, and delete database structure (not data). Think of DDL as the architecture work — you design the building before putting things in it.

📌 DDL vs DML — Know the Difference

DDL = changes structure: CREATE, ALTER, DROP, TRUNCATE
DML = changes data: INSERT, UPDATE, DELETE, SELECT
DDL auto-commits (no rollback possible in most cases). Always test DDL in dev before production.

Schemas — Organising Your Database into Namespaces

A schema is like a folder inside a database. One database can have many schemas. Each schema contains its own tables, views, functions, and types. This lets you logically separate different parts of your application.

Syntax — CREATE SCHEMA
sql
-- SYNTAX
CREATE SCHEMA schema_name;
CREATE SCHEMA IF NOT EXISTS schema_name;   -- safe: no error if exists
DROP SCHEMA schema_name CASCADE;          -- CASCADE drops everything inside

-- Refer to a table inside a schema:
schema_name.table_name
Real example — organising a SaaS app
sql
-- Create schemas for different concerns
CREATE SCHEMA IF NOT EXISTS app;         -- main application tables
CREATE SCHEMA IF NOT EXISTS auth;        -- authentication tables
CREATE SCHEMA IF NOT EXISTS analytics;   -- reporting / analytics tables

-- Create tables inside schemas
CREATE TABLE app.users ( id UUID PRIMARY KEY, name TEXT );
CREATE TABLE auth.sessions ( token TEXT PRIMARY KEY, user_id UUID );
CREATE TABLE analytics.page_views ( url TEXT, viewed_at TIMESTAMPTZ );

-- Set search path so you don't type the schema every time
SET search_path TO app, public;
SELECT * FROM users;         -- finds app.users automatically

-- List all schemas
SELECT schema_name FROM information_schema.schemata;
\dn                             -- in psql
CREATE TABLE — Full Syntax Explained

Every part of a CREATE TABLE statement has a purpose. Let's break it down piece by piece:

Syntax — annotated CREATE TABLE
sql
CREATE TABLE [IF NOT EXISTS] table_name (
  column_name  data_type  [column_constraints],
  ...
  [table_constraints]
);

-- Column constraints (apply to one column):
--   PRIMARY KEY        = unique + not null, identifies each row
--   NOT NULL           = column must always have a value
--   UNIQUE             = no two rows can have the same value
--   DEFAULT value      = value used if not provided on insert
--   CHECK (condition)  = value must satisfy the condition
--   REFERENCES table   = foreign key (links to another table)

-- Table constraints (apply to multiple columns):
--   PRIMARY KEY (col1, col2)  = composite primary key
--   UNIQUE (col1, col2)       = combination must be unique
--   CHECK (condition)         = condition across columns
--   FOREIGN KEY (col) REFERENCES table(col)
Real example — complete products table
sql
-- Step 1: Create the enum type (must exist before the table)
CREATE TYPE product_status AS ENUM ('active', 'inactive', 'archived');

-- Step 2: Create the categories table first (products will reference it)
CREATE TABLE categories (
  id   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL UNIQUE,
  slug TEXT NOT NULL UNIQUE
);

-- Step 3: Create products table that references categories
CREATE TABLE IF NOT EXISTS products (
  -- Primary key: UUID generated automatically
  id            UUID             PRIMARY KEY DEFAULT gen_random_uuid(),

  -- Foreign key: must reference an existing category
  category_id   UUID             REFERENCES categories(id) ON DELETE SET NULL,

  -- Text columns
  name          TEXT             NOT NULL,
  slug          TEXT             NOT NULL UNIQUE,
  description   TEXT,

  -- Price must be >= 0 (CHECK constraint)
  price         NUMERIC(10,2)   NOT NULL CHECK (price >= 0),
  stock         INTEGER         NOT NULL DEFAULT 0 CHECK (stock >= 0),

  -- Enum: only allows defined values
  status        product_status  NOT NULL DEFAULT 'active',

  -- Flexible fields
  attributes    JSONB           NOT NULL DEFAULT '{}',
  images        TEXT[]          NOT NULL DEFAULT '{}',

  -- Audit trail (always include)
  created_at    TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ     NOT NULL DEFAULT NOW(),

  -- Table-level constraint: named for better error messages
  CONSTRAINT uq_product_slug UNIQUE (slug)
);

-- Verify the table structure
\d products
ALTER TABLE — Modifying Existing Structure

After a table is created, you will often need to change it as requirements evolve. ALTER TABLE is how you do this without dropping and recreating the table.

Syntax — all ALTER TABLE operations
sql
-- Add a column
ALTER TABLE table_name ADD COLUMN column_name data_type [constraints];

-- Drop a column (and all data in it!)
ALTER TABLE table_name DROP COLUMN column_name;

-- Rename a column
ALTER TABLE table_name RENAME COLUMN old_name TO new_name;

-- Change a column's data type
ALTER TABLE table_name ALTER COLUMN column_name TYPE new_type;

-- Set or remove a default value
ALTER TABLE table_name ALTER COLUMN column_name SET DEFAULT value;
ALTER TABLE table_name ALTER COLUMN column_name DROP DEFAULT;

-- Add / remove NOT NULL
ALTER TABLE table_name ALTER COLUMN column_name SET NOT NULL;
ALTER TABLE table_name ALTER COLUMN column_name DROP NOT NULL;

-- Add a constraint
ALTER TABLE table_name ADD CONSTRAINT name CHECK (condition);

-- Drop a constraint
ALTER TABLE table_name DROP CONSTRAINT constraint_name;

-- Rename the whole table
ALTER TABLE old_name RENAME TO new_name;
Real example — evolving a table over time
sql
-- Week 1: Create initial table
CREATE TABLE users (
  id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email    TEXT NOT NULL UNIQUE,
  name     TEXT
);

-- Week 2: Add phone number (nullable = existing rows get NULL)
ALTER TABLE users ADD COLUMN phone TEXT;

-- Week 3: Add created_at with default (existing rows get NOW())
ALTER TABLE users ADD COLUMN created_at TIMESTAMPTZ DEFAULT NOW();

-- Week 4: Rename confusing column
ALTER TABLE users RENAME COLUMN name TO full_name;

-- Week 5: Phone should be required now
-- First fill in existing NULLs, then add constraint
UPDATE users SET phone = 'unknown' WHERE phone IS NULL;
ALTER TABLE users ALTER COLUMN phone SET NOT NULL;

-- Week 6: Add a check constraint
ALTER TABLE users
  ADD CONSTRAINT chk_email_format CHECK (email LIKE '%@%');
Generated Columns — Computed Values Stored in DB
Syntax & example
sql
-- SYNTAX: column_name type GENERATED ALWAYS AS (expression) STORED
-- The column value is automatically computed and stored whenever a row changes
-- You cannot INSERT or UPDATE into a generated column

CREATE TABLE order_items (
  id         UUID           PRIMARY KEY DEFAULT gen_random_uuid(),
  quantity   INTEGER        NOT NULL,
  unit_price NUMERIC(10,2) NOT NULL,
  discount   NUMERIC(10,2) NOT NULL DEFAULT 0,

  -- Automatically calculated: quantity * price - discount
  subtotal   NUMERIC(10,2) GENERATED ALWAYS AS
             (quantity * unit_price - discount) STORED
);

-- Insert without specifying subtotal:
INSERT INTO order_items (quantity, unit_price, discount)
VALUES (3, 25.00, 5.00);

-- subtotal is automatically 3 * 25.00 - 5.00 = 70.00
SELECT quantity, unit_price, discount, subtotal FROM order_items;
-- Returns: 3 | 25.00 | 5.00 | 70.00
DROP — Removing Database Objects
Syntax & example
sql
-- DROP TABLE: delete table + all its data permanently
DROP TABLE products;                     -- fails if other tables reference it
DROP TABLE IF EXISTS products;           -- no error if table doesn't exist
DROP TABLE products CASCADE;            -- also drops FK references to this table

-- TRUNCATE: delete ALL rows but keep the table structure
TRUNCATE TABLE products;                -- faster than DELETE FROM products
TRUNCATE TABLE products RESTART IDENTITY CASCADE; -- also resets sequences

-- DROP TYPE: remove a custom type
DROP TYPE IF EXISTS product_status;

-- DROP SCHEMA: remove schema and everything inside
DROP SCHEMA IF EXISTS analytics CASCADE;
🚨 DROP is immediate and irreversible
Unlike application code, you cannot undo a DROP in PostgreSQL (unless you have a transaction open or a backup). Always double-check in production. Wrap in a transaction: BEGIN; DROP TABLE ...; -- verify; COMMIT;

DML — CRUD Operations

🔴 CRITICAL — CRUD is the backbone of every database-backed application

DML (Data Manipulation Language) is the group of SQL commands that work with data (not structure). CRUD stands for the four fundamental operations: Create (INSERT), Read (SELECT), Update (UPDATE), Delete (DELETE). Every feature in every app uses these.

INSERT — Creating New Records
1
Basic INSERT — one row
Syntax
sql
INSERT INTO table_name (column1, column2, ...)
VALUES (value1, value2, ...);
Example
sql
INSERT INTO users (username, email, age)
VALUES ('alice', 'alice@example.com', 28);
-- Columns not listed get their DEFAULT value
-- id gets gen_random_uuid(), created_at gets NOW()
2
Multi-row INSERT — insert many rows at once (much faster than separate INSERTs)
Syntax
sql
INSERT INTO table_name (col1, col2)
VALUES
  (val1a, val2a),
  (val1b, val2b),
  (val1c, val2c);
Example
sql
INSERT INTO products (name, price, stock)
VALUES
  ('Laptop',  999.99, 50),
  ('Mouse',   29.99, 200),
  ('Keyboard', 79.99, 150);
-- Inserts 3 rows in one round-trip to the DB (faster than 3 separate INSERTs)
3
INSERT RETURNING — get back the inserted row immediately

Instead of inserting then immediately SELECTing to get the generated ID, RETURNING does it in one step. This is a PostgreSQL superpower.

Syntax
sql
INSERT INTO table_name (col1, col2)
VALUES (val1, val2)
RETURNING *;               -- return all columns
RETURNING id, created_at;  -- or specific columns
Example
sql
INSERT INTO users (username, email)
VALUES ('bob', 'bob@example.com')
RETURNING id, username, created_at;
-- Returns: {id: "a3f2...", username: "bob", created_at: "2024-01-15 10:30:00+00"}
-- Use this in Node.js: const { rows } = await pool.query(...); const newUser = rows[0];
4
UPSERT — Insert or Update on Conflict

UPSERT handles the very common case: "insert this row, but if a row with this unique key already exists, update it instead." Without UPSERT you'd need two queries; with it, one query handles both cases atomically.

Syntax
sql
INSERT INTO table_name (col1, col2)
VALUES (val1, val2)
ON CONFLICT (unique_column)
DO UPDATE SET
  col2 = EXCLUDED.col2;   -- EXCLUDED refers to the row that failed to insert
-- OR:
ON CONFLICT DO NOTHING;    -- silently skip duplicates
Example — sync user from OAuth
sql
-- User logs in with Google: create if new, update if existing
INSERT INTO users (email, username, avatar_url)
VALUES ('carol@gmail.com', 'carol', 'https://google.com/photo.jpg')
ON CONFLICT (email)
DO UPDATE SET
  avatar_url = EXCLUDED.avatar_url,   -- update photo if changed
  updated_at = NOW()
RETURNING id, username;               -- always get back the user ID

-- Silently skip if email already exists (import scenario)
INSERT INTO users (email, username)
VALUES ('dave@example.com', 'dave')
ON CONFLICT (email) DO NOTHING;

Soft DELETE pattern — preferred in production

Instead of permanently deleting rows (which can't be undone), set a deleted_at timestamp. The row still exists in the database for audit/recovery, but is filtered from all normal queries.

Example
sql

UPDATE users
SET deleted_at = NOW()
WHERE id = 'user-uuid';

SELECT * FROM users WHERE deleted_at IS NULL;

-- Restore a soft-deleted user
UPDATE users
SET deleted_at = NULL
WHERE id = 'user-uuid';

Window Functions

🟠 HIGH — Advanced — used in analytics & reporting

Window functions perform calculations across a set of rows related to the current row, without collapsing them into groups. They're one of PostgreSQL's most powerful features for analytics.

Syntax & Core Functions
Window function syntax
sql
-- General syntax:
-- function_name() OVER (PARTITION BY col ORDER BY col ROWS/RANGE frame)

-- ROW_NUMBER: rank within each partition
SELECT
  username,
  department,
  salary,
  ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rank_in_dept
FROM employees;

-- RANK vs DENSE_RANK (ties)
SELECT
  username, salary,
  RANK()       OVER (ORDER BY salary DESC) AS rank,        -- 1,2,2,4
  DENSE_RANK() OVER (ORDER BY salary DESC) AS dense_rank  -- 1,2,2,3
FROM employees;

-- LAG / LEAD: access previous/next row values
SELECT
  month,
  revenue,
  LAG(revenue, 1) OVER (ORDER BY month) AS prev_month_revenue,
  revenue - LAG(revenue, 1) OVER (ORDER BY month) AS growth
FROM monthly_revenue;

-- Running total (cumulative sum)
SELECT
  created_at::DATE AS date,
  COUNT(*) AS daily_signups,
  SUM(COUNT(*)) OVER (ORDER BY created_at::DATE) AS cumulative_users
FROM users
GROUP BY created_at::DATE;

-- Moving average (7-day)
SELECT
  date,
  revenue,
  AVG(revenue) OVER (
    ORDER BY date
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ) AS moving_avg_7d
FROM daily_revenue;

-- NTILE: split into N buckets (e.g. quartiles)
SELECT
  username, total_spent,
  NTILE(4) OVER (ORDER BY total_spent) AS quartile
FROM user_stats;

-- FIRST_VALUE / LAST_VALUE
SELECT
  department, username, salary,
  FIRST_VALUE(salary) OVER (
    PARTITION BY department ORDER BY salary DESC
  ) AS top_salary_in_dept
FROM employees;

CTEs & Subqueries

🟠 HIGH — Important for complex query logic
Common Table Expressions (CTEs)
CTE syntax and examples
sql
-- Basic CTE (WITH clause)
WITH active_users AS (
  SELECT id, username, email
  FROM users
  WHERE is_active = TRUE AND deleted_at IS NULL
)
SELECT u.username, COUNT(o.id) AS order_count
FROM active_users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.username;

-- Multiple CTEs chained
WITH
  monthly_orders AS (
    SELECT
      DATE_TRUNC('month', created_at) AS month,
      SUM(total) AS revenue
    FROM orders
    WHERE status = 'delivered'
    GROUP BY 1
  ),
  with_growth AS (
    SELECT
      month, revenue,
      LAG(revenue) OVER (ORDER BY month) AS prev_revenue
    FROM monthly_orders
  )
SELECT
  month,
  revenue,
  ROUND((revenue - prev_revenue) / prev_revenue * 100, 2) AS growth_pct
FROM with_growth;

-- Recursive CTE: traverse a hierarchy (org chart, category tree)
WITH RECURSIVE category_tree AS (
  -- Base case: top-level categories
  SELECT id, name, parent_id, 0 AS depth, name::text AS path
  FROM categories
  WHERE parent_id IS NULL

  UNION ALL

  -- Recursive case: children
  SELECT c.id, c.name, c.parent_id,
         ct.depth + 1,
         ct.path || ' > ' || c.name
  FROM categories c
  JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT path, depth FROM category_tree ORDER BY path;
Subqueries
Subquery patterns
sql
-- Scalar subquery (returns single value)
SELECT username,
  (SELECT COUNT(*) FROM orders WHERE user_id = u.id) AS order_count
FROM users u;

-- EXISTS subquery (fast membership check)
SELECT * FROM users u
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.user_id = u.id AND o.total > 500
);

-- IN with subquery
SELECT * FROM products
WHERE category_id IN (
  SELECT id FROM categories WHERE name = 'Electronics'
);

-- Derived table (subquery in FROM)
SELECT dept, avg_salary
FROM (
  SELECT department AS dept, AVG(salary) AS avg_salary
  FROM employees
  GROUP BY department
) dept_stats
WHERE avg_salary > 60000;
📌 CTE vs Subquery

Use CTEs when: the same result is referenced multiple times, readability matters, or you need recursion. Use subqueries for simple one-time use. In PostgreSQL 12+, CTEs are inlined by default (same performance as subqueries). Use WITH ... AS MATERIALIZED to force materialization when needed.

  DO $$
  BEGIN
    IF EXISTS (SELECT 1 FROM accounts WHERE balance < 0) THEN
      RAISE EXCEPTION 'Insufficient funds';
    END IF;
  END
  $$;

COMMIT;  -- make permanent if all good
-- or ROLLBACK; to undo everything

-- SAVEPOINT: partial rollback
BEGIN;
  INSERT INTO orders (...) VALUES (...);
  SAVEPOINT after_order;

  INSERT INTO payments (...) VALUES (...);
  -- if this fails, we can rollback to savepoint only:
  ROLLBACK TO SAVEPOINT after_order;

COMMIT;

⚠️ Deadlocks
Deadlocks occur when two transactions each hold a lock the other needs. PostgreSQL detects and resolves them by killing one transaction. Prevent them by: always acquiring locks in the same order, keeping transactions short, using SELECT ... FOR UPDATE SKIP LOCKED for job queues.

Unlike regular views, materialized views store the result set physically. They're fast to query but need to be refreshed when data changes.

Index creation
sql
-- Basic B-tree index
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- Composite index (column order matters!)
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
-- ↑ Can be used for queries on (user_id) or (user_id, status)
--   but NOT for queries on (status) alone

-- Unique index
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- Partial index (index only a subset of rows)
CREATE INDEX idx_orders_pending ON orders(created_at)
  WHERE status = 'pending';
-- Much smaller and faster — only indexes pending orders

-- Expression / functional index
CREATE INDEX idx_users_email_lower ON users(LOWER(email));
-- Now this query uses the index:
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';

-- GIN index for JSONB
CREATE INDEX idx_users_metadata ON users USING gin(metadata);
-- Now JSONB queries like metadata @> '{"plan":"pro"}' use the index

-- GIN index for full-text search
CREATE INDEX idx_products_fts ON products
  USING gin(to_tsvector('english', name || ' ' || description));

-- BRIN for huge append-only tables
CREATE INDEX idx_logs_created_at ON event_logs USING brin(created_at);

-- Create index CONCURRENTLY (doesn't lock table — use in production!)
CREATE INDEX CONCURRENTLY idx_orders_status ON orders(status);

-- Drop index
DROP INDEX idx_orders_user_id;
DROP INDEX CONCURRENTLY idx_orders_user_id;  -- production-safe

-- Simple SQL function
CREATE OR REPLACE FUNCTION get_user_order_count(p_user_id UUID)
RETURNS INTEGER
LANGUAGE SQL STABLE
AS $$
  SELECT COUNT(*)::INTEGER
  FROM orders
  WHERE user_id = p_user_id;
$$;

-- PL/pgSQL function with logic
CREATE OR REPLACE FUNCTION transfer_funds(
  p_from_id  UUID,
  p_to_id    UUID,
  p_amount   NUMERIC
)
RETURNS BOOLEAN
LANGUAGE plpgsql
AS $$
DECLARE
  v_balance NUMERIC;
BEGIN
  -- Check balance
  SELECT balance INTO v_balance
  FROM accounts WHERE id = p_from_id FOR UPDATE;

  IF v_balance < p_amount THEN
    RAISE EXCEPTION 'Insufficient funds: balance is %', v_balance;
  END IF;

  -- Deduct from sender
  UPDATE accounts SET balance = balance - p_amount WHERE id = p_from_id;

  -- Add to receiver
  UPDATE accounts SET balance = balance + p_amount WHERE id = p_to_id;

  RETURN TRUE;

EXCEPTION WHEN OTHERS THEN
  RAISE;   -- re-raise the exception
  RETURN FALSE;
END;
$$;

-- Call the function
SELECT transfer_funds('from-uuid', 'to-uuid', 100.00);

-- Function returning a table (like a view with parameters)
CREATE OR REPLACE FUNCTION get_user_orders(p_user_id UUID, p_limit INTEGER DEFAULT 10)
RETURNS TABLE(order_id UUID, total NUMERIC, status TEXT, created_at TIMESTAMPTZ)
LANGUAGE SQL STABLE
AS $$
  SELECT id, total, status, created_at
  FROM orders
  WHERE user_id = p_user_id
  ORDER BY created_at DESC
  LIMIT p_limit;
$$;

-- Use it:
SELECT * FROM get_user_orders('user-uuid', 5);

CREATE OR REPLACE PROCEDURE archive_old_orders(p_days_old INTEGER DEFAULT 365)
LANGUAGE plpgsql
AS $$
DECLARE
  v_count INTEGER;
BEGIN
  INSERT INTO orders_archive
  SELECT * FROM orders
  WHERE created_at < NOW() - (p_days_old || ' days')::INTERVAL;

  GET DIAGNOSTICS v_count = ROW_COUNT;

  DELETE FROM orders
  WHERE created_at < NOW() - (p_days_old || ' days')::INTERVAL;

  COMMIT;
  RAISE NOTICE 'Archived % orders', v_count;
END;
$$;

Triggers

🟠 HIGH — Important for automation & audit logs

Triggers automatically execute a function in response to a table event (INSERT, UPDATE, DELETE). They're perfect for audit logging, auto-updating timestamps, enforcing complex business rules, and data synchronization.

Trigger Syntax & Types
Trigger creation
sql
-- Step 1: Create trigger FUNCTION
-- (must return trigger type)

-- 1A. Auto-update updated_at (most common trigger)
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$;

-- Step 2: Attach trigger to a table
CREATE TRIGGER set_updated_at
  BEFORE UPDATE ON users
  FOR EACH ROW
  EXECUTE FUNCTION update_updated_at_column();

  FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();
CREATE TRIGGER set_updated_at BEFORE UPDATE ON orders
  FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();
Audit log trigger
sql
-- Audit log: record every change to a table
CREATE TABLE audit_log (
  id          BIGSERIAL PRIMARY KEY,
  table_name  TEXT,
  operation   TEXT,     -- INSERT, UPDATE, DELETE
  old_data    JSONB,
  new_data    JSONB,
  changed_by  TEXT,     -- current_user
  changed_at  TIMESTAMPTZ DEFAULT NOW()
);

CREATE OR REPLACE FUNCTION audit_trigger_fn()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
  INSERT INTO audit_log (table_name, operation, old_data, new_data, changed_by)
  VALUES (
    TG_TABLE_NAME,
    TG_OP,                                            -- INSERT/UPDATE/DELETE
    CASE WHEN TG_OP != 'INSERT' THEN to_jsonb(OLD) END,
    CASE WHEN TG_OP != 'DELETE' THEN to_jsonb(NEW) END,
    current_user
  );
  RETURN COALESCE(NEW, OLD);
END;
$$;

-- Attach to any table
CREATE TRIGGER orders_audit
  AFTER INSERT OR UPDATE OR DELETE ON orders
  FOR EACH ROW EXECUTE FUNCTION audit_trigger_fn();

sql
-- Keep a cached comment count on posts (performance optimization)
CREATE OR REPLACE FUNCTION update_post_comment_count()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE posts SET comment_count = comment_count + 1 WHERE id = NEW.post_id;
    RETURN NEW;
  ELSIF TG_OP = 'DELETE' THEN
    UPDATE posts SET comment_count = comment_count - 1 WHERE id = OLD.post_id;
    RETURN OLD;
  END IF;
END;
$$;

CREATE TRIGGER update_comment_count
  AFTER INSERT OR DELETE ON comments
  FOR EACH ROW EXECUTE FUNCTION update_post_comment_count();

Roles & Privileges

🔴 CRITICAL — Must Learn — security foundation

PostgreSQL uses a unified role system for both users and groups. Roles can own objects, have login privileges, and be granted privileges on specific database objects.

Creating & Managing Roles
Role management
sql
-- Create a login role (user)
CREATE ROLE app_user LOGIN PASSWORD 'strongpassword';

-- Create a group role (no login)
CREATE ROLE readonly;
CREATE ROLE readwrite;
CREATE ROLE admin;

-- Add user to group role
GRANT readonly TO app_user;

-- Role attributes
CREATE ROLE superadmin
  LOGIN
  PASSWORD 'pass'
  SUPERUSER           -- bypass all permission checks
  CREATEDB            -- can create databases
  CREATEROLE          -- can create roles
  CONNECTION LIMIT 10  -- max concurrent connections
  VALID UNTIL '2025-12-31';  -- expiry

-- Alter a role
ALTER ROLE app_user PASSWORD 'newpassword';
ALTER ROLE app_user CONNECTION LIMIT 20;

-- Drop a role
DROP ROLE IF EXISTS app_user;

-- List all roles
SELECT rolname, rolsuper, rolcreatedb, rolcanlogin, rolconnlimit
FROM pg_roles
ORDER BY rolname;
GRANT & REVOKE
Granting privileges
sql
-- Grant database access
GRANT CONNECT ON DATABASE myapp TO readonly;

-- Grant schema usage
GRANT USAGE ON SCHEMA public TO readonly;

-- Grant table privileges
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO readwrite;

-- Grant on specific table
GRANT SELECT (id, username, email) ON users TO readonly;  -- column-level

-- Grant sequence (for auto-increment / serial)
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO readwrite;

-- Grant function execution
GRANT EXECUTE ON FUNCTION get_user_order_count(UUID) TO readonly;

-- Auto-grant on future tables (crucial!)
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO readonly;

ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO readwrite;

-- Revoke privileges
REVOKE DELETE ON users FROM readwrite;

-- Check what privileges a role has
SELECT grantee, table_name, privilege_type
FROM information_schema.role_table_grants
WHERE grantee = 'readonly';
Recommended Role Setup for a Web App
Production role pattern
sql
-- 1. Group roles (no login)
CREATE ROLE app_readonly;
CREATE ROLE app_readwrite;

-- 2. Login users inherit from group roles
CREATE ROLE app_backend LOGIN PASSWORD 'backend_pass';
GRANT app_readwrite TO app_backend;

Row Level Security (RLS)

🔴 CRITICAL — Must Learn — row-level data security

RLS lets you control which rows a user can see or modify — not just which tables. It's the key to building secure multi-tenant applications and is a cornerstone of Supabase's security model.

RLS Fundamentals
Enabling & basic policies
sql
-- Step 1: Enable RLS on a table
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
-- Once enabled, users see ZERO rows unless a policy allows it

-- Step 2: Create policies

-- Policy: users can only see their own orders
CREATE POLICY users_own_orders
  ON orders
  FOR ALL          -- applies to SELECT, INSERT, UPDATE, DELETE
  TO app_user       -- which role this policy applies to
  USING (user_id = current_setting('app.user_id')::UUID);
  -- USING: filters rows for SELECT/UPDATE/DELETE

-- Separate INSERT check
CREATE POLICY users_insert_own_orders
  ON orders
  FOR INSERT
  TO app_user
  WITH CHECK (user_id = current_setting('app.user_id')::UUID);
  -- WITH CHECK: validates NEW row data on INSERT/UPDATE

-- Admins can see everything
CREATE POLICY admin_all_orders
  ON orders
  FOR ALL
  TO app_admin
  USING (TRUE);    -- no restriction

-- Set the app user context before queries
SET app.user_id = 'some-user-uuid';
SELECT * FROM orders;  -- only that user's orders returned
RLS with Supabase Auth
Supabase RLS patterns
sql
-- Supabase uses auth.uid() function for the logged-in user's UUID

-- Example: profiles table — users can only see/edit their own
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users can view own profile"
  ON profiles FOR SELECT
  USING (auth.uid() = user_id);

CREATE POLICY "Users can update own profile"
  ON profiles FOR UPDATE
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

CREATE POLICY "Users can insert own profile"
  ON profiles FOR INSERT
  WITH CHECK (auth.uid() = user_id);

-- Public read, owner write pattern (e.g. blog posts)
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Anyone can read published posts"
  ON posts FOR SELECT
  USING (status = 'published');

CREATE POLICY "Authors can manage own posts"
  ON posts FOR ALL
  USING (auth.uid() = author_id)
  WITH CHECK (auth.uid() = author_id);

-- Role-based: check user's role from a profiles table
CREATE POLICY "Admins can do everything"
  ON orders FOR ALL
  USING (
    EXISTS (
      SELECT 1 FROM profiles
      WHERE user_id = auth.uid()
        AND role = 'admin'
    )
  );

-- Organisation-scoped access (multi-tenant)
CREATE POLICY "Users access own org data"
  ON projects FOR ALL
  USING (
    org_id IN (
      SELECT org_id FROM org_members
      WHERE user_id = auth.uid()
    )
  );

-- View / drop policies
SELECT policyname, cmd, qual, with_check
FROM pg_policies
WHERE tablename = 'orders';

DROP POLICY IF EXISTS users_own_orders ON orders;

-- Bypass RLS for a role (e.g. migrations, superuser tasks)
ALTER ROLE app_migrations BYPASSRLS;
📌 RLS Performance Tip

Index the columns used in RLS policies (e.g. user_id, org_id). Without indexes, every RLS check does a sequential scan. Also, policies are evaluated per-row — keep USING expressions simple and fast.

Backup & Recovery

🔴 CRITICAL — Must Learn — your data safety net

Data loss is catastrophic. Understand and implement multiple layers of backup — because the question is not if you'll need a restore, but when.

pg_dump — Logical Backups
pg_dump commands
bash
# Backup a single database (SQL format)
pg_dump -U postgres -d myapp -f myapp_backup.sql

# Backup in custom format (faster, supports parallel restore)
pg_dump -U postgres -d myapp -F c -f myapp_backup.dump

# Backup with compression
pg_dump -U postgres -d myapp | gzip > myapp_$(date +%Y%m%d_%H%M%S).sql.gz

# Backup specific tables only
pg_dump -U postgres -d myapp -t users -t orders -f partial_backup.sql

# Backup only schema (no data)
pg_dump -U postgres -d myapp --schema-only -f schema_only.sql

# Backup only data (no schema)
pg_dump -U postgres -d myapp --data-only -f data_only.sql

# Parallel backup (faster for large DBs, custom format required)
pg_dump -U postgres -d myapp -F d -j 4 -f myapp_parallel_backup/

# Backup ALL databases
pg_dumpall -U postgres -f all_databases.sql

# ──── RESTORE ────
# Restore from SQL file
psql -U postgres -d myapp_new -f myapp_backup.sql

# Restore from custom format
pg_restore -U postgres -d myapp_new -F c myapp_backup.dump

# Restore with parallel workers
pg_restore -U postgres -d myapp_new -F d -j 4 myapp_parallel_backup/

# Restore from gzip
gunzip -c myapp_20240115.sql.gz | psql -U postgres -d myapp_new
Automated Daily Backup with Cron
Backup script + cron
bash
#!/bin/bash
# /opt/scripts/pg_backup.sh

DB_NAME="myapp"
DB_USER="postgres"
BACKUP_DIR="/var/backups/postgres"
RETENTION_DAYS=30
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="$BACKUP_DIR/${DB_NAME}_${DATE}.dump"

mkdir -p "$BACKUP_DIR"

# Create backup
pg_dump -U "$DB_USER" -F c -f "$BACKUP_FILE" "$DB_NAME"

# Remove backups older than retention period
find "$BACKUP_DIR" -name "*.dump" -mtime +$RETENTION_DAYS -delete

echo "Backup completed: $BACKUP_FILE"

✅ Choose PostgreSQL E-Commerce / Marketplace

Complex product catalogs, orders with line items, inventory management, payment records, coupon systems — all require ACID transactions, relational integrity, and complex queries. PostgreSQL's JSONB handles variable product attributes. Full-text search works for product search.

✅ Choose PostgreSQL SaaS / B2B Platform

Multi-tenant data isolation via RLS, complex permission systems, audit logging, subscription billing, usage metering — PostgreSQL handles all of this natively. Row Level Security is perfect for tenant isolation without application-layer complexity.

✅ Choose PostgreSQL Financial / Fintech

Money handling demands ACID compliance, no rounding errors (NUMERIC type), immutable audit trails, and serializable transactions for concurrent operations. PostgreSQL's reliability makes it the default in banking and fintech.

✅ Choose PostgreSQL Healthcare / Compliance-heavy

HIPAA, GDPR, SOC2 compliance requires fine-grained access control, complete audit trails, encryption, and data integrity guarantees. PostgreSQL's mature security features, RLS, and column-level encryption (pgcrypto) cover all of these.

⚠️ Consider Alternatives Pure Real-time Messaging / Chat

For storing billions of messages with high write throughput and time-series queries, Cassandra or specialized solutions may scale better. That said, Supabase Realtime + PostgreSQL handles thousands of concurrent users fine for most apps.

⚠️ Consider Alternatives Pure Caching / Session Store

For sub-millisecond key-value access (session tokens, rate limiting, pub/sub), Redis is better. Use PostgreSQL for durable data and Redis as a cache layer in front of it.

❌ Not the Best Choice Analytics / Data Warehouse at Scale

For petabyte-scale analytics with complex aggregations across billions of rows, columnar databases like BigQuery, Snowflake, or ClickHouse are purpose-built. Use PostgreSQL for OLTP (transactional) workloads; use a dedicated OLAP store for heavy analytics.

Query Cost & Time Analysis

🔴 CRITICAL — Understanding cost is how you make databases fast

Every time PostgreSQL runs a query, the query planner estimates how expensive each possible execution path is and picks the cheapest. Understanding how to read cost estimates and actual timing is essential for optimization.

Reading EXPLAIN Output — Cost Numbers
EXPLAIN cost breakdown
sql
EXPLAIN SELECT * FROM orders WHERE user_id = 'some-uuid';

/*
Output:
  Index Scan using idx_orders_user_id on orders
    (cost=0.43..8.45 rows=5 width=128)
         ↑            ↑       ↑        ↑
    startup cost  total cost  estimated  avg row
                              row count  size bytes

cost=0.43..8.45 means:
  0.43 = startup cost  (cost before first row returned)
  8.45 = total cost    (cost to return ALL rows)

Cost units are arbitrary (not milliseconds) — they reflect:
  - seq_page_cost = 1.0 (reading a page sequentially)
  - random_page_cost = 4.0 (random page access — disk seek)
  - cpu_tuple_cost = 0.01 (processing each row)
  - cpu_operator_cost = 0.0025 (each operator evaluation)
*/

-- With ANALYZE: see ACTUAL vs ESTIMATED
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 'some-uuid';

/*
  Index Scan using idx_orders_user_id on orders
    (cost=0.43..8.45 rows=5 width=128)
    (actual time=0.032..0.041 ms rows=3 loops=1)
                 ↑              ↑      ↑       ↑
           actual startup   actual    actual   how many
                time       total time  rows   times run

  Planning Time: 0.1 ms   ← time to generate the plan
  Execution Time: 0.2 ms  ← actual query run time
*/

LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.username;

VACUUM & Autovacuum
VACUUM explained
sql
-- WHY VACUUM EXISTS:
-- PostgreSQL uses MVCC: old row versions ("dead tuples") aren't deleted immediately.
-- VACUUM reclaims that dead space so it can be reused.
-- Without VACUUM, tables grow forever (table bloat).

-- Manual VACUUM
VACUUM orders;               -- reclaim dead tuples (table stays same size)
VACUUM FULL orders;          -- reclaim + compact (locks table! use rarely)
VACUUM ANALYZE orders;       -- reclaim + update statistics
ANALYZE orders;              -- update statistics only (helps planner)

-- Check table bloat (dead tuples)
SELECT
  schemaname,
  relname AS table_name,
  n_live_tup AS live_rows,
  n_dead_tup AS dead_rows,
  ROUND(n_dead_tup::numeric / NULLIF(n_live_tup + n_dead_tup, 0) * 100, 1) AS dead_pct,
  last_vacuum,
  last_autovacuum,
  last_analyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

-- Autovacuum tuning in postgresql.conf
-- autovacuum = on  (never turn this off!)
-- autovacuum_vacuum_threshold = 50       (min dead tuples before vacuum)
-- autovacuum_vacuum_scale_factor = 0.2   (vacuum when 20% of table is dead)
-- For high-write tables, reduce scale_factor:
ALTER TABLE orders
  SET (autovacuum_vacuum_scale_factor = 0.05); -- vacuum at 5% dead

Table Partitioning

🟠 HIGH — Essential for tables with 10M+ rows

Partitioning splits one large table into smaller physical pieces (partitions) while keeping a single logical table interface. Queries that filter on the partition key only scan relevant partitions — a huge performance win.

CREATE TABLE events (
  id         UUID NOT NULL DEFAULT gen_random_uuid(),
  user_id    UUID,
  event_type TEXT,
  payload    JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (created_at);

-- 2. Create partition slices
CREATE TABLE events_2024_q1 PARTITION OF events
  FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');

CREATE TABLE events_2024_q2 PARTITION OF events
  FOR VALUES FROM ('2024-04-01') TO ('2024-07-01');

CREATE TABLE events_2024_q3 PARTITION OF events
  FOR VALUES FROM ('2024-07-01') TO ('2024-10-01');

CREATE TABLE events_2024_q4 PARTITION OF events
  FOR VALUES FROM ('2024-10-01') TO ('2025-01-01');

-- Default partition: catches rows that don't fit any range
CREATE TABLE events_default PARTITION OF events DEFAULT;

-- 3. Create indexes ON EACH PARTITION (or on parent — propagates)
CREATE INDEX ON events (user_id);       -- creates on all partitions
CREATE INDEX ON events (created_at);

-- 4. Insert normally — PostgreSQL routes to correct partition
INSERT INTO events (user_id, event_type, created_at)
VALUES ('user-uuid', 'page_view', '2024-02-15');
-- Goes into events_2024_q1 automatically

-- 5. Query normally — partition pruning happens automatically
EXPLAIN SELECT * FROM events
WHERE created_at BETWEEN '2024-01-01' AND '2024-03-31';
-- Only scans events_2024_q1 — ignores all other partitions!

-- 6. Drop old partition (instant! no row-by-row delete)
ALTER TABLE events DETACH PARTITION events_2024_q1;
DROP TABLE events_2024_q1;

-- 7. List partitions
SELECT child.relname AS partition_name
FROM pg_inherits
JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
JOIN pg_class child ON pg_inherits.inhrelid = child.oid
WHERE parent.relname = 'events';

✅ When to Partition

  • Table has 10M+ rows and growing fast
  • Most queries filter on a specific column (date, region)
  • You need to bulk-delete old data fast (DROP PARTITION)
  • Parallel query scans across partitions
  • Different storage/retention per partition needed

❌ When NOT to Partition

  • Table is small (< 1M rows) — overhead not worth it
  • Queries don't filter on the partition key
  • You need to query across all partitions constantly
  • Adds complexity to schema management
  • Foreign keys from other tables are limited

AI Integration with PostgreSQL & pgvector

🔴 CRITICAL — pgvector turns PostgreSQL into a vector database for AI applications

pgvector is a PostgreSQL extension that adds a native vector data type and high-performance similarity search. Instead of running a separate vector database (Pinecone, Weaviate, Chroma), you store and search vectors directly in PostgreSQL alongside your relational data. This simplifies architecture enormously.

💭 Think — What is a Vector and Why Does AI Need It?

When an AI model processes text, images, or audio, it converts them to a list of numbers called an embedding vector. Similar content produces similar vectors (numerically close). Vector search finds the most similar items without exact keyword matching.

Traditional SearchVector / Semantic Search
Keyword match: "dog food"Finds "puppy nutrition", "canine meal" too
Only finds exact textFinds semantically similar content
Fast, simple, well understoodRequires embeddings, more powerful
Good for structured queriesGood for natural language, recommendations
When to Use Vector Search
Semantic search, RAG (retrieval augmented generation), recommendation systems, duplicate detection, anomaly detection, image search — any task where "similar meaning" matters more than exact keyword match.

Python: store and search embeddings
python
# pip install openai psycopg2-binary pgvector
import openai, psycopg2, os
from pgvector.psycopg2 import register_vector

client   = openai.OpenAI(api_key=os.environ["OPENAI_API_KEY"])
conn     = psycopg2.connect(os.environ["DATABASE_URL"])
register_vector(conn)   # tell psycopg2 how to handle vector type

# ── STEP 1: Generate embedding from text ──
def embed(text: str) -> list[float]:
    resp = client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return resp.data[0].embedding   # list of 1536 floats

# ── STEP 2: Store a document with its embedding ──
def store_document(title: str, content: str):
    vec = embed(content)           # convert text to vector
    with conn.cursor() as cur:
        cur.execute("""
            INSERT INTO documents (title, content, embedding)
            VALUES (%s, %s, %s)
            RETURNING id
        """, (title, content, vec))
        doc_id = cur.fetchone()[0]
        conn.commit()
    return doc_id

# ── STEP 3: Search for similar documents ──
def semantic_search(query: str, top_k: int = 5):
    query_vec = embed(query)       # embed the search query
    with conn.cursor() as cur:
        cur.execute("""
            SELECT
                id,
                title,
                content,
                1 - (embedding <=> %s) AS similarity
            FROM documents
            ORDER BY embedding <=> %s   -- cosine distance operator
            LIMIT %s
        """, (query_vec, query_vec, top_k))
        return cur.fetchall()

SQL: similarity operators
sql
-- Three distance operators in pgvector:
-- <=> cosine distance      (most common for text, range 0-2, lower=similar)
-- <-> L2 (Euclidean) distance (good for image embeddings)
-- <#> inner product        (good for normalized vectors)

-- Find top 5 most similar documents to a query vector
SELECT
  id,
  title,
  1 - (embedding <=> '[0.1, 0.2, ...]'::vector) AS similarity
FROM documents
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector
LIMIT 5;

-- Hybrid search: combine semantic + keyword (best of both worlds)
WITH semantic AS (
  SELECT id,
    1 - (embedding <=> '[...]'::vector) AS sem_score
  FROM documents
  ORDER BY embedding <=> '[...]'::vector
  LIMIT 20
),
keyword AS (
  SELECT id,
    ts_rank(to_tsvector('english', content), plainto_tsquery('dog food')) AS kw_score
  FROM documents
  WHERE to_tsvector('english', content) @@ plainto_tsquery('dog food')
)
SELECT
  d.title,
  COALESCE(s.sem_score, 0) * 0.7 +
  COALESCE(k.kw_score, 0)  * 0.3  AS combined_score
FROM documents d
LEFT JOIN semantic s ON d.id = s.id
LEFT JOIN keyword  k ON d.id = k.id
WHERE s.id IS NOT NULL OR k.id IS NOT NULL
ORDER BY combined_score DESC
LIMIT 5;

🔴 CRITICAL — RAG is the most used AI pattern in production. PostgreSQL is the ideal backend.

RAG (Retrieval Augmented Generation) solves a fundamental LLM problem: LLMs don't know your private data. An LLM trained until 2024 knows nothing about your company's documents, your product manuals, or your customer history. RAG gives the LLM access to your specific knowledge at query time — without retraining the model.

# Chunker: splits text respecting sentence boundaries
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,          # ~500 tokens per chunk
    chunk_overlap=50,        # overlap prevents losing context at boundaries
    separators=["\n\n", "\n", ". ", " "]
)

def ingest_document(title: str, text: str, source_url: str = None):
    with conn.cursor() as cur:
        # Step A: store the source document
        cur.execute("""
            INSERT INTO rag_sources (title, source_url)
            VALUES (%s, %s) RETURNING id
        """, (title, source_url))
        source_id = cur.fetchone()[0]

        # Step B: split document into chunks
        chunks = splitter.split_text(text)
        print(f"Split into {len(chunks)} chunks")

        # Step C: embed all chunks in one batch API call (faster & cheaper)
        resp = client.embeddings.create(
            model="text-embedding-3-small",
            input=chunks
        )
        embeddings = [item.embedding for item in resp.data]

        # Step D: store chunks with embeddings
        for i, (chunk, vec) in enumerate(zip(chunks, embeddings)):
            cur.execute("""
                INSERT INTO document_chunks
                  (source_id, chunk_index, content, token_count, embedding)
                VALUES (%s, %s, %s, %s, %s)
            """, (source_id, i, chunk, len(chunk.split()), vec))

        conn.commit()
        print(f"Ingested: {title} ({len(chunks)} chunks)")
        return source_id

    context_parts = []

    for chunk_id, content, title, url, sim in chunks:
        chunk_ids.append(str(chunk_id))
        context_parts.append(f"[Source: {title}]\n{content}")

    context = "\n\n---\n\n".join(context_parts)

    prompt = f"""You are a helpful assistant. Answer the user's question
using ONLY the context provided below. If the answer is not in the
context, say "I don't have information about that."

CONTEXT:
{context}

USER QUESTION: {user_question}

ANSWER:"""

    # ── Step 4: Call the LLM ──
    llm_resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.1    # low temp = factual, less creative
    )
    answer    = llm_resp.choices[0].message.content
    tokens    = llm_resp.usage.total_tokens
    latency   = int((time.time() - start) * 1000)

    # ── Step 5: Log the query and response to DB ──
    with conn.cursor() as cur:
        cur.execute("""
            INSERT INTO rag_queries
              (session_id, user_query, query_embedding, retrieved_chunks,
               prompt_used, llm_response, model_used, tokens_used, latency_ms)
            VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s)
        """, (session_id, user_question, q_vec, chunk_ids,
              prompt, answer, "gpt-4o-mini", tokens, latency))
        conn.commit()

    return answer

python
import openai, psycopg2, json, os, re
from typing import Optional

client = openai.OpenAI(api_key=os.environ["OPENAI_API_KEY"])
conn   = psycopg2.connect(os.environ["DATABASE_URL"])

# The schema context you give to the LLM
SCHEMA_CONTEXT = """
You have access to these PostgreSQL tables:

users(id uuid, username text, email text, balance numeric, created_at timestamptz)
orders(id uuid, user_id uuid FK→users.id, total numeric, status text, created_at timestamptz)
products(id uuid, name text, price numeric, stock integer, category_id uuid)

Rules:
- Only generate SELECT statements (no INSERT/UPDATE/DELETE)
- Always use table aliases for clarity
- Return ONLY the SQL, no explanation
- Use LIMIT 100 maximum
"""

def nl_to_sql(question: str) -> Optional[str]:
    """Convert natural language question to SQL."""
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": SCHEMA_CONTEXT},
            {"role": "user", "content": f"Question: {question}"}
        ],
        temperature=0   # always deterministic for SQL
    )
    sql = resp.choices[0].message.content.strip()
    # Strip code fences if LLM adds them
    sql = re.sub(r'```sql\n?|```\n?', '', sql).strip()
    return sql

def safe_execute(sql: str) -> dict:
    """Execute SQL safely: read-only, timeout, logging."""
    # Safety: reject anything that isn't SELECT
    if not sql.strip().upper().startswith("SELECT"):
        return {"error": "Only SELECT queries are allowed"}

    import time
    start = time.time()
    try:
        with conn.cursor() as cur:
            cur.execute("SET statement_timeout = '5s'")   # 5s max
            cur.execute(sql)
            rows    = cur.fetchall()
            cols    = [d[0] for d in cur.description]
            elapsed = int((time.time() - start) * 1000)
            return {"columns": cols, "rows": rows, "ms": elapsed}
    except Exception as e:
        conn.rollback()
        return {"error": str(e)}

def ask_database(question: str):
    """Full pipeline: question → SQL → results → natural language answer."""
    sql    = nl_to_sql(question)
    result = safe_execute(sql)

    if "error" in result:
        return f"Error: {result['error']}"

    # Let LLM explain the results in plain English
    rows_str = json.dumps(result["rows"][:20], default=str)
    explain  = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{
            "role": "user",
            "content": f"Question: {question}\nSQL: {sql}\nResults: {rows_str}\nExplain the results in plain English."
        }]
    )
    return explain.choices[0].message.content

# Usage:
print(ask_database("Who are the top 5 customers by total spending?"))
print(ask_database("How many orders were placed in the last 30 days?"))
print(ask_database("Which products are running low on stock?"))

def chat(session_id: str, user_message: str) -> str:
    with conn.cursor() as cur:
        # Step 1: Fetch full conversation history from DB
        cur.execute("""
            SELECT role, content FROM chat_messages
            WHERE session_id = %s
            ORDER BY created_at ASC
        """, (session_id,))
        history = [{"role": r, "content": c} for r, c in cur.fetchall()]

        # Step 2: Add the new user message
        history.append({"role": "user", "content": user_message})

        # Step 3: Call LLM with full history (multi-turn memory)
        resp = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[
                {"role": "system", "content": "You are a helpful assistant."},
                *history
            ]
        )
        answer = resp.choices[0].message.content

        # Step 4: Persist both messages to DB
        cur.execute("""
            INSERT INTO chat_messages (session_id, role, content) VALUES
            (%s, 'user',      %s),
            (%s, 'assistant', %s)
        """, (session_id, user_message, session_id, answer))
        conn.commit()

    return answer

An AI agent is a system where an LLM can autonomously decide which actions to take, execute them, observe results, and loop until a goal is achieved. PostgreSQL is the ideal agent brain: it stores memory, queues tasks, logs every action, and coordinates multi-agent workflows.

📌 Agents vs Chatbots

A chatbot responds to one message. An agent is given a goal and autonomously takes multiple steps to achieve it. Example goal: "Find all customers who haven't ordered in 90 days, draft a personalised re-engagement email for each one, and store the drafts for review." An agent does this in 5 autonomous steps without a human involved at each step.

📋 Plan — Agent Memory Architecture in PostgreSQL

Cognitive scientists describe three types of memory. Your agent needs all three, all stored in PostgreSQL:

📖
Episodic Memory
What the agent did: past actions, observations, tool outputs. Stored in agent_runs and agent_steps tables.
🧠
Semantic Memory
What the agent knows: documents, facts, embeddings. Stored with pgvector for retrieval.
⚙️
Procedural Memory
How to do things: tool definitions, workflows, skill templates stored as JSONB.

import openai, psycopg2, json, os, time

client = openai.OpenAI(api_key=os.environ["OPENAI_API_KEY"])
conn   = psycopg2.connect(os.environ["DATABASE_URL"])

# ── TOOLS: functions the agent can call ──
def tool_run_sql(sql: str) -> dict:
    """Execute a SELECT query and return results."""
    if not sql.strip().upper().startswith("SELECT"):
        return {"error": "Only SELECT allowed"}
    try:
        with conn.cursor() as cur:
            cur.execute("SET statement_timeout='10s'")
            cur.execute(sql)
            cols = [d[0] for d in cur.description]
            rows = cur.fetchmany(50)
            return {"columns": cols, "rows": [dict(zip(cols,r)) for r in rows]}
    except Exception as e:
        conn.rollback(); return {"error": str(e)}

def tool_remember(fact: str, agent: str = "default"):
    """Store a fact in agent long-term memory."""
    with conn.cursor() as cur:
        cur.execute("""
            INSERT INTO agent_memory (agent_name, memory_type, content)
            VALUES (%s, 'fact', %s)
        """, (agent, fact))
        conn.commit()
    return {"stored": True}

TOOLS = [
    {"type": "function", "function": {
        "name": "run_sql",
        "description": "Run a SELECT SQL query on the database",
        "parameters": {"type": "object",
            "properties": {"sql": {"type": "string"}},
            "required": ["sql"]}
    }},
    {"type": "function", "function": {
        "name": "remember",
        "description": "Store an important fact in long-term memory",
        "parameters": {"type": "object",
            "properties": {"fact": {"type": "string"}},
            "required": ["fact"]}
    }}
]

TOOL_MAP = {"run_sql": tool_run_sql, "remember": tool_remember}

# ── AGENT RUNNER ──
def run_agent(goal: str, max_steps: int = 10) -> str:
    # Create the run record in DB
    with conn.cursor() as cur:
        cur.execute("INSERT INTO agent_runs (agent_name, goal) VALUES (%s,%s) RETURNING id",
                   ("data-analyst", goal))
        run_id = cur.fetchone()[0]; conn.commit()

    messages = [{
        "role": "system",
        "content": """You are a data analyst agent. Use run_sql to query
the database and remember to store key findings. Think step by step.
DB has: users, orders, products, ml_experiments tables."""
    }, {"role": "user", "content": goal}]

    step_n = 0

    while step_n < max_steps:
        step_n += 1
        t0 = time.time()

        # LLM decides: think or use a tool
        resp = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=messages,
            tools=TOOLS,
            tool_choice="auto"
        )
        msg     = resp.choices[0].message
        elapsed = int((time.time()-t0)*1000)

        # Log this step to DB
        with conn.cursor() as cur:
            cur.execute("""INSERT INTO agent_steps
              (run_id, step_number, step_type, content, tokens_used, duration_ms)
              VALUES (%s,%s,%s,%s,%s,%s)""",
              (run_id, step_n,
               "tool_call" if msg.tool_calls else "thought",
               msg.content or "[tool call]",
               resp.usage.total_tokens, elapsed))
            conn.commit()

        # If no tool call → agent is done
        if not msg.tool_calls:
            with conn.cursor() as cur:
                cur.execute("""UPDATE agent_runs
                  SET status='completed', result=%s, total_steps=%s, completed_at=NOW()
                  WHERE id=%s""", (msg.content, step_n, run_id))
                conn.commit()
            return msg.content

        # Execute each tool call and feed result back
        messages.append(msg)
        for tc in msg.tool_calls:
            args   = json.loads(tc.function.arguments)
            result = TOOL_MAP[tc.function.name](**args)
            print(f"Step {step_n}: {tc.function.name}({args}) → {str(result)[:80]}")
            messages.append({
                "role": "tool",
                "tool_call_id": tc.id,
                "content": json.dumps(result, default=str)
            })

    return "Max steps reached"

# ── Run the agent ──
result = run_agent(
  "Analyse our top 5 customers by revenue, check if they have any failed orders, and summarise findings"
)
print("\nAGENT RESULT:", result)

from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.types import Tool, TextContent
import psycopg2, json, os

conn = psycopg2.connect(os.environ["DATABASE_URL"])
app  = Server("postgres-mcp")

# ── Tool 1: list all tables ──
@app.list_tools()
async def list_tools():
    return [
        Tool(name="list_tables",
             description="List all tables in the database",
             inputSchema={"type": "object", "properties": {}}),
        Tool(name="describe_table",
             description="Show columns and types of a table",
             inputSchema={"type": "object",
               "properties": {"table_name": {"type": "string"}},
               "required": ["table_name"]}),
        Tool(name="run_query",
             description="Execute a READ-ONLY SQL query",
             inputSchema={"type": "object",
               "properties": {"sql": {"type": "string"}},
               "required": ["sql"]}),
    ]

# ── Tool implementations ──
@app.call_tool()
async def call_tool(name: str, arguments: dict):
    with conn.cursor() as cur:

        if name == "list_tables":
            cur.execute("""SELECT table_name FROM information_schema.tables
                           WHERE table_schema='public' ORDER BY table_name""")
            tables = [r[0] for r in cur.fetchall()]
            return [TextContent(type="text", text=json.dumps(tables))]

        elif name == "describe_table":
            cur.execute("""SELECT column_name, data_type, is_nullable
                           FROM information_schema.columns
                           WHERE table_name=%s ORDER BY ordinal_position""",
                       (arguments["table_name"],))
            cols = [dict(zip(["name","type","nullable"], r)) for r in cur.fetchall()]
            return [TextContent(type="text", text=json.dumps(cols))]

        elif name == "run_query":
            sql = arguments["sql"]
            if not sql.strip().upper().startswith("SELECT"):
                return [TextContent(type="text", text="Error: Only SELECT allowed")]
            cur.execute("SET statement_timeout='10s'")
            cur.execute(sql)
            cols = [d[0] for d in cur.description]
            rows = [dict(zip(cols, r)) for r in cur.fetchmany(100)]
            return [TextContent(type="text", text=json.dumps(rows, default=str))]

# ── Start the MCP server ──
async def main():
    async with stdio_server() as streams:
        await app.run(*streams)

if __name__ == "__main__":
    import asyncio
    asyncio.run(main())

Multi-agent coordination via PostgreSQL

Multiple agents can coordinate by reading/writing shared state in PostgreSQL. One agent creates tasks, another executes them, a third monitors results.

SQL: agent task queue pattern
sql
-- Claim a task atomically (prevents two agents taking the same task)
UPDATE agent_tasks
SET
  status      = 'running',
  assigned_to = 'agent-worker-3'
WHERE id = (
  SELECT id FROM agent_tasks
  WHERE status = 'queued'
    AND (parent_task_id IS NULL OR
         parent_task_id IN (SELECT id FROM agent_tasks WHERE status = 'completed'))
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED   -- skip tasks locked by other agents
)
RETURNING id, description;

-- Agent monitoring: view all running agents and their progress
SELECT
  ar.agent_name,
  ar.goal,
  ar.status,
  ar.total_steps,
  NOW() - ar.started_at            AS running_time,
  MAX(s.step_number)               AS current_step,
  MAX(s.content)                   AS last_action
FROM agent_runs ar
JOIN agent_steps s ON ar.id = s.run_id
WHERE ar.status = 'running'
GROUP BY ar.id
ORDER BY ar.started_at;
