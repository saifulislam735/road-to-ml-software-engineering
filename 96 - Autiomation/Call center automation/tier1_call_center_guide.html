The one thing to hold in your head
Your Node.js server is not the star. It is the wiring. Every piece above is independent. Your server just connects them in the right order at the right time. If you understand the connections, you understand the whole system.

The Loop That Runs Continuously

This is not a request-response system like a web API. It is a continuous loop that runs for the entire duration of the call — firing every time the caller finishes a sentence.

→
LLM thinks

TTS speaks
→
caller listens
↑ this loop fires on every caller utterance, for the entire call duration

What You Are NOT Building

You are not building a chatbot. You are not building a phone app. You are not building a voice recorder. You are building a real-time audio processing pipeline that happens to feel like a phone conversation.

The distinction matters because it shapes every decision — latency over accuracy, streaming over batching, stateful over stateless.

Section 02 — Foundation
The 2-Second Rule
This is the single constraint that governs every technical decision you will make. Understand it before you touch a line of code.

Why 2 Seconds

When you are talking to a person and they pause for more than 2 seconds before responding, you think one of three things: the call dropped, they did not hear you, or something is wrong. Your instinct is to say "hello?" or hang up.

Callers behave identically with an AI voice agent. Beyond 2 seconds of silence, abandonment rate spikes sharply. Your entire architecture must fit inside this window.

Breaking Down the Budget

< 300ms
STT — speech to text
Faster-Whisper (learning) / Deepgram (production)
< 600ms
LLM first token
Ollama (learning) / Claude API (production)
< 200ms
TTS first audio chunk
Piper (learning) / ElevenLabs Turbo (production)
~900ms
Network + overhead budget
WebSocket round trips, buffer processing
Local stack reality check
On your local machine with Ollama (CPU), the LLM alone may take 2–5 seconds. This breaks the 2-second rule. That is fine for learning. You are not serving real callers. The architecture is correct even if the latency is not. When you switch Ollama for Claude API in production, latency drops to under 600ms automatically.

The Technique That Saves You: Streaming + Interleaving

You do not have to wait for the entire LLM response before starting TTS. The moment the LLM returns the first complete sentence, you start converting it to audio and playing it — while the LLM is still generating the rest.

timeline →
LLM starts
→
sentence 1 done
→
TTS starts sentence 1
→
sentence 2 done
→
TTS starts sentence 2
↑ caller hears first words while LLM is still generating. Perceived latency drops dramatically.

This technique — sentence-level streaming interleave — is what makes real-time voice AI feel natural. You will implement this in the Orchestrator.

End-to-End Detection: Where to Add Silence

You also need to know when the caller has finished speaking before you send audio to STT. This is called Voice Activity Detection (VAD). The simplest version: if there is 800ms of silence after the last detected speech, the caller has finished their utterance. Send what you have to Whisper.

VAD library for Node.js
Use @ricky0123/vad-node — a lightweight VAD that runs in Node.js and fires a callback when speech ends. This is your end-of-utterance trigger.

Section 04 — The Pieces
WebSockets
The pipe that carries everything. Audio in, audio out. You cannot build this system without understanding how this pipe works.

HTTP vs WebSocket — The One Comparison That Matters

HTTP — wrong for audio
client sends request
↓ open TCP connection
server sends response
↓ connection closes
× repeat 3000 times per call
WebSocket — correct
client connects once
↓ connection stays open
both sides send freely
↓ 3000 audio chunks, 1 connection
✓ one connection per call, forever

How a WebSocket Connection Starts

A WebSocket always starts as a normal HTTP request — then it upgrades. This handshake happens once. After that, HTTP is gone and it is a raw persistent pipe.

// Client side (browser)
const ws = new WebSocket('ws://localhost:3000');

ws.onopen = () => {
  console.log('connected — pipe is open');
};

ws.onmessage = (event) => {
  // server pushed data to us — could be audio bytes, text, anything
  console.log('received:', event.data);
};

ws.send('hello from browser');   // send anytime, no request needed
// Server side (Node.js with 'ws' package)
import { WebSocketServer } from 'ws';

const wss = new WebSocketServer({ port: 3000 });

wss.on('connection', (socket) => {
  console.log('caller connected');

  socket.on('message', (data) => {
    // data is what the client sent — could be audio bytes
    console.log('received from caller:', data);

    // push something back — no request needed from client
    socket.send('hello from server');
  });

  socket.on('close', () => {
    console.log('caller disconnected — call ended');
  });
});
Audio is just bytes
When the browser sends microphone audio over a WebSocket, it is sending raw PCM bytes — just numbers representing air pressure at a point in time. 16,000 numbers per second (16kHz sample rate). 16 bits per number. Your server receives a Buffer object. Faster-Whisper reads that buffer. That is it.

Binary Messages — What Audio Actually Looks Like

Text WebSocket messages are strings. Audio messages are binary frames — raw bytes. You need to tell the WebSocket to send and receive binary:

// Server: handle binary messages (audio chunks)
socket.on('message', (data: Buffer) => {
  if (data instanceof Buffer) {
    // this is audio — pipe it to Whisper
    processAudioChunk(data);
  }
});

// Server: send binary audio back to caller
socket.send(audioBuffer, { binary: true });

The Two WebSocket Connections in Your System

ConnectionBetweenDirectionWhat flows
WS-1 Browser ↔ Node.js server Both ways Caller audio IN → AI audio OUT
WS-2 Node.js server ↔ Deepgram (production) Both ways Audio IN → Transcript OUT (streaming)

In your local stack, WS-2 is replaced by a subprocess pipe to Faster-Whisper (a Python process running locally). In production, you swap it for Deepgram's WebSocket API. The Node.js orchestrator code changes minimally — just the transport layer.

The hardest part of WebSockets in practice
Connections drop. Networks are unreliable. Your server must handle socket.on('error') and socket.on('close') gracefully — cleaning up state, releasing resources, not crashing. Build this from day one, not as an afterthought.
Section 05 — The Pieces
Phone Layer
How does a real phone call reach your Node.js server? In learning, you use a browser. In production, Twilio or FreeSWITCH. The server code is the same either way.

For Learning: Browser Microphone

The simplest possible phone layer. A single HTML page with a "Start Call" button that captures your microphone and streams audio to your WebSocket server over the browser's built-in AudioWorklet API.

Why this is the right starting point
You control both ends. You can open browser DevTools, see exactly what audio bytes are being sent, pause, debug, replay. No SIP configuration. No account. No cost. When the pipeline works in the browser, you know your server is correct — then you add Twilio on top.

How Browser Audio Capture Works

  1. Browser calls navigator.mediaDevices.getUserMedia({ audio: true }) — asks for mic permission
  2. You get a MediaStream — raw audio from the microphone
  3. You connect it to an AudioWorklet — a background thread that processes audio in 128-sample chunks
  4. Each chunk is sent as binary over the WebSocket to your server
  5. Your server receives audio chunks at ~16kHz, 16-bit PCM

Audio Format — What Faster-Whisper Expects

PropertyValueWhy
Sample rate16000 HzWhisper was trained on 16kHz audio
Channels1 (mono)Whisper expects mono — stereo wastes bandwidth
Bit depth16-bit integerStandard telephony format
EncodingPCM (raw)No compression overhead
Browser default is float32, not int16
The browser's AudioWorklet gives you 32-bit float samples. Whisper wants 16-bit integer. You must convert in the AudioWorklet before sending. This is a common gotcha — if you skip it, Whisper gets garbage and returns garbage transcripts.

For Later: Twilio Media Streams

When you move to production with Twilio, the phone layer changes but your server does not. Twilio receives the real phone call and opens a WebSocket connection to your server — streaming audio in the exact same binary format. Your server code handles it identically.

Section 06 — The Pieces
STT — Faster-Whisper
Speech to text. Turns the caller's voice into words your LLM can read. In learning, this is Faster-Whisper running locally. The interface you build here works identically with Deepgram in production.

How Faster-Whisper Works in Your Pipeline

Faster-Whisper is a Python library. Your Node.js orchestrator cannot call Python libraries directly. You solve this by running Faster-Whisper as a child process — a small Python server that your Node.js server communicates with via stdin/stdout or a local HTTP port.

Node.js (audio buffer)
→
spawn Python process
→
Faster-Whisper
→
transcript text
→
Node.js (text ready)

Two Ways to Connect Node.js to Faster-Whisper

MethodHowBest for
Child process + pipe Node spawns a Python script, sends audio via stdin, reads transcript from stdout Simple, no extra dependencies
Local HTTP server Python runs a Flask/FastAPI server on port 8001. Node calls it via HTTP POST with audio data Cleaner separation, easier to swap for Deepgram later
Recommended: local HTTP server
Build Faster-Whisper as a local HTTP microservice on port 8001. Your Node.js orchestrator sends a POST request with the audio buffer and receives JSON with the transcript. When you move to production, you change the URL from localhost:8001 to api.deepgram.com — the rest of your code does not change. This is good architecture.

The VAD Problem — Knowing When to Send

Whisper is not a streaming transcriber. It transcribes a complete audio segment — not individual chunks as they arrive. You need to collect audio chunks until the caller finishes speaking, then send the whole utterance to Whisper.

This is where Voice Activity Detection (VAD) comes in. VAD listens to the incoming audio stream and tells you: "speech started" and "speech ended." On "speech ended" — you have your complete utterance. Send it to Whisper.

Simple VAD rule for learning
If you want to skip a VAD library initially, implement a simple energy-based detector: calculate the RMS of each audio chunk. If RMS drops below a threshold for 800ms consecutively, speech has ended. It is crude but works well enough to learn the pipeline.

Whisper Model Selection

Bengali language note
Whisper supports Bengali natively — it was trained on multilingual data. You do not need a separate Bengali model. Just pass language="bn" when initializing. For code-switching (Bengali + English in same sentence), use language=None and let Whisper auto-detect — it handles it surprisingly well.
Section 07 — The Pieces
LLM Brain — Ollama
The brain that understands what the caller wants and decides what to say. In learning, this is Ollama. The system prompt, conversation history, and tool calls you design here are permanent — they carry into Claude API in production unchanged.

How Your Orchestrator Talks to Ollama

Ollama exposes a local REST API on port 11434. Your Node.js server sends a POST request with the conversation history and gets a response back. The API is intentionally similar to OpenAI's chat completions format — so switching to Claude API later is a small change.

// Talking to Ollama from Node.js
const response = await fetch('http://localhost:11434/api/chat', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    model: 'llama3.2:3b',
    messages: conversationHistory,   // full history every time
    stream: true,                    // stream tokens as they arrive
  })
});

// Stream handling — get tokens as they come
for await (const chunk of response.body) {
  const token = JSON.parse(chunk).message.content;
  // collect tokens, detect sentence boundary, trigger TTS
}

Conversation History — The Most Important Thing

The LLM has no memory between requests. Every single call to Ollama must include the entire conversation history — every message from the start of the call. Your orchestrator maintains this array in memory, appending each new caller utterance and AI response.

// Conversation state — lives in memory for the call duration
const conversation = [
  {
    role: 'system',
    content: `You are Riya, a customer support agent for ShopBD.
You speak Bengali and English.
You help callers with order status, returns, and tracking.
Always be brief. One question at a time. Never make up order data.
When you need to look up an order, call the get_order_status tool.`
  },
  // caller and AI turns added dynamically:
  { role: 'user', content: 'আমার অর্ডার কোথায়?' },  // caller
  { role: 'assistant', content: 'অর্ডার নম্বরটা বলুন।' }, // AI
  { role: 'user', content: 'Order 4521' },              // caller
  // ... and so on
];

Tool Calls — How the AI Looks Up Real Data

When the caller asks for their order status, the AI does not guess. It calls a tool — a function you define that queries your order database. Ollama supports tool calling natively.

Tool calling flow
  1. Caller: "Where is my order 4521?"
  2. LLM decides it needs order data → returns a tool_call response instead of text
  3. Your orchestrator sees tool_call → runs your actual function → queries order DB
  4. You send the tool result back to LLM as a new message
  5. LLM now has the data → generates the final spoken response

The System Prompt — Where Your Business Logic Lives

The system prompt is the most important thing you write. It is the AI's complete instruction manual. For a call center agent it must cover:

SectionWhat it defines
IdentityName, language, tone — "You are Riya, speak in Bangla and English"
ScopeWhat you can and cannot help with
Constraints"Never make up data. Never promise what you cannot deliver."
Style"Be brief. One question at a time. Always confirm before taking action."
ToolsWhich tools exist and when to use them
Escalation"If caller expresses anger or says 'manager', say you will transfer them."
Local model limitation
Llama3.2:3b follows instructions reasonably but inconsistently. You will find it sometimes ignores the system prompt, breaks character, or hallucinates order data. This is a model quality issue, not an architecture issue. When you swap in Claude API, these problems largely disappear. Build the architecture correctly now — tolerate imperfect LLM behavior in learning mode.
Section 08 — The Pieces
TTS — Piper
Converts the AI's text response back into audio the caller hears. The voice, speed, and quality live here. In learning, Piper runs locally and produces a WAV file in milliseconds.

How Piper Works in Your Pipeline

Piper is a command-line binary. You pipe text into it and it outputs a WAV audio file. Your Node.js orchestrator calls Piper as a child process, reads the audio output, and streams it back over the WebSocket to the caller.

LLM response text
→
Node.js spawns Piper
→
WAV audio bytes
→
WebSocket → caller

Sentence-Level Streaming With Piper

Remember the 2-second rule. You do not wait for the LLM to finish the entire response before starting TTS. You detect sentence boundaries in the LLM token stream and run Piper on each sentence immediately.

  1. LLM streams tokens: "Your" "order" "will" "arrive" "tomorrow."
  2. Your orchestrator sees the period → sentence 1 complete
  3. Immediately spawn Piper with "Your order will arrive tomorrow."
  4. Piper returns audio in ~80ms → stream to caller immediately
  5. LLM continues generating sentence 2 while caller is hearing sentence 1
This is the single biggest latency win
Without sentence streaming, a 3-sentence response takes: LLM full generation (2s) + TTS full conversion (300ms) = 2.3s before the caller hears a word. With sentence streaming, the caller hears the first word in ~700ms. Same content, dramatically better perceived experience.

Audio Format Compatibility

Piper outputs WAV at 22050Hz by default. Your browser expects audio at 16000Hz or 44100Hz. You need to resample — either configure Piper to match, or use a lightweight resampler like sox as a pipe step.

# Tell Piper to output at 16kHz (matches browser audio)
echo "Hello caller" | ./piper \
  --model en_US-lessac-medium.onnx \
  --output_raw \       # raw PCM, no WAV header
  --noise_scale 0.667 \
  --length_scale 1.0 | sox -t raw -r 22050 -e signed -b 16 -c 1 - \
                           -t raw -r 16000 -e signed -b 16 -c 1 -

Bengali TTS

Piper has a Bengali voice model: bn_BD-multi-medium.onnx. Download it from the Piper voices repository on HuggingFace. Voice quality is acceptable for learning but not production-grade yet.

For production Bengali TTS, ElevenLabs is currently the best option — it has a natural-sounding female Bengali voice. This is one area where the local learning stack and production stack diverge in quality significantly.

Code-switching TTS challenge
Bengali callers mix Bengali and English in the same sentence: "আমার order 4521 কোথায়?" Your TTS must handle this gracefully. Piper's Bengali model will mispronounce "order 4521". The production solution is ElevenLabs' multilingual model. For learning, this is an acceptable limitation — note it and move on.

Node.js Orchestrator
The central nervous system. Everything else is a component. This is the code you write — the thing that makes them work together as a single system.

Call Session State

For each active call, your orchestrator holds a session object in memory:

interface CallSession {
  id: string;                     // unique call ID
  socket: WebSocket;              // the caller's connection
  startTime: Date;
  conversation: Message[];        // full conversation history
  audioBuffer: Buffer[];          // accumulating audio chunks
  isProcessing: boolean;          // true while STT/LLM/TTS is running
  callerPhone?: string;           // from Twilio in production
  orderId?: string;               // extracted during conversation
  escalated: boolean;             // true if handed to human
}

The Processing Lock

This is a subtle but important detail: while the AI is processing (STT → LLM → TTS), the caller may continue speaking. You need a lock to prevent processing two utterances simultaneously, which would create chaos in the conversation history.

The isProcessing flag
Set isProcessing = true when you send audio to STT. Set it back to false when TTS audio is fully sent. While isProcessing is true, either: (a) buffer incoming audio and process it after, or (b) discard it and rely on barge-in detection. For learning, discarding is simpler. Barge-in is a Tier 2 feature.

Design principle: thin interfaces
Each of stt.ts, llm.ts, and tts.ts exports a single function with a fixed interface. stt.ts exports transcribe(audioBuffer: Buffer): Promise<string>. Nothing else. When you move to Deepgram, you rewrite only the inside of that function — the interface stays identical. The session manager never changes.
Section 10 — The System
The Hard Parts & Traps
These are the walls you will hit. Knowing they exist before you hit them saves you days of confusion. Each one has a solution — but only if you know to look for it.

Trap 1 — Audio Format Mismatch

What happens: Whisper returns garbage transcripts or errors. The audio plays back distorted.

Why: Your browser sends float32 audio. Whisper needs int16 at 16kHz. You forgot to convert in the AudioWorklet.

Solution: Always convert float32 → int16 in the AudioWorklet before sending over WebSocket. Log the first 20 bytes of every audio message during development to confirm the format.

Most common first blocker
80% of people building this for the first time spend 2–3 days on this exact issue without knowing what to search for. Now you know. If Whisper gives you wrong transcripts — check the audio format first.

Trap 2 — VAD Cutoff Too Early

What happens: The AI keeps interrupting the caller mid-sentence. Transcripts are cut off: "where is my" instead of "where is my order 4521".

Why: Your silence threshold is too aggressive (300ms). Normal human speech has natural pauses within a sentence — a 300ms gap after "where is my" looks like end-of-speech to the VAD.

Solution: Start with 800ms silence threshold. Tune upward if callers are still being cut off. Never go below 500ms for conversational speech.

Trap 3 — Conversation History Grows Unbounded

What happens: After 10–15 turns, Ollama slows down dramatically or throws a context length error.

Why: You are appending every turn to the history and sending the whole thing every time. Local models have small context windows (~4K tokens for 3b models).

Solution: Keep the last 6–8 turns in active history. Summarize older turns into a single system message. In production with Claude API, the context window is huge — this problem goes away.

Trap 4 — WebSocket Closes Unexpectedly

What happens: The browser tab refreshes. Network blips. The call drops but your server has no cleanup logic — the session leaks, the child processes keep running, memory builds up.

Why: You handled socket.on('message') but forgot socket.on('close') and socket.on('error').

Solution: Always implement all three handlers. On close/error: kill any running child processes (Whisper, Piper), release the session from your sessions Map, log the call summary.

Trap 5 — Sentence Boundary Detection is Wrong

What happens: The AI says something like "Your order — order 4521 — will arrive tomorrow." Your sentence splitter fires on the em-dash, sending "Your order" to TTS as a complete sentence. Sounds weird.

Why: Naive sentence splitting on periods and commas breaks on abbreviations, numbers, and pauses within a sentence.

Solution: Use a proper sentence boundary detection library. For Node.js, sentence-splitter or a simple regex that splits on [.!?] followed by a space and capital letter handles 90% of cases. For the remaining 10%, tolerate it in learning mode.

Trap 6 — Piper Startup Latency

What happens: TTS latency is 1–2 seconds instead of 80ms. The call feels laggy even when STT and LLM are fast.

Why: You are spawning a new Piper process for every sentence. Process startup overhead is ~500ms each time.

Solution: Spawn Piper once at server startup in streaming mode, keep stdin open, and pipe text to the running process. This reduces per-sentence TTS latency to under 100ms.

Trap 7 — The LLM Hallucinates Order Data

What happens: The AI tells the caller their order is in Dhaka even though it is in Chittagong. Or invents a tracking number.

Why: The system prompt says "call the tool to get order data" but local models (llama3.2:3b) sometimes ignore tool call instructions and generate a plausible-sounding answer instead.

Solution: Add a validator in your orchestrator: if the LLM response contains an order number or tracking number but did not make a tool call, reject it and re-prompt with "You must use the get_order_status tool before answering." In production with Claude API this almost never happens.

The meta-lesson
Every single one of these traps has a clean solution. None of them require you to rebuild the architecture. They are integration details — the kind you can only learn by hitting them. Now you have a head start on all seven.
Section 11 — The System
Build Order & Milestones
The sequence matters. Build in this order and each step builds on the last. Skip the order and you will debug three things at once and not know which is broken.

The Rule: One Pipe at a Time

Never connect two new pieces simultaneously. Test each piece works in isolation before connecting it to the next. A call center pipeline has 5 pieces. If you wire all 5 at once and it does not work, you have 5 places to debug. If you wire them one at a time, you always know exactly where the problem is.

The 12-Step Build Order

  1. WebSocket echo server
    Server that receives a text message and echoes it back. No audio. No AI. Just confirm the pipe works. ✓ when: browser sends "hello" and receives "hello".
  2. Browser mic capture
    Add the HTML page that captures microphone and sends binary audio over WebSocket. Log received bytes on the server. ✓ when: you see binary buffer logs in the server console while speaking.
  3. Audio format validation
    Confirm audio is 16kHz, int16, mono before sending to Whisper. Save a raw PCM file to disk and play it back. ✓ when: saved audio sounds like your voice.
  4. Faster-Whisper standalone
    Run Faster-Whisper on a pre-recorded WAV file. Get a transcript. No Node.js yet — just Python. ✓ when: transcript matches what you said.
  5. VAD + Whisper integration
    Add VAD to the Node.js server. Collect audio until silence. Send to Whisper HTTP server. Log the transcript. ✓ when: you speak a sentence into the browser and see the correct transcript in server logs.
  6. Ollama standalone
    Call Ollama directly from Node.js with a hardcoded message. Get a response. No STT or TTS yet. ✓ when: "Where is my order?" returns a coherent response in the logs.
  7. STT → LLM pipeline
    Connect STT output to LLM input. Speak into browser → transcript → LLM response in logs. ✓ when: you ask about your order and see a relevant AI response in the terminal.
  8. Piper TTS standalone
    Run Piper on a hardcoded string. Save and play the audio. ✓ when: you hear "Your order will arrive tomorrow" from your speakers.
  9. TTS → WebSocket audio playback
    Send Piper audio over WebSocket to browser. Browser plays it. ✓ when: browser plays audio streamed from the server.
  10. Full loop — first end-to-end test
    Connect all pieces. Speak → transcript → LLM → TTS → hear response. ✓ when: you have a real voice conversation with the AI, even with latency.
  11. Add tool calls — order status
    Add a mock order DB. Add the get_order_status tool. Ask "Where is order 4521?" and hear the AI respond with actual mock data. ✓ when: the AI reads real data from your DB, not hallucinated data.
  12. Add escalation detection
    Detect escalation keywords. When triggered, AI says "Transferring you now" and logs the escalation. ✓ when: saying "I want to speak to a manager" triggers the escalation path.

What Success Looks Like at the End of Tier 1

Tier 1 milestone
You open a browser tab. You click "Start Call." You say: "Amar order 4521 kothay?" — The AI responds in voice with the correct order status from your mock database. You say "I want to speak to a manager" — the AI says "Transferring you now" and logs the escalation. The whole loop works. Latency is high on local models — that is fine. The architecture is production-ready. Swapping the tools makes it production-fast.
