01 Power ON — First Milliseconds
⚡
Chapter 01
Power ON — The First Milliseconds
Before any OS, before any file, before any process — the CPU wakes in a completely primitive state. No memory management, no filesystem, no concept of a "program". Just raw electricity and one chip executing bytes burned into ROM.
🔍 A newborn baby: no memories, no language — only reflexes burned into DNA at birth
Sequence of events — first 500 ms
⚡ PSU & power sequencing
Voltage rails come up in order
Click to expand ↓
The PSU sends 12V, 5V, 3.3V rails. A power-sequencing circuit holds CPU RESET# pin LOW until all voltages stabilise (~100–300 ms). Components power in order: voltage regulators → chipset → PCIe slots → CPU. The CPU cannot execute anything while RESET# is asserted.
🧠 First instruction from ROM
Address 0xFFFFFFF0 on x86
Click to expand ↓
After reset, x86 EIP is hardwired to 0xFFFFFFF0 — mapped to UEFI/BIOS ROM, not RAM. CPU is in 16-bit Real Mode. First instruction is a far JMP into firmware. RAM hasn't been initialised yet — the CPU reads code off the ROM chip on the motherboard.
🔬 POST — Power-On Self Test
Hardware validation
Click to expand ↓
POST tests: CPU registers (internal), RAM (write pattern → read back at every address), storage controllers, and enough GPU for error output. RAM failure → beep codes (display not ready). Motherboards with debug LEDs show hex POST codes (0x19 = PCI init, 0x64 = memory done). Entirely pre-OS.
📋 Hardware enumeration
UEFI builds ACPI & SMBIOS tables
Click to expand ↓
UEFI scans PCI/PCIe bus, assigns IRQ numbers and MMIO addresses to each device (GPU, NVMe, USB, NIC). Builds ACPI tables (power management description the OS will use) and SMBIOS tables (CPU model, RAM size — what dmidecode reads on Linux).
🔒 Secure Boot check
Cryptographic signature verification
Click to expand ↓
UEFI holds a DB (allowed signing certificates) and DBX (revoked) in NVRAM. Before loading any EFI binary it verifies RSA-2048 + SHA-256 signature. Fail → boot refused. Prevents bootkits. Linux distros ship a "shim" signed by Microsoft's key, which then verifies GRUB's signature. You can add own keys with mokutil.
🚀 Bootloader handed control
UEFI to OS territory
Click to expand ↓
UEFI finds EFI System Partition (GPT GUID C12A7328…), reads boot entry from NVRAM, loads grubx64.efi / bootmgfw.efi into RAM, jumps to it. Firmware stays in memory but yields control. GRUB is now running.

Chapter 02 — Bootloader
The Bootloader — Relay Runner
The bootloader has one job: find the OS kernel on disk, load it into RAM, and jump to it. It does NOT start the OS. It does NOT initialise hardware. It finds, loads, and jumps — then vanishes entirely from memory.
🔍 A librarian who finds the right book, opens it to page 1, hands it to you — then leaves the room permanently

Critical misconception: GRUB does NOT "start" or "run" Linux. It only finds vmlinuz, decompresses it into RAM, and does a CPU JMP to its entry point. GRUB is completely erased from memory by the time the kernel runs. The kernel builds everything from scratch.
03 Privilege Rings & Syscalls
🔐
Chapter 03 — Privilege Rings & Syscalls
Privilege Rings & System Calls
The CPU enforces security levels in hardware — the chip itself physically refuses certain instructions unless you're at the right privilege level. This is not a software check. It is the entire foundation of OS security.
🔍 A hospital: janitors, nurses, doctors, and surgeons each physically cannot enter restricted areas — the door locks enforce it, not a policy document
x86-64 ring architecture
Ring −1
Hypervisor — VMX root mode (Intel VT-x / AMD-V). Sits below everything. Controls all physical hardware across VMs. Can silently intercept any Ring 0 instruction from a guest OS. Only exists on machines with virtualisation extensions active. (Chapter 04 covers this fully.)
Ring 0
Kernel — full hardware access. Can: write any physical address, execute HLT/LGDT/LIDT/WRMSR/IN/OUT, modify page tables (CR3), enable/disable interrupts (CLI/STI), manage the MMU. Zero safety net above Ring 0. One bad pointer = entire machine panic. This is exactly why CrowdStrike crashed 8.5 million machines in 2024.
Ring 1/2
Unused on modern x86 — originally for OS services and device drivers. Linux and Windows run all drivers in Ring 0 for performance. Some microkernels (L4, seL4) use Ring 1. ARM uses EL0/EL1/EL2/EL3 instead of x86 rings, same concept.
Ring 3
User space — every app you run. Can: execute code, do arithmetic, read own memory. Cannot: access hardware directly, read another process's memory, modify page tables, disable interrupts. The CPU raises a General Protection Fault (GPF) if Ring 3 code tries a privileged instruction. Kernel catches GPF → sends SIGSEGV → process dies.
System call — crossing the ring boundary

04 Hypervisors & Ring −1
🖥️
Chapter 04 — Hypervisors
Hypervisors & Ring −1 (VMX Root Mode)
A hypervisor creates and manages virtual machines. To sit below the OS kernel it needs a privilege level lower than Ring 0. Intel (VT-x) and AMD (AMD-V) added this in hardware: VMX root mode — informally Ring −1.
🔍 A theatre director: each actor (VM) believes they're in a real play, but the director controls the stage, lights, props — and can pause/resume any scene without the actors knowing
Ring −1 — how it's implemented in hardware
Intel VT-x — the five key instructions

VMXON — enters VMX root mode (Ring −1 activated). Hypervisor must run this first. VMCLEAR / VMPTRLD — prepare and activate a VMCS (VM Control Structure, 4 KB) that describes a VM's full state including which operations cause VMEXIT. VMLAUNCH / VMRESUME — start or continue a VM. CPU switches from VMX root → VMX non-root. VMEXIT — triggered when guest does something the VMCS intercepts. CPU saves guest state, returns to hypervisor. VMXOFF — disable virtualisation, return to normal Ring 0.

VMX Root · Ring −1
Hypervisor (KVM, VMware ESXi, Hyper-V, Xen) — controls physical hardware. Each VM has a VMCS defining what causes VMEXIT. On VMEXIT the hypervisor decides: emulate the operation, pass through to real hardware, or inject a virtual interrupt into the guest.
VMX Non-Root · Ring 0
Guest OS kernel — believes it's in Ring 0. When it writes CR3 (page tables) or accesses hardware, the CPU may silently intercept via EPT (Extended Page Tables) or trigger VMEXIT. The guest kernel has no idea it's virtualised unless it queries CPUID leaf 0x40000000 ("KVMKVMKVM" or "VMwareVMware").
VMX Non-Root · Ring 3
Guest user applications — fully virtualised Ring 3. Identical to bare metal from the app's perspective. Syscalls go to the guest kernel in VMX non-root Ring 0.
Type 1 vs Type 2 hypervisors
⚡ Type 1 — Bare Metal
✅ Runs directly on hardware — IS the OS
✅ Near-native performance (1–3% overhead)
✅ Full hardware control, direct device access
📦 KVM (AWS, GCP), VMware ESXi, Hyper-V (Azure), Xen
🎯 Every cloud VM you've ever used
🖥️ Type 2 — Hosted
Runs as a process inside host OS
10–20% performance overhead
Easy to install and use
📦 VirtualBox, VMware Workstation, QEMU, Parallels
🎯 Developer VMs, testing, Windows-on-Mac
VMEXIT triggers — when the hypervisor takes control
📝 CPUID instruction
Guest queries CPU features
Click to expand ↓
Every CPUID in the guest causes VMEXIT. The hypervisor returns virtualised values. AWS EC2 can claim "Intel Xeon" even if the physical CPU differs. Hypervisors hide features (TSX, SGX) or expose virtual ones. Leaf 0x40000000 returns "KVMKVMKVM" or "VMwareVMware" — how software detects virtualisation.
💾 Page table ops (EPT/NPT)
CR3 writes, TLB flushes
Click to expand ↓
Without EPT (Intel) / NPT (AMD), every guest page-table modification causes VMEXIT — catastrophic performance. EPT adds a second translation level: Guest Virtual → Guest Physical → Host Physical. Hardware MMU does both transparently. VMEXITs only on actual EPT violations (guest accessing unallocated host memory).
🔌 I/O port access
IN/OUT instructions
Click to expand ↓
Guest accesses I/O ports → hypervisor intercepts. Options: emulate in software (slow), PCI passthrough (give guest direct HW access, near-native speed), or VirtIO (paravirtualised driver — guest and host cooperate to avoid VMEXITs entirely, used for network/disk in most cloud VMs).
⏱️ Timer & interrupt virtualisation
vAPIC, HPET virtualisation
Click to expand ↓
The hypervisor multiplexes the physical APIC timer across VMs. Each VM gets a virtual APIC (vAPIC) so it thinks it has its own interrupt controller. Intel APICv lets the guest vAPIC handle interrupts without VMEXITs for most cases — dramatically improving interrupt-heavy workloads. The hypervisor injects virtual interrupts via VMCS interrupt-injection fields.
Real-world: Every AWS EC2 instance runs inside KVM (AWS Nitro hypervisor). Your "Ring 0" kernel is VMX non-root Ring 0. Live migration works because the hypervisor pauses a VM, serialises its VMCS + RAM to another physical host over the network, and resumes. The VM never notices. This is virtualisation's superpower.

Chapter 05 — Virtual Memory
Virtual Memory — The Kernel's Greatest Illusion
Every program thinks it owns the entire 64-bit address space. This is a hardware-enforced lie. Your browser at virtual address 0x400000 and your editor at virtual address 0x400000 are at completely different physical RAM locations. The MMU handles the translation in hardware, transparently, thousands of times per second.
🔍 Every apartment in a city has "Room 101" on its door — but each Room 101 is physically in a different building at a different location

Key memory tricks — demand paging, CoW, swap
📖 Demand paging
Pages load only when touched
Click to expand ↓
Launching a 50 MB binary: kernel maps ELF sections into virtual address space, marks every page "not present", points them at the file on disk. When CPU executes code on a not-present page → page fault → kernel loads that 4 KB page from disk → resumes. A typical app uses only ~30% of its code. Launch is nearly instant because almost nothing actually loads upfront.
🔄 Copy-on-Write (CoW)
fork() without copying memory
Click to expand ↓
fork() naively copies all parent RAM — a 500 MB process would take ~500 ms. Instead: parent and child share the same physical pages, all marked read-only. First write by either → page fault → kernel allocates new frame, copies just that 4 KB page, marks writable, resumes. fork() of a 2 GB process takes microseconds. CoW is also how APFS, Btrfs, and ZFS implement instant snapshots.
💾 Swap space
Evict pages to disk when RAM fills
Click to expand ↓
RAM full + new page needed → page reclaim runs. Selects victim page via LRU / clock algorithm, writes to swap partition/file, marks page table entry "swapped" (stores disk offset). Frame is now free. Next access → page fault → kernel reads from swap → fills new frame → resumes. Repeated swap = "thrashing" → everything slows. This is why opening 100 Chrome tabs degrades performance.
🔒 Address space isolation
Processes truly cannot read each other
Click to expand ↓
Each process has its own page table (pointed to by CR3, switched on context switch). Virtual address 0x400000 in Chrome → physical frame 47. Same virtual address in VS Code → physical frame 831. MMU uses Chrome's page table — frame 831 simply doesn't appear in Chrome's page table. Any attempt → page fault → SIGSEGV. Chrome crashes, not VS Code. Hardware-enforced, not software-checked.

Chapter 06 — File System
File Systems & Inodes
Your disk at the lowest level is a long sequence of numbered sectors. A file system builds the abstraction of files and folders on top. The most important insight: the filename is NOT stored with the file's data — they are completely separate structures.
🔍 A library catalogue: the catalogue (directory) lists book titles (filenames) and shelf numbers (inode numbers). The books themselves (data blocks) are on the shelves. Catalogue and books are separate things.

VFS (Virtual File System): Linux's abstraction layer that makes every storage backend look identical to your app. open("/proc/cpuinfo") → routes to procfs. open("/home/user/file") → routes to ext4. open("/mnt/usb/photo") → routes to FAT32. Same read() syscall for all. "Everything is a file" is made true by VFS.
Journaling prevents corruption: Before writing data, FS writes a journal entry: "I'm about to overwrite blocks [504,505]." Power dies mid-write → on next boot, FS reads journal → replays or rolls back → FS is clean. Without journaling (FAT32): half-written files = corruption. fsck sometimes recovers, often doesn't.

Chapter 07 — Drivers & Interrupts
Device Drivers & Hardware Interrupts
Drivers translate generic kernel requests into hardware-specific commands. Interrupts are how hardware asynchronously notifies the CPU that something happened — without the CPU wasting cycles constantly polling.
🔍 Drivers = language translators between kernel English and hardware assembly. Interrupts = a coworker urgently tapping your shoulder mid-work saying "something needs attention RIGHT NOW."

Why Ring 0 drivers are dangerous — CrowdStrike 2024
CrowdStrike Falcon (July 19, 2024): A content update to the Falcon sensor kernel driver (csagent.sys on Windows) contained a null-pointer dereference in its channel file parser. In Ring 0, there is no exception handler above you — the Windows kernel panicked → Blue Screen of Death → machine reboots → BSOD again → infinite loop. 8.5 million Windows machines worldwide were bricked simultaneously. Airlines (Delta, United), hospitals, banks, broadcasters all went down. Estimated damage: $5–10 billion. Fix required physically booting each machine into Safe Mode to delete a 291-byte corrupt file. Root cause: a kernel driver in Ring 0 with no memory-safety guarantees. This is exactly why the Linux kernel is now adopting Rust — Rust's ownership model prevents null pointer dereferences at compile time.
Driver architecture options
🔴 Kernel drivers (.ko / .sys)
Ring 0 — fastest, no safety net
Click to expand ↓
Traditional Linux kernel modules (nvidia.ko, ath9k.ko, e1000e.ko, ext4.ko). Loaded with insmod/modprobe. Direct hardware access, zero overhead from Ring 3 crossings. One bad pointer = kernel panic. On Windows: Kernel Mode Drivers (.sys). KMDF (Kernel Mode Driver Framework) adds safety rails but can't prevent all bugs. What CrowdStrike's csagent.sys was.
🟡 FUSE — user-space drivers
Ring 3 — safe but 2–4× slower
Click to expand ↓
FUSE (Filesystem in Userspace) lets you write filesystem drivers in Python, Go, or Rust. A kernel shim sends VFS calls to your user-space process via /dev/fuse. A crash kills only the driver process, not the kernel. sshfs (SSH filesystem), ntfs-3g, Dropbox, Google Drive desktop, rclone all use FUSE. Overhead: 2–4× slower due to context switches for every I/O call.
⚡ eBPF — safe kernel code
Sandboxed kernel programmability
Click to expand ↓
eBPF (extended Berkeley Packet Filter) lets you run sandboxed programs inside the kernel without a full driver. The kernel verifier checks all bytecode before running: no infinite loops, no invalid memory access. Used for: networking (Cilium/Cloudflare), observability (DataDog, bpftrace), security (Falco). Attach to any kernel hook: syscall entry/exit, network Rx/Tx, function call. The future of safe kernel extension.
🔔 Top-half / Bottom-half split
Keeping ISRs short
Click to expand ↓
A hardware interrupt disables further interrupts while it runs. Long ISRs delay all other interrupts — terrible for real-time. Linux splits work: Top half (ISR) — runs immediately with interrupts off. Does minimal work: acknowledge IRQ, read status register, enqueue data. Bottom half (softirq/tasklet/workqueue) — runs later with interrupts re-enabled. Does heavy processing: parse network packet, update filesystem buffers. Keeps IRQ latency microseconds even under load.

Chapter 08 — Processes & Threads
Processes, Threads & PID 1
A process is a running program with its own isolated address space. A thread is an execution unit that shares its process's address space. The kernel tracks every one in a Process Control Block (PCB). Everything starts from PID 1.
🔍 Process = a company (own office building, budget, bank account). Thread = an employee inside that company (shares the office, but has their own desk, tasks, and mini-notebook).

Chapter 09 — CPU Scheduling
CPU Scheduler — The Air Traffic Controller
8 CPU cores. 400+ processes. The scheduler decides who gets the CPU, for how long, and in what order. Get it wrong and your system stutters. Get it right and hundreds of programs run "simultaneously" without you noticing any switching.
🔍 An air traffic controller: many planes (processes), few runways (CPU cores). Must be fair, prevent starvation, handle emergencies (high-priority tasks) without ignoring everyone else.

Context switch — what the CPU actually saves/restores

Why EEVDF replaced CFS in Linux 6.6 (Oct 2023): CFS had fairness breakdowns at high thread counts and for bursty workloads (e.g., a video game that uses CPU in 16 ms bursts). EEVDF tracks a "lag" metric (how much CPU a task received vs. how much it's entitled to) and picks the task with the earliest virtual deadline among those eligible. Result: better interactive latency (your mouse stays smooth), fairer sharing, better handling of mixed workloads. Google, Meta, and Valve contributed to its development and tested it on real production workloads before it shipped.

Why io_uring is revolutionary: Traditional I/O: each read()/write() = one syscall = one Ring 3→0→3 context switch. At 1M requests/sec = 1M context switches. For CPU-bound servers at millions of I/O ops/sec, this eliminates essentially all syscall overhead. Cloudflare reported 30–50% throughput improvements. tokio (Rust's async runtime) has an io_uring backend.

📝 Page cache (buffer cache)
RAM mirror of disk blocks
Click to expand ↓
When you write() to a file, data goes to the kernel page cache first (fast, RAM speed). The actual disk write happens asynchronously by the writeback daemon (kworker). This is why write() returns instantly even for large files — data isn't on disk yet. fsync() forces the cache to flush to disk synchronously. Databases call fsync() after every transaction commit.
⚡ Block layer & I/O scheduler
Reordering writes for efficiency
Click to expand ↓
The block layer collects I/O requests and reorders them using a scheduler. For HDDs: elevator algorithm (sort by sector address, reduce seek time). For SSDs/NVMe: no seek time, so MQ-deadline or none. The block layer also merges adjacent requests (if two writes are to sectors 100–107 and 108–115, merge into one 16-sector write). Linux uses blk-mq (multi-queue) for NVMe — one queue per CPU core to avoid lock contention.
💾 NVMe vs SATA — why NVMe is so fast
Protocol and queue depth
Click to expand ↓
SATA uses AHCI protocol: 1 command queue, max 32 outstanding commands, designed for spinning disks. NVMe uses PCIe lanes directly: up to 65,535 queues, each with 65,536 commands. NVMe also uses the OS memory directly via DMA — no intermediate SATA controller buffer. Result: NVMe latency ~20–100 µs vs SATA ~200 µs. Sequential read: NVMe 7,000 MB/s vs SATA 600 MB/s. Fully saturates PCIe 4.0 x4 bandwidth.
🔄 Writeback vs write-through
When data reaches disk
Click to expand ↓
Writeback (default): write() → page cache (fast return) → kworker flushes to disk asynchronously. Risk: power loss between write() and flush = data lost. Write-through: write() → page cache AND disk simultaneously before returning. Slower but durable. O_DIRECT: bypasses page cache entirely — application manages its own buffering (PostgreSQL does this with its shared_buffers). O_SYNC: every write() waits for disk acknowledgement before returning.

Chapter 11 — Shutdown
Shutdown — The Reverse Journey
Shutdown is not "just turn off." It is a carefully ordered, staged teardown to ensure no data is lost, all hardware is left clean, and the system can safely boot next time. Everything that happened during boot is undone — in reverse.
🔍 Closing a restaurant: tell staff to stop seating, clear all tables, let kitchen finish open orders, clean equipment, lock walk-in, turn off gas, then lights, then lock the door. Order matters — skip a step and something breaks.
Complete shutdown sequence — step by step
1
User triggers shutdown — SIGTERM sent to PID 1
Running shutdown -h now, systemctl poweroff, or pressing power button sends SIGPWR/SIGTERM to systemd (PID 1). On Windows: NtShutdownSystem() called via Win32 API. The OS enters an ordered teardown phase. Force-killing power during this phase risks data corruption — the page cache may have unflushed dirty pages.
2
systemd stops all services — in reverse dependency order
systemd knows the full dependency graph (from unit file After=/Before= declarations). If nginx depends on postgresql, nginx stops first. Each service gets SIGTERM with a timeout (default 90 seconds). During those 90 seconds: nginx flushes buffers, closes keep-alive connections, finishes in-flight requests. PostgreSQL writes a clean checkpoint to WAL and closes all sockets. After timeout, remaining processes get SIGKILL (unkillable immediate termination).
3
All user processes killed — process table cleared
Any remaining user-space processes get SIGTERM then SIGKILL. The kernel reaps all zombies (reads exit codes, frees PCBs). All open file descriptors are closed. All sockets send TCP FIN packets (RST if SIGKILL'd). The process table is now empty except for kernel threads (kthreadd, kworker, ksoftirqd, kswapd).
4
sync() — flushing the page cache to disk
This is the most critical step for data integrity. The kernel page cache holds dirty pages — data written by apps but not yet on disk. sync() forces ALL dirty pages to be written to their backing storage (disk, network storage). This can take several seconds if a database or build system was writing heavily. Yanking power during sync() = potential data loss. The filesystem journal helps recover the FS structure, but the actual data you wrote may be gone.
5
Filesystems unmounted — journal marked clean
All mounted filesystems are unmounted in reverse order: umount /mnt/data → umount /home → umount /. Unmounting verifies all writes are complete and writes a "clean unmount" marker in the filesystem superblock (ext4: s_state = EXT4_VALID_FS). On next boot, the kernel sees the clean flag and skips fsck. If machine was force-powered, the clean flag is absent → fsck runs on next boot → may take minutes for large volumes.
6
Swap deactivated — kernel threads stopped
Swap partitions/files deactivated (swapoff). Pages still in swap that belong to running processes are swapped back into RAM. Swap devices marked clean. Kernel threads (kworker, ksoftirqd, kswapd, rcu_sched) are signalled to stop. The kernel's internal workqueue is drained of pending work items.
7
Kernel stops hardware — driver shutdown callbacks
Interrupts are disabled (CLI on x86 — Clear Interrupt Flag). Each device driver's shutdown() callback is called: NIC driver sends link-down signal, GPU driver powers off the display pipeline and scanout, NVMe driver issues an NVMe Shutdown command (the controller writes its internal write buffer to NAND — takes ~100 ms, critical to wait for!), SATA drives receive STANDBY IMMEDIATE. USB hub is powered down.
8
ACPI S5 invoked — power rails cut. Done.
The kernel calls acpi_enter_sleep_state(ACPI_STATE_S5). This invokes the firmware's _S5_ ACPI method which signals the Power Management Controller (PMC) chip. PMC tells the PSU to cut the main power rails (12V, 5V, 3.3V). The CPU executes a final HLT instruction. Standby power (5VSB) remains for USB charging and Wake-on-LAN. The whole sequence from "shutdown" command to powered-off: typically 5–30 seconds on a healthy system.

Why Windows Fast Startup breaks dual-boot: When you click "Shut Down" on Windows 10/11, it logs out users normally but hibernates the kernel session (drivers, kernel state) to hiberfil.sys. Next boot, Windows restores the kernel from disk — skips POST and hardware init. Side effect: The NTFS filesystem is still "mounted" from Windows's perspective. Linux cannot safely write to NTFS partitions from a Windows that "shut down" this way. Solution: always use Restart (not Shut Down) before booting Linux in a dual-boot setup.
Why force-power-off sometimes corrupts data: The page cache holds dirty pages. A power cut gives the disk no warning — those pages are gone. The filesystem journal recovers the FS structure (no corruption), but the actual data written in the last few seconds may be gone. This is why PostgreSQL calls fdatasync() after every transaction commit — forces data to disk before acknowledging the commit. Slower, but guarantees durability (the "D" in ACID). Redis by default does not fsync — it trades durability for speed.
