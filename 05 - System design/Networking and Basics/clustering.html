Feynman Technique

Explain it like I'm five

Before any config, architecture, or code — understand the idea so well you can explain it to anyone. That's the Feynman test.

Imagine a restaurant with one chef. If that chef gets sick, the restaurant closes. Now imagine the same restaurant but with five chefs. If one chef is sick, the other four keep cooking. Customers never know anything went wrong. That's a cluster. Multiple servers (chefs) working together so that no single failure shuts the whole system down.

Now go one level deeper. In a regular restaurant, each chef works independently. In a cluster, all chefs communicate constantly — "I'm okay," "Order #47 done," "I'm overloaded, can you take order #52?" That constant communication is the heartbeat. If a chef stops responding, the others notice and redistribute the work immediately.

Validated Definition

6 Fundamental Requirements of a Cluster

Before going deeper, let's lock down exactly what makes a cluster a cluster. These six properties are the checklist — if something satisfies all six, it's a cluster. Important correction: nodes do not have to be directly connected to every other node.

✅

Validated & Corrected

A common misconception: "every server must connect to every other server." This is false. Nodes only need enough connectivity to cooperate. A load balancer sitting in front is sufficient coordination — nodes behind it never have to talk to each other directly at all.

01

Multiple Nodes

Two or more computers working together — physical or virtual.

Each machine in a cluster is called a node. A single machine cannot be a cluster regardless of how powerful it is. The minimum is 2 nodes — but 2 is dangerous for quorum (covered later). Nodes can be VMs, bare-metal servers, or containers.

EXAMPLE
VPS1 · VPS2 · VPS3
Three VPS nodes = a valid multi-node cluster foundation
▾
02

Communication

Nodes exchange information — directly or through a coordinator.

Nodes must be able to talk. But not every node must talk to every other node directly. Two valid topologies:

MESH (direct)
Each node connects to all others. Full visibility, more complexity.
HUB (via coordinator)
Nodes connect to LB only. No direct node-to-node needed.
KEY INSIGHT
They only need enough connectivity to cooperate — nothing more.
▾
03

Common Purpose

All nodes work toward one shared goal.

Without a common goal, you just have several unrelated computers. A cluster has one job that the nodes collectively accomplish together.

🌐 Serving one website 🗄️ Running one database 📁 Storing files together 🎬 Processing videos 🤖 Training ML models
FEYNMAN CHECK
If you can't say what the cluster does as one sentence, it's not a cluster — it's just several computers.
▾
04

Coordination

A mechanism that organizes the work between nodes.

Nodes must cooperate, not just coexist. Coordination is the organizational layer — it decides who does what, when, and what happens when something fails.

Load BalancerRoutes incoming requests to available nodes
KubernetesSchedules, heals, and scales container workloads
DB ReplicationKeeps data synchronized across primary and replicas
Message QueueDistributes tasks from producers to worker nodes
ConsensusRaft/Paxos — nodes vote on who leads, what's committed
▾
05

Resource Sharing

Nodes share workload, data, or responsibilities.

A cluster isn't just nodes communicating — they must actively share the burden. This is what distinguishes a cluster from a monitoring setup where nodes just watch each other.

⚡
Requests distributed
Web server cluster → each node handles a slice of traffic
🔄
Data synchronized
DB replicas → each node has the same data, writes propagate
💾
Storage distributed
HDFS / Ceph → file chunks spread across storage nodes
▾
06

Single System View

From the user's perspective, it looks like one system.

The user — whether human or another service — must not need to know how many nodes exist or which node handles their request. The cluster presents one unified interface.

FROM THE OUTSIDE
👤 → https://example.com
The user visits one URL. Behind it: 3 servers? 300 servers? 3,000?
They will never know. That's the point.

Think of a call center. You dial one number. Any available agent answers. You don't know how many agents exist or which one you got. The call center is the cluster; the phone number is the VIP; the agents are the nodes.

Common Misconceptions

What a Cluster Does NOT Require

These are the things most people get wrong about clustering. Each misconception leads to over-engineering, wrong decisions, or rejecting valid cluster architectures.

❌

All nodes do not have to run the same application

A Kubernetes cluster runs a database node, a web server node, a job worker node, and a monitoring node — all in the same cluster. Different containers, different roles, same cluster.

REAL EXAMPLE

A Hadoop cluster: NameNode (metadata), DataNodes (storage), ResourceManager (scheduling), NodeManagers (execution) — four different roles, one cluster.

❌

All nodes do not have to communicate directly with all other nodes

This is the most important correction. A load balancer in front of three web servers is a cluster — the three web servers never talk to each other. Coordination happens through the LB.

✓ VALID CLUSTER TOPOLOGY
Users
  ↓
Load Balancer
↓    ↓    ↓
N1   N2   N3
N1, N2, N3 never talk to each other directly — still a valid cluster.
✓ ALSO VALID
N1 ←→ N2
  \    /
    N3
Mesh topology — nodes talk directly. Also valid. Not the only option.
❌

All nodes do not have to belong to one company

Content Delivery Networks (CDNs) are clusters of servers owned and operated by Cloudflare (or Akamai, etc.) — third-party machines serving your content as one system. Federated clusters in Kubernetes can span multiple organizations.

❌

All nodes do not have to have identical hardware

In heterogeneous clusters, nodes have different CPUs, RAM, or storage. Kubernetes handles this via resource requests and limits — a Pod asking for 2 CPUs gets scheduled on whatever node has 2 CPUs free, regardless of total node capacity.

KUBERNETES EXAMPLE

Node A: 4 vCPU, 8GB RAM. Node B: 8 vCPU, 32GB RAM. Node C: 2 vCPU, 4GB RAM.
The scheduler places workloads where they fit. Different hardware, same cluster.

Feynman Definition (Validated):

A cluster is a collection of computers that can communicate and cooperate to accomplish a common task while appearing as one larger system.

Motivation

Why Clustering?

Single servers fail. Clustering is the engineering answer to that fact. But it solves four distinct problems — confusing them leads to over-engineering.

🛡️ HIGH AVAILABILITY

Survive node failures

When one server dies, others take over. Users experience zero downtime. Critical for anything that must run 24/7: banking, healthcare, e-commerce.

📈 SCALABILITY

Grow without rewrite

Hit the ceiling? Add another node to the cluster. Traffic doubles, add two more nodes. No code changes. Scale horizontally, not just vertically.

⚡ PERFORMANCE

Distribute the load

Multiple nodes process requests in parallel. What one server can't handle in time, five servers handle trivially. Latency drops, throughput rises.

🔧 FAULT TOLERANCE

Hardware doesn't matter

SSDs fail, memory corrupts, network cards die. Clustering makes the physical layer irrelevant — the software cluster absorbs those failures silently.

⚠️

Clustering ≠ Load Balancing

A load balancer only routes traffic. A cluster does failover, shared storage, distributed processing, state synchronization. Load balancing is often one component inside a cluster, not the same thing.

🖥️ NODES

The servers themselves

Each physical or virtual machine in the cluster is a node. Nodes can be identical (homogeneous) or have different specs (heterogeneous). Best practice: same OS, same config — less operational surprise.

🧠 CLUSTER MANAGER

The brain

Monitors all nodes, makes failover decisions, reschedules work. Examples: Kubernetes, Pacemaker, ZooKeeper. Without this, nodes can't coordinate — you just have multiple servers, not a cluster.

💓 HEARTBEAT

Are you alive?

Nodes send tiny "I'm alive" pings every few hundred milliseconds. Missed heartbeats trigger failure detection. It's the simplest thing in a cluster and also the most critical.

💾 SHARED STORAGE

One truth, accessible by all

SAN, NAS, or distributed file systems (Ceph, GlusterFS) let all nodes read/write the same data. Without this, each node has its own view of the data — which creates inconsistency.

🌐 VIRTUAL IP (VIP)

The cluster's public face

One floating IP address that always points to the active/healthy node. When failover happens, the VIP moves to the new active node. Clients always connect to the same IP — they never know which node they're hitting.

📡 PRIVATE NETWORK

Nodes talk to each other

A dedicated internal network (separate from public traffic) for heartbeats, replication, and coordination. Keeps cluster chatter off the public network — both for security and to avoid bandwidth contention.

Cluster Modes

Active-Passive vs Active-Active

The most fundamental decision in any cluster design. Both are valid — they solve different constraints.

ACTIVE-PASSIVE (HA FAILOVER)

One worker, one backup

Only the active node handles traffic. The passive node is on standby — synchronized, warmed up, watching. The moment the active node misses heartbeats, the passive node takes over and acquires the Virtual IP.

Like a pilot and co-pilot. The pilot flies the plane. The co-pilot does nothing except watch, be ready, and take over instantly if the pilot has a heart attack. The plane never stops flying.

When to use it

Databases where write consistency matters. Any system where two nodes accidentally both being "active" would cause corruption (split-brain). Simpler to configure and reason about.

Active-Passive — simulate failure
Active node handling all traffic

✓ Pros

  • Simple to configure
  • No split-brain risk
  • Consistent behavior
  • Cheaper (passive uses no compute)

✗ Cons

  • 50% resource waste
  • Brief downtime on failover
  • Passive node idle
  • Doesn't scale traffic
ACTIVE-ACTIVE (LOAD SHARING)

Everyone works, all the time

All nodes handle traffic simultaneously. A load balancer distributes incoming requests across all nodes. If one node fails, traffic redistributes to the surviving nodes — no idle standby needed.

Like a team of cashiers at a supermarket. All lanes are open, all cashiers are serving. One cashier goes home sick — the remaining cashiers handle more customers. Maybe there's a short queue, but nothing stops.

When to use it

Web servers, API gateways, stateless services. Any system where reads are the majority of work. Sessions must be stored externally (Redis, DB) — not in-process.

Active-Active — click to kill a node
3 nodes active — load balanced

✓ Pros

  • Zero downtime on failure
  • Full resource utilization
  • Scales traffic linearly
  • Higher throughput

✗ Cons

  • Complex state management
  • Requires external sessions
  • Data consistency harder
  • More expensive to set up

Health Detection

Heartbeat & Failure Detection

The heartbeat is the simplest mechanism in clustering and also the most consequential. Get it wrong and you either miss real failures or trigger false failovers.

Heartbeat simulation — watch the pulses
💓 Heartbeat healthy — interval: 200ms

How it works

Each node sends a heartbeat signal (usually a tiny UDP or TCP packet) to other nodes on a fixed interval — typically every 200ms to 1 second.

The cluster manager tracks missed heartbeats. After N consecutive misses (configurable, commonly 3–5), the node is declared dead and failover begins.

KEEPALIVED CONFIG
# /etc/keepalived/keepalived.conf
vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 100
    
    # heartbeat interval (seconds)
    advert_int 1
    
    # how many missed = dead
    dead_interval 3
    
    virtual_ipaddress {
        192.168.1.100
    }
}

Failure detection timeline

T+0ms

Node goes down

Hardware fails, OOM killer, network partition — node stops sending heartbeats.

T+200ms

First missed heartbeat

Cluster manager notices silence. Starts counting missed intervals.

T+600ms

3rd miss — node declared dead

Cluster manager initiates failover. VIP is being transferred.

T+800ms

Failover complete

Passive node acquires VIP, becomes active. Clients retry and hit the new active node.

T+1000ms

System healthy again

Monitoring alerts fire. Ops team investigates. N-1 redundancy until fixed.

⚠️

Network blip vs real failure

A too-aggressive heartbeat threshold causes false failovers on network hiccups. A too-lenient threshold means longer downtime on real failures. Typical production sweet spot: heartbeat every 1s, declare dead after 3 misses = ~3s detection time.

Classic Problem

Split-Brain Problem

The most dangerous failure mode in clustering. Understanding it explains why clusters have odd numbers of nodes, why Quorum exists, and why "availability" has limits.

You and your colleague are both on-call. The office phone rings. The line is crackly and you lose connection with your colleague. You think they're dead — so you pick up all calls. Your colleague thinks you're dead — so they pick up all calls too. Now both of you are handling the same calls, making conflicting decisions, with neither knowing about the other. That's split-brain. Two nodes both believe they're the active leader, and they both write data independently. The result? Corrupted, conflicting data that's nearly impossible to reconcile.

Split-brain scenario — network partition
Network intact — nodes communicating

Why it happens

In an Active-Passive cluster, the passive node watches heartbeats to decide "is the active node dead?" If the network link between nodes goes down (but both servers are fine), the passive node sees: "No heartbeats = active is dead" → promotes itself to active. Meanwhile the actual active node is still running, still serving traffic, still writing data. Now you have two active nodes with diverging state.

🧠 SYMPTOM

Two writers, one database

Both nodes accept writes. Row 42 gets updated differently on each node. When the network heals, which version wins? There's no clean answer — data is corrupt.

🗳️ SOLUTION

STONITH — Shoot The Other Node In The Head

Before promoting itself, the passive node sends a hardware-level power-off command to the other node via IPMI/iDRAC. Now only one node is definitely running. Brutal but effective.

The Fix for Split-Brain

Quorum & Voting

Quorum is democracy applied to distributed systems. A node can only become active if it has the vote of the majority. Majority requires more than half — which is why you always use odd numbers of nodes.

Three judges must reach a majority verdict. Even if two judges lose contact with the third, the two know they're the majority (2 out of 3). They can safely proceed. The lone judge, even if they think the other two are dead, knows they are not the majority (1 out of 3) and must step down. No two groups can both claim majority simultaneously. Split-brain solved.

Quorum voting — 5-node cluster
5 nodes alive — quorum: 3/5 required

The math

Quorum = ⌊N/2⌋ + 1 — you need more than half.

💡

2-node clusters are dangerous

With 2 nodes, losing even 1 means you've lost quorum (1 < 2/2+1=2). Add a third "witness" node — a cheap VM that only votes, doesn't serve traffic.

Witness / Tiebreaker node

A cheap, lightweight node that participates in voting but doesn't serve application traffic. It exists solely to prevent 50/50 ties in even-numbered clusters.

# patroni.yml
bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 10
    
    # majority required to elect leader
    maximum_lag_on_failover: 1048576

  # etcd is our quorum store (3 nodes)
  hosts:
    - etcd1:2380
    - etcd2:2380
    - etcd3:2380
Implementation

Step-by-Step: Build a Real Cluster

We'll build a 3-node Active-Passive HA cluster using Keepalived + HAProxy on Ubuntu 24. Every step explained — not just what to run, but why you're running it.

Step 1: Plan before you touch anything

Most cluster failures come from poor planning, not bad code. Decide these before installing anything:

1

Choose cluster mode

Is this a database? → Active-Passive. Is this a web server? → Active-Active. Pick now and stick with it. Changing later means rebuilding.

2

Decide node count

Always odd numbers: 3, 5, or 7. 3 nodes is the sweet spot for most systems — tolerates 1 failure, affordable, not overengineered.

3

Plan your IP addresses

You need: one IP per node (private), one Virtual IP (VIP) for clients, one network for heartbeat (separate NIC preferred).

4

Plan your failover SLA

What's acceptable downtime? 30 seconds? 5 seconds? This drives your heartbeat interval, timeout settings, and whether you need STONITH.

CLUSTER TOPOLOGY PLAN
# Our 3-node HA cluster design
# ─────────────────────────────────────
Node 1 (Master)  IP: 10.0.1.10  role: ACTIVE
Node 2 (Backup)  IP: 10.0.1.11  role: PASSIVE
Node 3 (Witness) IP: 10.0.1.12  role: QUORUM-ONLY

Virtual IP (VIP): 10.0.1.100   # clients connect here
Heartbeat net:    192.168.100.x # private NIC, cluster-only

Failover target:  <30s
Heartbeat:        every 1s
Dead threshold:   3 missed = dead

Step 2: Set up the network

The network is where clusters fail in production. Get this right first.

1

Static IPs — never DHCP for cluster nodes

Dynamic IPs mean a reboot could give a node a different IP. The cluster manager loses track. All cluster nodes must have static, predictable addresses.

2

Add all nodes to /etc/hosts on each node

DNS can fail. Your cluster communication must not depend on DNS. Hard-code every node's hostname → IP mapping in /etc/hosts.

3

Verify node-to-node connectivity

Before installing anything, ping each node from every other node. Confirm firewall rules allow heartbeat ports and replication traffic.

BASH — NETWORK SETUP (RUN ON ALL NODES)
# 1. Set static IP via Netplan (Ubuntu 24)
sudo nano /etc/netplan/01-netcfg.yaml

# Netplan config:
network:
  version: 2
  ethernets:
    eth0:
      addresses: [10.0.1.10/24]
      gateway4: 10.0.1.1
      nameservers:
        addresses: [8.8.8.8, 1.1.1.1]

sudo netplan apply

# 2. Add all nodes to /etc/hosts
echo "10.0.1.10 node1" | sudo tee -a /etc/hosts
echo "10.0.1.11 node2" | sudo tee -a /etc/hosts
echo "10.0.1.12 node3" | sudo tee -a /etc/hosts

# 3. Allow VIP failover (VRRP protocol)
sudo ufw allow 112/any  # VRRP
sudo ufw allow 3306/tcp  # MySQL (if DB cluster)

# 4. Test connectivity between nodes
ping -c 3 node2
ping -c 3 node3

Step 3: Install Keepalived + HAProxy

Keepalived manages the Virtual IP and heartbeat (VRRP protocol). HAProxy is the load balancer that distributes traffic. Together they give you a production-grade HA layer.

BASH — INSTALL ON ALL NODES
# Update first — always
sudo apt update && sudo apt upgrade -y

# Install keepalived (VIP + heartbeat)
sudo apt install -y keepalived

# Install haproxy (load balancer)
sudo apt install -y haproxy

# Allow kernel to bind to non-local IPs
# (needed for VIP to work)
echo "net.ipv4.ip_nonlocal_bind=1" | \
  sudo tee /etc/sysctl.d/99-haproxy.conf
sudo sysctl --system

# Verify installed
keepalived --version
haproxy -v

Step 4: Configure Keepalived

The MASTER node has higher priority. When the master fails, the backup (lower priority) takes over the VIP automatically via VRRP.

NODE 1 — MASTER config

/etc/keepalived/keepalived.conf (node1)
vrrp_script chk_haproxy {
    # check if HAProxy is running
    script "killall -0 haproxy"
    interval 2   # check every 2s
    weight  -20 # drop priority if fail
}

vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 100   # MASTER has highest
    advert_int 1  # heartbeat 1/s
    
    authentication {
        auth_type PASS
        auth_pass cluster_secret
    }
    
    virtual_ipaddress {
        10.0.1.100   # the VIP
    }
    
    track_script { chk_haproxy }
}

NODE 2 — BACKUP config

/etc/keepalived/keepalived.conf (node2)
vrrp_script chk_haproxy {
    script "killall -0 haproxy"
    interval 2
    weight  -20
}

vrrp_instance VI_1 {
    state BACKUP      # not MASTER
    interface eth0
    virtual_router_id 51
    priority 90   # lower than master
    advert_int 1
    
    authentication {
        auth_type PASS
        auth_pass cluster_secret
    }
    
    virtual_ipaddress {
        10.0.1.100   # same VIP
    }
    
    track_script { chk_haproxy }
}
HAPROXY CONFIG — /etc/haproxy/haproxy.cfg
frontend http_front
    bind *:80
    default_backend http_back

backend http_back
    balance roundrobin
    # health check: every 5s, fail after 3 bad, recover after 2 good
    option httpchk GET /health
    server app1 10.0.1.20:3000 check inter 5s fall 3 rise 2
    server app2 10.0.1.21:3000 check inter 5s fall 3 rise 2

listen stats
    bind *:8080
    stats enable
    stats uri /haproxy-stats
    stats auth admin:password
START + ENABLE SERVICES
sudo systemctl enable --now keepalived
sudo systemctl enable --now haproxy

# Verify VIP is on node1
ip addr show eth0 | grep "10.0.1.100"

Step 5: Test your cluster

Never trust a cluster you haven't deliberately broken. Testing failover is not optional — it's the job.

1

Confirm VIP is on the master

On node1: ip addr show | grep 10.0.1.100 — you should see the VIP bound to node1's interface.

2

Simulate master failure — stop keepalived

sudo systemctl stop keepalived on node1. Within 3 seconds, node2 should acquire the VIP.

3

Confirm VIP moved to node2

On node2: ip addr show | grep 10.0.1.100 — VIP should now be here.

4

Restore and confirm failback

Start keepalived on node1 again. Since node1 has higher priority, it should re-acquire the VIP (preemption). Verify with ip addr.

5

Watch HAProxy stats

Visit http://10.0.1.100:8080/haproxy-stats — see backend health, connection counts, response times in real-time.

Step 6: Monitor your cluster

A cluster without monitoring is a cluster that will fail silently and surprise you. Set up observability from day one.

Database Clustering

Database High Availability

Databases need clustering more than anything else — data loss is catastrophic. But databases have state, which makes clustering them much harder than stateless web servers.

PATRONI — POSTGRESQL HA

Industry standard Postgres HA

Patroni uses etcd (or Consul/ZooKeeper) as a distributed configuration store and quorum arbitrator. One PostgreSQL is primary (reads + writes), others are hot standbys (read-only replicas). Patroni promotes a replica automatically on primary failure.

Patroni is like a manager watching three employees. The manager's notebook (etcd) records who's in charge. If the team leader (primary) goes silent, the manager updates the notebook and promotes someone else — and the notebook ensures only one promotion can happen at a time.

RoleReadsWritesCount
Primary✓✓1
Standby (sync)✓✗1+
Standby (async)✓✗many
PATRONI SETUP (patroni.yml)
scope: postgres-cluster
namespace: /service/
name: node1

restapi:
  listen: 0.0.0.0:8008
  connect_address: 10.0.1.10:8008

etcd:
  hosts: node1:2379,node2:2379,node3:2379

postgresql:
  listen: 0.0.0.0:5432
  connect_address: 10.0.1.10:5432
  
  parameters:
    max_connections: 200
    wal_level: replica
    max_wal_senders: 5
    wal_keep_size: 1GB
    
  # Sync replica prevents data loss
  synchronous_mode: true

bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 10
    maximum_lag_on_failover: 1048576

# Manual failover

# Switchover (graceful)
patronictl -c patroni.yml switchover
MYSQL GROUP REPLICATION

Built-in MySQL clustering

MySQL Group Replication provides synchronous replication with automatic failover built directly into MySQL — no external tools needed. All writes go through a consensus protocol (Paxos-based). Minimum 3 nodes for quorum.

⚠️

Network latency matters

Group Replication requires all members to acknowledge every transaction. High latency between nodes = slow writes. Keep nodes in the same AZ or use async replication for cross-region.

MYSQL — GROUP REPLICATION SETUP
-- my.cnf additions (all nodes)
[mysqld]
server_id = 1  -- unique per node!
log_bin = binlog
binlog_format = ROW

plugin_load_add = 'group_replication.so'
group_replication_group_name = "aaaaaaaa-1111-..."
group_replication_start_on_boot = off
group_replication_local_address = "node1:33061"
group_replication_group_seeds = "node1:33061,node2:33061,node3:33061"
group_replication_bootstrap_group = off

-- Start the group (on primary first)
SET GLOBAL group_replication_bootstrap_group=ON;
START GROUP_REPLICATION;
SET GLOBAL group_replication_bootstrap_group=OFF;
MONGODB REPLICA SET

Primary + secondaries + arbiter

MongoDB's native clustering uses a Replica Set: one Primary accepts all writes and replicates to Secondaries. An Arbiter (lightweight node) participates in elections but holds no data — exactly the witness/quorum concept.

💡

Oplog is the heartbeat of replication

MongoDB uses an "oplog" (operations log) — a rolling window of all write operations. Secondaries tail this log to stay synchronized. The oplog size determines how far behind a secondary can fall before needing a full resync.

MONGODB REPLICA SET INIT
// mongosh on node1
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "node1:27017", priority: 2 },
    { _id: 1, host: "node2:27017", priority: 1 },
    { _id: 2, host: "node3:27017", 
      arbiterOnly: true }  // quorum only
  ]
})

// Check status
rs.status()

// Read from secondaries (for scale)
db.getMongo().setReadPref("secondaryPreferred")
REDIS SENTINEL

HA for in-memory cache

Redis Sentinel is a separate process that monitors Redis masters and replicas. If the master dies, Sentinels vote, elect a new master, reconfigure replicas to point to it, and notify clients. Minimum 3 Sentinels for quorum.

Sentinels are security guards watching the Redis master. If the master goes silent, the guards hold an election among themselves. Once the majority agrees "master is dead," they promote one replica and update everyone's paperwork.

REDIS SENTINEL CONFIG
# sentinel.conf
port 26379

# watch the master
sentinel monitor mymaster 10.0.1.10 6379 2
# ↑ quorum: 2 sentinels must agree

# declare dead after 5s silence
sentinel down-after-milliseconds mymaster 5000

# wait 10s before next failover attempt
sentinel failover-timeout mymaster 10000

Container Orchestration

Kubernetes Cluster

Kubernetes is the modern standard for running clustered applications in containers. It handles scheduling, healing, scaling, and networking automatically.

If a traditional cluster is a football team with players (nodes) and a coach (manager), Kubernetes is an entire football league organization. It manages multiple teams, transfers players, decides formations, fires underperforming players and hires replacements automatically, and can spin up an entirely new team from scratch based on a rulebook (YAML manifests).

Kubernetes cluster architecture
Click any component to learn what it does
🎛️ CONTROL PLANE (MASTER)

API Server

The front door to Kubernetes. Everything talks to the API Server — kubectl, workers, controllers. It validates and persists state to etcd. Think of it as the cluster's single source of truth gateway.

📅 CONTROL PLANE

Scheduler

Decides which worker node a Pod runs on. Considers CPU, RAM, affinity rules, taints, and tolerations. If a node is overloaded, the scheduler sends new Pods elsewhere.

🔁 CONTROL PLANE

Controller Manager

Runs reconciliation loops — constantly comparing "desired state" (your YAML) against "actual state" (running cluster). Pod crashed? Controller sees 2 running, desired 3, creates a new one.

🗃️ CONTROL PLANE

etcd

Distributed key-value store holding all cluster state. If etcd dies, Kubernetes is blind — it can still run existing Pods but can't change anything. etcd itself needs 3+ nodes for HA.

👷 WORKER NODE

Kubelet

The agent on every worker node. Receives Pod specifications from the API Server and ensures the right containers are running. Reports node health back to the control plane.

🌐 WORKER NODE

kube-proxy

Manages network rules on each node. Routes traffic to the correct Pod for any given Service. Implements the cluster's virtual network layer using iptables or eBPF.

Key Kubernetes HA patterns

KUBERNETES — PRODUCTION HA DEPLOYMENT
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
spec:
  replicas: 3  # 3 Pods = tolerate 1 failure
  
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1         # max extra pods during update
      maxUnavailable: 0   # never kill before new is ready
  
  template:
    spec:
      # Spread across nodes — no single point of failure
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
      
      # Pod disruption budget — keep at least 2 running
      containers:
        - name: api
          image: myapp:v1.2.3
          
          # Health checks — K8s restarts if these fail
          livenessProbe:
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 10
            periodSeconds: 5
          
          readinessProbe:
            httpGet:
              path: /ready
              port: 3000
            initialDelaySeconds: 5
            
          # Resource limits = prevent one pod killing the node
          resources:
            requests:
              cpu: "100m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"

The CAP theorem for cluster choices

Every distributed cluster must make a tradeoff between three properties. You can only guarantee two.

✅ CONSISTENCY

Every read gets the latest write

All nodes see the same data at the same time. PostgreSQL with synchronous replication. Slow, but safe.

🟢 AVAILABILITY

Every request gets a response

System never returns an error — always responds, even if the data might be slightly stale. Cassandra, DynamoDB.

🌐 PARTITION TOLERANCE

Works despite network splits

Cluster keeps working even if nodes can't talk to each other. This one is basically non-negotiable in distributed systems.

💡

Practical interpretation

Network partitions happen in the real world — so you must tolerate them (P). That means you choose between Consistency and Availability during a partition. PostgreSQL Patroni chooses C (stops writes until quorum). Cassandra chooses A (keeps accepting writes, reconciles later).

Production Engineering

Production Patterns

The gap between "cluster that works in a demo" and "cluster that survives production" comes down to these patterns. Every senior engineer knows them.

🎯 ODD NODES

Always 3, 5, or 7

Even numbers can deadlock: 2 nodes that disagree have no tiebreaker. Odd numbers always produce a clear majority. 3 nodes is the minimum viable HA cluster — tolerates 1 failure.

🌍 MULTI-AZ

Different availability zones

Spread nodes across data center zones or physical racks. An entire AZ going down (power, cooling failure) shouldn't kill your cluster. One node per AZ is the rule.

🔥 CHAOS ENGINEERING

Break it before users do

Monthly failover drills. Kill a random node. Does the cluster heal? Measure the actual downtime. Netflix Chaos Monkey made this famous — most clusters that "should work" don't.

📊 RESOURCE LIMITS

One node can't starve others

In Kubernetes: always set resource requests and limits. In bare-metal: use cgroups or nice values. One runaway process consuming all RAM will crash the node, triggering unnecessary failover.

🔄 ROLLING UPDATES

Zero-downtime deploys

Update one node at a time. Wait for health checks to pass. Never update all nodes simultaneously — that's a full cluster outage disguised as a deployment. Kubernetes handles this natively.

⏰ GRACEFUL SHUTDOWN

Drain before you stop

Before stopping a node, tell the cluster: "I'm leaving." The node stops accepting new requests, finishes in-flight ones, then shuts down. No lost requests, no abrupt connection resets.

Backup is not clustering

⚠️

Critical distinction — beginners always miss this

A replica set is not a backup. If you run DELETE FROM orders accidentally, that DELETE replicates instantly to all replicas. Your cluster has zero data now. Backups (pg_dump, WAL archiving, point-in-time recovery) are a separate concern. Run both.

Case Studies

How Real Companies Do It

Scale these patterns mentally from 2 servers to 10,000.

🎬 NETFLIX

Multi-region active-active

Netflix runs active-active across 3 AWS regions. Any region can fail completely. They invented Chaos Monkey to test this. Cassandra (AP database) chosen specifically because it continues accepting writes during partitions. They sacrificed consistency for availability.

🔍 GOOGLE

Borg → Kubernetes

Google's internal cluster scheduler (Borg) ran for 15+ years before inspiring Kubernetes. Borg runs across continents — millions of jobs scheduled on hundreds of thousands of machines. Everything at Google is a cluster of something.

📘 FACEBOOK / META

ZooKeeper for coordination

Facebook uses Apache ZooKeeper for distributed coordination across their infrastructure — leader election, configuration management, service discovery. The same quorum-based system you'd use with 3 nodes, scaled to handle billions of users.

🛒 E-COMMERCE (YOUR USE CASE)

Practical 3-node setup

For a Bangladeshi e-commerce platform: 3 VPS nodes — 1 PostgreSQL primary (Patroni), 1 hot standby, 1 witness + read replica. Keepalived + HAProxy for web layer. Redis Sentinel for session store. Under 100USD/month, 99.95% uptime achievable.

Lessons Learned

Common Mistakes (and How to Avoid Them)

Every mistake here has caused a real production outage. Learn them for free by reading this. Or learn them expensively by experiencing them.

✗

2-node cluster without a witness

With only 2 nodes and no witness, losing 1 node means losing quorum (1 out of 2 ≠ majority). Your cluster freezes. Fix: always add a 3rd node, even a tiny $5 VM just for voting.

✗

Not testing failover until production fails

A failover that's never been tested is a failover that won't work. The cluster manager, DNS TTL, app reconnect logic, session handling — all must be verified. Do a drill monthly.

✗

Treating the cluster as a backup

Replication is not backup. A corrupted write replicates to all nodes in milliseconds. Take real backups: pg_basebackup, WAL archiving, mongodump — tested and restorable.

✗

All nodes in the same physical location

A power outage, cooling failure, or fire in one data center kills all nodes simultaneously. The cluster was fault-tolerant against software failures but not infrastructure failures. Use different AZs or at minimum different physical racks.

✗

Aggressive heartbeat = false failovers

Setting heartbeat too aggressive (e.g., 100ms interval, 2 misses = dead) causes failovers on network hiccups. A failover causes its own brief outage. Tune carefully: start with 1s interval, 3-5 missed = dead.

✗

Skipping the PodDisruptionBudget in Kubernetes

Without a PDB, a kubectl drain or node upgrade can evict all replicas of a service simultaneously. Your 3-replica "highly available" deployment goes to 0 during maintenance. Always set minAvailable: 1 or maxUnavailable: 1.
