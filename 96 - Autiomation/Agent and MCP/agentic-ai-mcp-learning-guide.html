Phase 0

Foundation

LLM fundamentals · async Node.js · first tool call · Docker · 2–3 weeks

📖
Explanation

An agent is just an LLM running in a loop. It reads what's in its context window, decides on an action — either a tool call or a final answer — executes it, appends the result, and repeats. Everything you build in later phases is a variation of this loop. The loop is the atom of agentic AI.

Three concepts to lock in before writing any agent code:

Tokens are the unit of computation. The LLM does not read words — it reads token IDs. Cost and speed both scale with token count. Everything from your system prompt to tool results consumes tokens.

Context window is the LLM's working memory. It only sees what's currently in the context. There is no persistent memory between calls — that's your job to manage. When the context fills up, early messages drop off and the model "forgets".

Tool calling is the bridge from language to action. You define functions as JSON schemas. When the model decides to use one, it emits a structured tool_use block. You run the function and inject the result back as a tool_result. The model never actually runs code — it asks you to, then reads what you report back.

🔢
Steps
  1. Read the Anthropic Messages API docs. Understand the raw JSON: role, content, tool_use, tool_result blocks.
  2. Make a raw curl POST to api.anthropic.com/v1/messages. Read the full response structure before touching any SDK.
  3. Install the Node.js SDK: npm i @anthropic-ai/sdk. Replicate the curl call in TypeScript.
  4. Build a chat loop that appends messages to a history array and sends the full history on each turn.
  5. Define one tool (e.g. get_weather) as a JSON schema. Handle the tool_use → execute → tool_result cycle manually.
  6. Add a max_iterations guard so the loop can never run forever.
  7. Wrap everything in Docker Compose with your ANTHROPIC_API_KEY in an .env file.
✅

Checkpoint: One chatbot that calls at least one tool, running inside docker compose up, with message history maintained across turns.

Thinking & designing

Design your message history as a plain typed array: Array<{role: 'user'|'assistant', content: ContentBlock[]}>. Every turn appends to it. The LLM only sees what's in that array — it IS your state. Think of it as a transcript the model reads from scratch on every API call.

A tool definition is a JSON Schema contract. Ask: what is the minimum input the model needs to invoke this? What is the minimum output the tool needs to return? Keep both minimal and strongly typed. Avoid optional fields until you have a reason for them.

Think about failure modes now. What happens if the tool throws? Catch the error, return a tool_result with is_error: true and a human-readable message. Never let a tool exception bubble up and crash the loop.

import Anthropic from '@anthropic-ai/sdk'; import { TOOLS, executeTool } from './tools'; const client = new Anthropic(); export async function runAgent(userMessage: string) { const messages: Anthropic.MessageParam[] = [ { role: 'user', content: userMessage } ]; for (let i = 0; i < 10; i++) { const res = await client.messages.create({ model: 'claude-sonnet-4-6', max_tokens: 1024, system: 'You are a helpful assistant with tools.', tools: TOOLS, messages, }); if (res.stop_reason === 'end_turn') { return res.content.find(b => b.type === 'text')?.text; } if (res.stop_reason === 'tool_use') { messages.push({ role: 'assistant', content: res.content }); const toolResults: Anthropic.ToolResultBlockParam[] = []; for (const block of res.content) { if (block.type !== 'tool_use') continue; try { const output = await executeTool(block.name, block.input); toolResults.push({ type: 'tool_result', tool_use_id: block.id, content: JSON.stringify(output), }); } catch (err) { toolResults.push({ type: 'tool_result', tool_use_id: block.id, content: String(err), is_error: true, }); } } messages.push({ role: 'user', content: toolResults }); } } throw new Error('Max iterations reached'); }

Phase 1 — Junior

ReAct loop + first MCP server

Agent loop · MCP SDK · HTTP/SSE transport · PM2 + Nginx on VPS · 3–4 weeks

📖
Explanation

ReAct (Reason + Act) is the canonical agent pattern. The model reasons in natural language, decides to call a tool, observes the result, reasons again. Your executor runs between each act and observe step. This loop, with proper error handling and stopping conditions, is what you are building.

MCP (Model Context Protocol) is a standard for exposing tools over a network. Instead of defining tools as hardcoded functions inside your agent, you run a separate MCP server that advertises its capabilities as a manifest. Any MCP-compatible client connects, reads the manifest at runtime, and can call those tools.

Think of MCP as "what if your tool registry was a service". The agent connects like a client. The server runs independently. You can update tools, add new ones, restrict access — all without touching the agent code.

🔢
Steps
  1. Add a max_iterations guard and stopReason state machine to your Phase 0 agent loop.
  2. Ensure all tool errors return tool_result with is_error: true — never throw from inside the loop.
  3. Install @modelcontextprotocol/sdk. Read the MCP protocol overview (5-minute read).
  4. Create a new mcp-server/ package. Register 3 tools using McpServer.tool(). Run over stdio transport first.
  5. Test the server in isolation with MCP Inspector: npx @modelcontextprotocol/inspector. Confirm all tools appear and respond correctly.
  6. Switch to HTTP + SSE transport. Expose on port 3001. Add a GET /health endpoint that returns 200.
  7. Rewrite your agent to use an MCP client from the SDK. Agent discovers tools from the server at startup — no hardcoding.
  8. Deploy both to your KVM2 VPS: PM2 for process management, Nginx as reverse proxy with SSE-specific config.
✅

Checkpoint: Agent + MCP server both live on your VPS, reachable over HTTPS. Agent uses tools it discovered at runtime from the MCP server.

Thinking & designing

Design your MCP server as a thin adapter. No business logic inside it — just translate MCP protocol calls to your actual functions. If you put business logic in the MCP server, you'll need to version it carefully. Keep tools dumb and fast.

The trust boundary is deliberate: the MCP server is a separate process or machine. The agent trusts its output as tool results. This means you can update tool implementations, fix bugs, or swap backends without redeploying the agent.

Design your tool schemas to be model-friendly: clear descriptions, explicit parameter names, concrete examples. The model reads these schemas to decide when and how to call a tool. Vague schemas lead to incorrect or missed tool calls.

Scale

Single instance is fine at Phase 1. Two things to configure correctly for future scaling:

Nginx SSE settings: proxy_buffering off and proxy_read_timeout 300s are non-negotiable. Without them, Nginx silently closes SSE connections after 60 seconds and you'll see mysterious tool failures.

Health endpoint: Add GET /health returning 200 OK now. You'll need it for blue-green deploys in Phase 3, and it costs nothing to add today.

🔄
Retrain / update

Updating a tool = deploy new code + pm2 reload mcp-server. The agent discovers the updated schemas on next connection — no agent restart needed if the schema is backward-compatible.

Add a version string to your MCP server name (e.g. 'my-tools@1.2.0') and log it on every agent startup. When you see a bug, you know exactly which server version was running.

Breaking schema changes (renaming params, changing types) require a coordinated deploy: update the server first, then redeploy the agent that expects the new schema.

Phase 2 — Intermediate

Multi-agent systems + real MCP

Orchestration · pgvector memory · RAG · MCP auth · CI/CD · horizontal scale · 4–6 weeks

📖
Explanation

A single agent hits limits fast: the context window fills up, the tool set grows unwieldy, and one long failure blocks everything. Multi-agent systems solve this through specialization and delegation.

An orchestrator agent receives a high-level task, breaks it into subtasks, and delegates to specialist agents — each with a focused tool set, a smaller context, and a specific role (researcher, coder, reviewer). The orchestrator collects results and assembles the final output.

Memory solves the goldfish problem. Between sessions, agents forget everything. A vector store (pgvector in Postgres) lets you store past interactions as embeddings and retrieve the most semantically relevant ones at session start. RAG is simply retrieval exposed as a tool the agent calls when it needs more information.

🔢
Steps
  1. Design the orchestrator ↔ subagent contract: typed task input objects and typed result objects. Use Zod for validation.
  2. Implement parallel subagent dispatch with Promise.all for independent subtasks. Sequential only when one result feeds the next.
  3. Add pgvector to Postgres: CREATE EXTENSION vector;. Design the memory table schema.
  4. Write embed(text), storeMemory(), and retrieveMemory(query, topK) functions.
  5. Expose retrieve_memory as an MCP tool so agents call it naturally inside their loop.
  6. Add API key authentication middleware to your MCP Express server (header: x-api-key).
  7. Add per-client rate limiting with a Redis counter: INCR rate:{apiKey} + EXPIRE rate:{apiKey} 60.
  8. Write a GitHub Actions workflow: lint → test → docker build → push → SSH to VPS and docker compose up -d.
  9. Add MCP Resources (URI-based data) and Prompt templates to your server.
✅

Checkpoint: Orchestrator delegates to 2+ specialists. MCP server has auth + rate limiting. Full CI/CD on git push. Memory persists across sessions via pgvector.

Thinking & designing

Design the orchestrator to be stateless between invocations. All state lives in message history + external stores. Pass everything as input. This makes it resumable and horizontally scalable later without changes.

Memory schema design — get this right now: (id uuid, content text, embedding vector(1536), session_id text, agent_id text, created_at timestamptz, metadata jsonb). The metadata column is where you store topics, tags, or filters. Adding a new filter field later is just writing to metadata — no schema migration needed.

For multi-agent work, design a task contract before writing any LLM calls. Define: what does the orchestrator send to a subagent? What does the subagent return? Type these strictly with Zod. The LLM will hallucinate fields if you don't enforce the schema on outputs.

Scale

MCP SSE horizontal scaling requires sticky sessions because SSE connections are stateful. Two instances need the same client to always hit the same backend.

upstream mcp_backend { ip_hash; # sticky: same client → same backend server mcp1:3001; server mcp2:3001; }

Before adding a second MCP instance: move any in-process session state to Redis. Anything stored in a Node.js global or module-level variable will not survive load balancing.

🔄
Retrain / update

At Phase 2, "retraining" means improving system prompts, updating your RAG corpus, and refining tool schemas based on real usage logs.

Build a simple admin script to re-index your vector store when source documents change. Don't let the corpus drift silently out of date.

For breaking tool schema changes: bump the tool name (e.g. search_web_v2) and keep the old version running until you've confirmed no agents are using it. This is your zero-downtime tool migration pattern.

Phase 3 — Senior

Production reliability

Observability · durable queues · multi-tenant MCP · blue-green deploy · prompt caching · 6–8 weeks

📖
Explanation

Three failure modes dominate production agentic systems:

1. Mid-task crashes. The server dies while the agent is 6 steps into a 10-step task. Without checkpointing, the user gets nothing and you have no trace. Durable job queues (BullMQ) serialize agent state after each step. On restart, the job resumes from the last checkpoint.

2. Silent quality regressions. You update a system prompt on Friday. By Monday, users are getting worse answers and you don't know why. Observability (Langfuse) solves this: every LLM call, every tool call, every token cost is traced. You can compare before/after on your eval dataset.

3. Tenant bleed. Tenant A's tool permissions accidentally apply to Tenant B, or one tenant's heavy usage slows everyone else. Multi-tenant MCP config with per-tenant isolation solves this by mapping each API key to a strict, isolated config object.

🔢
Steps
  1. Instrument your agent loop with OpenTelemetry: one span per LLM call (token counts as attributes), one span per tool call.
  2. Run Langfuse via Docker Compose (self-hosted) and configure the OTel exporter to push traces to it.
  3. Move agent invocations to BullMQ jobs. Each job = one complete agent run. Configure retries (3x exponential backoff) and a dead-letter queue.
  4. After each tool result, checkpoint the full message history to Redis: SET agent:checkpoint:{jobId} {json} EX 3600.
  5. On job resume after worker restart, load the checkpoint and continue from where it stopped.
  6. Build a human-in-the-loop gate: certain tools emit a "needs approval" event, pause the job, resume only when a webhook delivers approval.
  7. Implement per-tenant MCP config: apiKey → tenantConfig → { allowedTools, toolParams } stored in Postgres, cached in Redis.
  8. Write and test blue-green.sh with health-check gating. Test it before you need it in a real incident.
  9. Add Anthropic prompt caching: prefix system prompt block with "cache_control": {"type": "ephemeral"}.
✅

Checkpoint: Every agent run is traced in Langfuse, jobs survive server restarts via BullMQ checkpointing, zero-downtime blue-green deploys work, multi-tenant config is isolated and live.

Thinking & designing

Think of each agent run as a transaction with observable state. Design a job schema: { job_id, tenant_id, status, steps_completed, checkpoint_data, created_at, finished_at, cost_tokens }. Everything meaningful about a run lives in this record.

For multi-tenancy: one config object per tenant stored in Postgres. A tenant's API key maps to a config with their allowed tool list, per-tool parameters (their DB connection, their API keys), and rate limits. Never share config objects between tenants — this is both a security concern and a debugging concern.

For the human-in-loop gate: the cleanest pattern is a "pause callback". The tool returns { type: 'awaiting_approval', approval_id: 'xxx' }. The worker pauses the job. Your API exposes POST /approve/:id that un-pauses it. Build a simple dashboard to show pending approvals.

const worker = new Worker('agent-runs', async (job) => { const { tenantId, userMessage } = job.data; const saved = await redis.get(`checkpoint:${job.id}`); const messages = saved ? JSON.parse(saved) : [ { role: 'user', content: userMessage } ]; const config = await getTenantConfig(tenantId); const span = tracer.startSpan('agent_run', { attributes: { tenantId, jobId: job.id } }); try { for (let i = 0; i < 20; i++) { const res = await callLLM(messages, config.allowedTools); if (res.stop_reason === 'end_turn') break; messages.push({ role: 'assistant', content: res.content }); // Checkpoint after every step await redis.set( `checkpoint:${job.id}`, JSON.stringify(messages), 'EX', 3600 ); await job.updateProgress({ step: i }); const results = await executeTools(res.content, config); messages.push({ role: 'user', content: results }); } span.setStatus({ code: SpanStatusCode.OK }); return { success: true }; } catch (err) { span.recordException(err); throw err; } finally { span.end(); } }, { connection: redis, concurrency: 10 });

Scale

Queue-depth autoscaling: a cron every 30 seconds checks BullMQ waiting count. Above threshold → docker compose scale worker=N. Manual but very effective on a single VPS with spare RAM.

Prompt caching ROI: if your system prompt is 2000 tokens and you make 1000 agent calls per day, caching saves ~1.8M input tokens per day. That's a 40–90% latency reduction on the cached portion of each call plus significant cost savings.

Concurrency tuning: set BullMQ concurrency to match available memory. Each concurrent agent run holds ~50MB of Node.js heap. On a 4GB VPS with other services, concurrency: 10–15 is a safe starting point.

Phase 4 — Expert

Platform scale + cloud-native

Kubernetes · managed queues · LLM gateway · edge MCP · advanced architectures · ongoing

📖
Explanation

Expert-level problems shift from "make it work" to "make it work for thousands of concurrent users globally, within a cost budget". The three dominant concerns:

Cost. LLM API calls are your largest operating expense at scale. Every unnecessary token multiplies. Prompt caching, context compression, model routing (cheap model for simple steps, expensive for hard reasoning), and batching are all levers you must actively manage.

Latency. A user in Dhaka calling an MCP tool on a server in Virginia adds 200–300ms of round-trip per tool call. An agent making 10 tool calls feels unacceptably slow. Edge MCP (Cloudflare Workers, 300+ regions) brings tool latency down to <30ms for most users globally.

Advanced agent quality. Reflexion (self-critique loops), MCTS planners (tree search over action sequences), and world model agents tackle the quality problem: how do you make agents that reliably solve hard, multi-step problems? Understanding these lets you design better agents even without implementing the full algorithms.

Steps
  1. Write Kubernetes manifests for each service (agent worker, MCP server, API, LLM gateway). Start small with 2 nodes.
  2. Provision a managed K8s cluster: DigitalOcean DOKS, GKE Autopilot, or EKS. Migrate one service at a time.
  3. Replace BullMQ with a managed queue: AWS SQS or GCP Pub/Sub. Your worker just pulls from the cloud queue instead of Redis.
  4. Build an LLM gateway service: model fallback, per-tenant cost caps, retry with backoff, and request logging.
  5. Write your first Cloudflare Worker MCP tool (e.g. a fast search or lookup). Measure latency vs your VPS version.
  6. Implement a global rate limit and quota service (Redis Cluster or Momento) shared across all pods and edge nodes.
  7. Implement the Reflexion pattern: after a failed run, re-run with a self-critique prompt describing the failure.
  8. Build your domain-specific eval framework. Run it against every new Anthropic model before migrating production.

Thinking & designing

Design for cost first. Every architecture decision should include a cost model: "N LLM calls per user request × M average tokens × price = cost per 1000 requests". Build a cost dashboard into your LLM gateway from day one. Cost surprises at scale are business-critical.

The LLM gateway is the single most important infra component at platform scale. It's a thin service between your agents and Anthropic that handles: request logging, per-tenant budget enforcement, model fallback, identical prompt deduplication (cache responses to byte-identical prompts in Redis), and retry with backoff.

Reflexion is the most practical advanced architecture to start with. When an agent run fails or scores below threshold, re-run with an additional system prompt section: "Your previous attempt failed because X. Think carefully about how to avoid that mistake." Studies show 10–25% improvement on hard tasks with no model changes.

Scale
10,000+ concurrent sessions 1M+ tool calls/day 50+ MCP server instances <200ms p99 tool latency (edge)

Context batching: group short-context agent calls (under 4k tokens each) into Anthropic Batch API requests. Batch API is 50% cheaper and processes within 24h — ideal for background/async agent runs.

Model routing: route simple classification steps to Haiku (cheap, fast), complex reasoning to Sonnet, and Opus only for the hardest multi-step planning. Your LLM gateway handles routing transparently based on a step-type annotation.

Global rate limit: all K8s pods and edge nodes must share a single Redis Cluster quota service. Without this, 50 pods each think they have the full rate limit — causing cascading failures.

🔄
Retrain / update

Prompt registry: a version-controlled store of system prompts. Each entry has: the prompt text, eval score, deploy date, and who approved it. Changing a prompt means creating a new version, running evals, and promoting — never editing in place.

Model upgrade protocol: when Anthropic releases a new model, never upgrade production blindly. Run your full eval suite against it on a staging cluster. Compare scores on your golden dataset. Migrate production only after confirming parity or improvement.

A/B testing: route 10% of live traffic to a new system prompt variant. Collect eval scores on real traffic for 48 hours. If the variant wins, promote to 100%. Your LLM gateway handles routing by tenant bucket or random hash.
