Section 01

What Are TCP and UDP?

Both live at the Transport Layer (Layer 4) of the OSI model. They sit on top of IP and are responsible for delivering data between applications on two machines. But they make very different tradeoffs.

TCP

🔑 Key Mental Model
TCP is like a phone call — you establish a connection, confirm the other side is listening, talk back and forth, then formally hang up. UDP is like sending a flyer through the mail slot — you just push it in and walk away, no confirmation it was picked up.

Section 02

Real-World Analogies

The best way to understand protocols is to map them to something physical you already know.

📦
TCP = Courier Service (DHL/FedEx)
You send a package. They give you a tracking number. They confirm it was received. If it gets lost, they re-send it. Packages always arrive in the right order. You pay for the service (overhead). The recipient must sign (acknowledge).
📮
UDP = Dropping Flyers
You print 1000 flyers and drop them out a window. You don't know who got them. Some might blow away. You don't care — if most land, the job is done. You can distribute far more flyers (speed) because there's no overhead.
📞
TCP = Phone Conversation
You dial, it rings, they pick up (handshake). You speak, they respond (acknowledgment). If you say "what?" they repeat (retransmission). You always know what was said in what order (in-order delivery). You formally say goodbye (connection teardown).
📻
UDP = Radio Broadcast
The radio tower broadcasts. It doesn't know who's listening. It doesn't re-broadcast if you missed a part. The signal goes out — whether 0 or 1 million hear it is not its concern. Extremely efficient for one-to-many. Perfect for live music or sports.
⚡ Why would you WANT to lose packets?
In a video call, if a frame of video arrives 2 seconds late — it's useless. You'd rather show a slightly blurry image (packet loss) than freeze while waiting for retransmission. UDP lets the application decide what to do with missing data, which is often: just skip it.

📐 Why the size difference matters
TCP's 20-byte header has 15× more information than UDP's 8 bytes. Every packet you send carries this overhead. For a 1-byte ping, TCP sends 21 bytes minimum — 2100% overhead. For a 1500-byte packet, it's only 1.3% overhead. This is why UDP wins for small, frequent packets like voice samples (every 20ms = 50 packets/sec).

🔒 Why 3-Way? Why Not 2-Way?
A 2-way handshake (SYN → SYN+ACK) would establish the connection but the client never confirms it received the server's response. The server would have no way to know if the client is actually ready. The 3rd step (ACK) solves this — both sides confirm they can send and receive before any data flows. This prevents "half-open" connections from wasting server resources.
⏱️ TCP State Machine — All States
CLOSED LISTEN SYN_SENT SYN_RECEIVED ESTABLISHED FIN_WAIT_1 FIN_WAIT_2 CLOSE_WAIT CLOSING LAST_ACK TIME_WAIT
TIME_WAIT is crucial — the client waits 2×MSL (60–240 seconds) before final CLOSED to ensure the last ACK arrived. This prevents a reused port from getting stale packets.

🧠 Jitter Buffer — How Calls Handle Lost Packets
Your phone doesn't play audio as it arrives. It buffers 40–200ms of audio ahead, so if a packet arrives late (jitter), there's still audio to play. If a packet is lost entirely, the codec uses Packet Loss Concealment (PLC) — it extrapolates what the audio probably sounded like (often imperceptible for speech). This is why calls sometimes sound slightly robotic: PLC is doing its job.

Section 07

Advanced TCP Mechanics

What makes TCP's reliability work under the hood. These are the mechanisms that separate TCP from UDP at the engineering level.

Retransmission — What Happens When a Packet is Lost

TCP detects loss via timeout (RTO) or 3 Duplicate ACKs (Fast Retransmit). When the sender doesn't receive an ACK within the Retransmission Timeout, it re-sends the packet.

RTO Calculation (How TCP Estimates Timeout)

ALGORITHM rtt_estimation.pseudo 
// Jacobson/Karels Algorithm (RFC 6298)

// On each ACK received:
SRTT = (1 - 0.125) * SRTT + 0.125 * R   // Smoothed RTT
RTTVAR = (1 - 0.25) * RTTVAR + 0.25 * |SRTT - R|  // Variance
RTO = SRTT + max(1ms, 4 * RTTVAR)

// On timeout (exponential backoff):
RTO = RTO * 2   // Double it each time. Max: 60s
// This is called "Karn's Algorithm" - don't use retransmit RTT for estimation

Sliding Window — How TCP Stays Fast

Instead of waiting for each packet's ACK before sending the next (stop-and-wait), TCP sends multiple packets within a "window" simultaneously. The window slides forward as ACKs arrive.

Window size: 4 segments
Segment buffer (10 segments total)
Waiting In-flight ACK'd
📊 Bandwidth = Window Size / RTT
If your window is 64KB and your RTT is 100ms, your max throughput is 64KB / 0.1s = 640 KB/s (5.12 Mbps). Even on a 1 Gbps link, a small window on a high-latency connection bottlenecks you. This is the "Bandwidth-Delay Product" problem. Solutions: TCP window scaling (RFC 7323) allows windows up to 1GB.

Congestion Control — TCP Being a Good Network Citizen

TCP won't flood the network. It starts slow, probes for bandwidth, and backs off when it detects congestion. This is why TCP is "fair" — all connections sharing a link converge to equal bandwidth.

Slow Start
Starts with cwnd=1 MSS. Doubles every RTT until it hits ssthresh or a loss. "Exponential" growth initially. 
// cwnd = congestion window
RTT1: cwnd = 1 MSS = 1460B
RTT2: cwnd = 2 MSS = 2920B
RTT3: cwnd = 4 MSS = 5840B
RTT4: cwnd = 8 MSS = 11680B
// Until ssthresh reached → CA
Congestion Avoidance (AIMD)
Additive Increase: +1 MSS per RTT. On loss: Multiplicative Decrease, halve the window. This is "AIMD" — it converges to fair share. 
// After ssthresh:
cwnd += (MSS * MSS) / cwnd
// ≈ +1 MSS per RTT

// On packet loss (timeout):
ssthresh = cwnd / 2
cwnd = 1  // back to slow start
Fast Retransmit
3 duplicate ACKs = probably a single packet loss, not full congestion. Retransmit immediately without waiting for timeout. Then: cwnd = cwnd/2 (not back to 1).
UDP Has None of This
UDP sends at whatever rate the application wants. This is why a badly written UDP app can "starve" TCP flows on the same link. Applications using UDP must implement their own congestion control (like QUIC/WebRTC does).

Nagle's Algorithm — Batching Small Writes

Without Nagle, each keystroke in SSH would send 41 bytes (20B IP + 20B TCP + 1B data). Nagle buffers small writes into larger packets, drastically reducing overhead.

ALGORITHMnagle.pseudo 
if (data_to_send AND outstanding_unacked_data > 0):
    // Buffer it — wait for ACK before sending
    buffer(data_to_send)
    wait_for_ack()
    send(buffered_data_combined)
else:
    // No outstanding data — send immediately
    send(data_to_send)

// Disable Nagle for real-time needs:
// setsockopt(sock, IPPROTO_TCP, TCP_NODELAY, 1, ...)
// Redis, SSH, game servers all disable Nagle
⚠️ Nagle + Delayed ACK = 200ms Hell
Linux by default delays ACKs by up to 40ms (to batch them). Nagle waits for ACK before sending more. When both are active: sender waits for ACK → receiver delays ACK → 40ms stall. Multiplied across many packets in a game or trading system, this kills performance. Solution: TCP_NODELAY.

PYTHON TCP SERVER — What Every Line Does
PYTHON tcp_server.py 
import socket
import threading

# ── Step 1: Create a socket ──────────────────────────────────
# AF_INET = IPv4 address family
# SOCK_STREAM = TCP (byte stream, reliable, ordered)
# SOCK_DGRAM would be UDP instead
server_socket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)

# Allow reuse of port immediately after restart (avoids TIME_WAIT delay)
server_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)

# ── Step 2: Bind to address/port ─────────────────────────────
# '' = all interfaces, 8080 = port
# The OS now owns port 8080 for this process
server_socket.bind(('', 8080))

# ── Step 3: Listen (server enters LISTEN state) ───────────────
# backlog=5 = max queued connections before refusing
server_socket.listen(5)
print("Server listening on :8080")

def handle_client(conn, addr):
    print(f"New connection from {addr}")
    # Connection is now ESTABLISHED
    # TCP handshake already happened inside accept()
    
    try:
        while True:
            # ── Step 5: Receive data ──────────────────────────
            # recv(1024) = read up to 1024 bytes
            # Blocks until data arrives (TCP is stream-based)
            # Returns b'' (empty bytes) when connection closes
            data = conn.recv(1024)
            
            if not data:
                break  # Client sent FIN (graceful close)
            
            message = data.decode('utf-8')
            print(f"Received: {message}")
            
            # ── Step 6: Send response ────────────────────────
            # TCP automatically: segments, sequences, retransmits
            response = f"Echo: {message}".encode('utf-8')
            conn.send(response)
            
    except ConnectionResetError:
        print(f"Client {addr} disconnected abruptly")
    finally:
        # ── Step 7: Close (sends FIN, enters FIN_WAIT) ───
        conn.close()

# ── Step 4: Accept connections ────────────────────────────────
while True:
    # Blocks until client connects
    # Returns AFTER 3-way handshake completes
    # conn = new socket for THIS client
    # addr = (ip, port) of client
    conn, addr = server_socket.accept()
    
    # Handle each client in a thread (don't block)
    threading.Thread(target=handle_client, args=(conn, addr)).start()
PYTHON tcp_client.py 
import socket

# ── Create socket (same as server) ───────────────────────────
client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)

# ── CONNECT = triggers 3-way handshake ───────────────────────
# OS sends SYN → receives SYN+ACK → sends ACK
# Returns only after ESTABLISHED state
# Raises ConnectionRefusedError if server not listening
client.connect(('127.0.0.1', 8080))
print("Connected! (handshake done)")

# ── Send data ────────────────────────────────────────────────
# TCP may buffer this (Nagle's algorithm)
# Use TCP_NODELAY to disable buffering for real-time
messages = ["Hello", "How are you", "Goodbye"]

for msg in messages:
    client.send(msg.encode('utf-8'))
    
    # ── Receive response ─────────────────────────────────────
    # IMPORTANT: TCP is a BYTE STREAM, not a message stream
    # recv(1024) might return PART of a message, or multiple messages
    # You need framing (length prefix or delimiter) in real apps
    response = client.recv(1024)
    print(f"Server: {response.decode()}")

# ── Close: sends FIN ─────────────────────────────────────────
client.close()

Sending: send("Hello") + send("World")

FIX — Length-prefixed framing:
import struct

def send_msg(sock, msg):
    msg_bytes = msg.encode('utf-8')
    # Prefix with 4-byte big-endian length
    header = struct.pack('>I', len(msg_bytes))
    sock.sendall(header + msg_bytes)

def recv_msg(sock):
    # Read exactly 4 bytes for the length header
    raw_len = recvall(sock, 4)
    msg_len = struct.unpack('>I', raw_len)[0]
    # Read exactly msg_len bytes
    return recvall(sock, msg_len).decode('utf-8')
PYTHON udp_server.py 
import socket

# ── SOCK_DGRAM = UDP ─────────────────────────────────────────
# No handshake. No state machine. Just bind and receive.
udp_sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
udp_sock.bind(('', 9000))
print("UDP server on :9000")

while True:
    # ── recvfrom = receive datagram ──────────────────────────
    # Returns the COMPLETE datagram (UDP preserves boundaries)
    # No partial reads like TCP! Each call = 1 datagram
    # addr = (ip, port) of sender
    data, addr = udp_sock.recvfrom(65535)
    
    # Data might be corrupt (checksum fail = kernel drops it)
    # Data might be out of order
    # Data might be duplicated
    # All the app's problem to handle!
    
    msg = data.decode('utf-8')
    print(f"Got from {addr}: {msg}")
    
    # ── sendto = send datagram to specific address ───────────
    # No connection — must specify destination each time
    # This might arrive. It might not. That's UDP.
    udp_sock.sendto(f"Ack: {msg}".encode(), addr)

UDP for Real-Time Audio (simplified RTP-like)
────────────────────────────────────────────────────────────────
import struct, time

def build_rtp_packet(seq_num, timestamp, payload):
    # Simplified RTP header: seq(2) + ts(4) + ssrc(4) + payload
    header = struct.pack('>HII', seq_num, timestamp, 0x12345678)
    return header + payload

def send_audio_stream(sock, addr, audio_chunks):
    for i, chunk in enumerate(audio_chunks):
        pkt = build_rtp_packet(
            seq_num=i,                          # For reordering
            timestamp=i * 160,                 # 160 samples @ 8kHz = 20ms
            payload=chunk
        )
        sock.sendto(pkt, addr)
        # No wait. No ACK. Keep going at 50 packets/sec.
        time.sleep(0.02)  # 20ms intervals

def simple_dns_query(hostname):

JAVASCRIPT messenger_server.js (Node.js) 
const WebSocket = require('ws');
const server = new WebSocket.Server({ port: 8080 });

// WebSocket = HTTP Upgrade → TCP persistent connection
// Browser opens 1 TCP connection, keeps it open forever
// Server can PUSH data to client without client polling

const clients = new Map(); // userId → socket

server.on('connection', (ws, req) => {
    // At this point: TCP handshake DONE + WebSocket upgrade DONE
    // ws is the persistent TCP connection for this user
    
    let userId = null;
    
    ws.on('message', (rawData) => {
        const msg = JSON.parse(rawData);  // Parse frame from TCP stream
        
        switch(msg.type) {
            case 'auth':
                // Register this TCP connection with a user ID
                userId = msg.userId;
                clients.set(userId, ws);
                ws.send(JSON.stringify({ type: 'auth_ok' }));
                break;
                
            case 'message':
                // Route message to recipient
                // TCP ensures: delivery + ordering + no corruption
                const recipientWs = clients.get(msg.to);
                
                if (recipientWs?.readyState === WebSocket.OPEN) {
                    // Push directly over their TCP connection
                    recipientWs.send(JSON.stringify({
                        type: 'message',
                        from: userId,
                        text: msg.text,
                        id: msg.id,
                        timestamp: Date.now()
                    }));
                    
                    // Send delivery confirmation to sender
                    ws.send(JSON.stringify({
                        type: 'delivered',
                        msgId: msg.id
                    }));
                } else {
                    // Recipient offline → store in DB, send push notification
                    storeOfflineMessage(msg);
                    sendPushNotification(msg.to, msg.text);
                }
                break;
        }
    });
    
    ws.on('close', () => {
        // TCP FIN received — user disconnected
        clients.delete(userId);
        broadcastStatus(userId, 'offline');
    });
    
    // Heartbeat: TCP doesn't detect dead connections fast
    // Solution: ping every 30s, disconnect if no pong
    const heartbeat = setInterval(() => {
        if (ws.readyState === WebSocket.OPEN) ws.ping();
    }, 30000);
});

Section 09

End-to-End: "Send Message" Full Journey

What actually happens when you hit send on a WhatsApp message. Every layer. Every millisecond.

1
Application Layer — Your App
You type "Hey!" and tap Send. The app serializes it to JSON (or Protocol Buffers), encrypts with Signal Protocol (E2E encryption), and calls WebSocket.send(data).
2
WebSocket → TLS → TCP (Transport Layer)
The browser/app wraps your message in a WebSocket frame, hands it to TLS (encrypts it), which hands it to TCP. TCP segments it, assigns sequence numbers, starts a retransmission timer. The OS copies it into the kernel's send buffer.
3
TCP Segment Leaves Your Device
Your kernel writes the TCP segment into an IP packet (adds source/dest IP). The network card converts it to electrical/radio signals. On WiFi: frames go to your router via 802.11. The router forwards via your ISP.
4
Routing — Many Hops to Server
Your packet hops through 10–20 routers. Each router reads the IP header, looks up its routing table, and forwards. None of them care about TCP or your message content — IP is dumb delivery. The TCP connection is end-to-end only between your device and WhatsApp's server.
5
WhatsApp's Server Receives — TCP ACK
Server's NIC receives the packet. The kernel reads the TCP sequence number, writes data to the socket's receive buffer, and sends an ACK back. Your device's TCP layer marks the segment as delivered and cancels the retransmission timer.
6
Server Routes to Recipient
The server decrypts (envelope), reads "to: Bob", finds Bob's WebSocket connection (another TCP connection, persistent), and calls bobSocket.send(message). The message travels back down through TCP → IP → Network to Bob's device.
7
Bob's Device Receives & Shows Message
Bob's TCP layer receives, ACKs, delivers to WebSocket, which delivers to the app. App decrypts (Signal E2E), shows the message, sends a "delivered" receipt back (another TCP packet). You see the double tick. Total time: 50–300ms.
