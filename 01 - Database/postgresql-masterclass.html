Database Fundamentals

ACID Properties

ACID is the set of properties that guarantee database transactions are processed reliably. Every serious database — including PostgreSQL — upholds these four principles.

PropertyMeaningExample
AtomicityAll steps in a transaction succeed, or none doMoney transfer: debit + credit happen together or neither does
ConsistencyDB goes from one valid state to anotherConstraints and rules are never violated
IsolationConcurrent transactions don't interfereTwo users booking the last seat — only one wins
DurabilityCommitted data survives crashesPayment confirmed → it stays, even after power failure
📌 Key Insight

PostgreSQL is one of the most ACID-compliant databases available. This is why it's chosen for financial systems, healthcare, and anywhere data integrity is non-negotiable.

CAP Theorem

In a distributed system, you can only guarantee 2 of 3 properties simultaneously:

🔵 Consistency
Every read receives the most recent write or an error
🟢 Availability
Every request gets a response (not necessarily latest data)
🟡 Partition Tolerance
System continues despite network splits

PostgreSQL is a CP system — it prioritizes Consistency over Availability during network partitions.

Availability, Consistency & Security Concepts
ConceptWhat It Means in PostgreSQL
High Availability (HA)Replication, failover, read replicas — keep DB running even if primary fails
ReplicationPhysical streaming replication (WAL-based), logical replication for selective tables
Point-in-Time RecoveryRestore DB to any moment using WAL logs — like a time machine for data
Connection SecuritySSL/TLS encryption in transit; pg_hba.conf controls who can connect
Data at RestOS-level or tablespace-level encryption (e.g., pgcrypto, disk encryption)
Role-Based Access ControlFine-grained GRANT/REVOKE on databases, schemas, tables, columns, rows
Relational vs NoSQL — When Each Shines

🐘 Relational (PostgreSQL)

  • Strong data relationships
  • Complex queries & reporting
  • ACID transactions required
  • Schema stability
  • Financial / medical data
  • Multi-table joins needed

🍃 NoSQL

  • Unstructured / flexible schema
  • Horizontal scale at massive volume
  • Event logs, time series
  • Document storage (JSON-heavy)
  • Cache / session stores
  • Graph relationships
💡 Pro Tip
PostgreSQL supports JSON/JSONB natively — you often don't need a separate NoSQL DB. It can act as both!

Why PostgreSQL?

PostgreSQL (aka "Postgres") is a 35+ year old open-source RDBMS that has become the go-to choice for serious backend development. It's used by Instagram, GitHub, Shopify, Discord, and thousands more.

When to pick PostgreSQL
Your data has relationships · You need complex queries · Data integrity is critical · You need advanced features like RLS, FTS, PostGIS, or JSONB · You want one DB that can do everything
📌 Notes

PostgreSQL's MVCC (Multi-Version Concurrency Control) means readers never block writers and writers never block readers. This is huge for performance in real apps with concurrent users.

sudo apt update

# 2. Install PostgreSQL (latest stable)
sudo apt install -y postgresql postgresql-contrib

# 3. Start and enable service
sudo systemctl start postgresql
sudo systemctl enable postgresql

# 4. Check status
sudo systemctl status postgresql

# 5. Access the postgres shell as superuser
sudo -u postgres psql

# 6. Set a password for postgres user
sudo -u postgres psql -c "ALTER USER postgres PASSWORD 'yourpassword';"

# 7. Create a new database and user
sudo -u postgres createdb myapp
sudo -u postgres createuser --interactive myuser

Docker PostgreSQL Setup

Docker is the best way to run Postgres in development — isolated, reproducible, easy to reset. Use Docker Compose for multi-container apps.

Quick Run (one-liner)
Docker run
bash
# Run Postgres with named volume (data persists even if container stops)
docker run -d \
  --name my-postgres \
  -e POSTGRES_USER=admin \
  -e POSTGRES_PASSWORD=secret123 \
  -e POSTGRES_DB=myapp \
  -p 5432:5432 \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16

# Connect into it
docker exec -it my-postgres psql -U admin -d myapp

# Stop / start
docker stop my-postgres
docker start my-postgres
docker-compose.yml (Recommended for Projects)
docker-compose.yml
yaml
version: '3.9'

services:
  postgres:
    image: postgres:16
    container_name: myapp_postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${DB_USER:-admin}
      POSTGRES_PASSWORD: ${DB_PASSWORD:-secret123}
      POSTGRES_DB: ${DB_NAME:-myapp}
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data   # named volume: data survives restarts
      - ./init:/docker-entrypoint-initdb.d # auto-runs .sql files on first start
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
      interval: 10s
      timeout: 5s
      retries: 5

  pgadmin:                                 # optional GUI tool
    image: dpage/pgadmin4
    container_name: myapp_pgadmin
    environment:
      PGADMIN_DEFAULT_EMAIL: admin@example.com
      PGADMIN_DEFAULT_PASSWORD: admin
    ports:
      - "8080:80"
    depends_on:
      - postgres

volumes:
  pgdata:                                   # Docker manages this volume
Usage commands
bash
# Start all services
docker compose up -d

# View logs
docker compose logs -f postgres

# Connect to DB
docker compose exec postgres psql -U admin -d myapp

# Stop (data preserved)
docker compose down

# Stop AND delete all data (DANGEROUS!)
docker compose down -v

# Backup from Docker
docker compose exec postgres pg_dump -U admin myapp > backup.sql

# Restore into Docker
cat backup.sql | docker compose exec -T postgres psql -U admin -d myapp
🚨 Data Loss Warning
Never run docker compose down -v on production — the -v flag deletes named volumes and ALL your data. Always use docker compose down (without -v) to stop safely.
📌 Notes

Always use named volumes (like pgdata:/var/...), not bind mounts for Postgres data on Windows/Mac hosts — it prevents permission errors and performance issues.

const { Pool } = require('pg');

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  ssl: { rejectUnauthorized: false }  // required for Supabase

async function getUsers() {
  const { rows } = await pool.query('SELECT * FROM users LIMIT 10');

Remote Server PostgreSQL

Setup on a VPS (Ubuntu)
Remote server setup
bash
# 1. Install postgres on the server
sudo apt update && sudo apt install -y postgresql

# 2. Create a database and user
sudo -u postgres psql -c "CREATE USER appuser WITH PASSWORD 'strongpass';"
sudo -u postgres psql -c "CREATE DATABASE myappdb OWNER appuser;"
sudo -u postgres psql -c "GRANT ALL PRIVILEGES ON DATABASE myappdb TO appuser;"

# 3. Allow remote connections in postgresql.conf
sudo nano /etc/postgresql/16/main/postgresql.conf
# Change: listen_addresses = 'localhost'  →  listen_addresses = '*'

# 4. Add auth rule in pg_hba.conf
sudo nano /etc/postgresql/16/main/pg_hba.conf
# Add line (replace 0.0.0.0/0 with your app server IP for security):
# host  myappdb  appuser  0.0.0.0/0  scram-sha-256

# 5. Restart postgres
sudo systemctl restart postgresql

# 6. Open firewall (UFW)
sudo ufw allow from YOUR_APP_IP to any port 5432

# 7. Connect from your machine
psql -h YOUR_SERVER_IP -U appuser -d myappdb
SSL Connection Setup
Enable SSL
bash
# SSL is on by default in postgres 16 — generate certificates if needed
openssl req -new -x509 -days 365 -nodes \
  -out /etc/ssl/certs/server.crt \
  -keyout /etc/ssl/private/server.key

# Set permissions
chmod 600 /etc/ssl/private/server.key
chown postgres:postgres /etc/ssl/private/server.key

# postgresql.conf:
# ssl = on
# ssl_cert_file = '/etc/ssl/certs/server.crt'
# ssl_key_file  = '/etc/ssl/private/server.key'

# Connect with SSL
psql "postgresql://appuser:pass@server_ip/myappdb?sslmode=require"
Key Things to NOT Lose Data
💾
Automated Backups
Set up daily pg_dump via cron. Store backups off-server (S3, etc.)
📡
WAL Archiving
Archive WAL segments to allow Point-in-Time Recovery
🔄
Replication
Set up a hot standby replica for automatic failover
📊
Monitoring
Use pg_stat_activity, pgBadger, or Prometheus + Grafana
🚨 Never Do This on Production
Never allow pg_hba.conf to have trust auth for remote connections. Never open port 5432 to 0.0.0.0/0 without firewall rules. Always use scram-sha-256 or md5 auth with SSL.

DDL — Tables, Schemas & Databases

DDL (Data Definition Language) defines the structure of your database. These commands create, modify, and delete database objects.

Schemas — Namespacing Your Database
Schema management
sql
-- Create schemas to organize tables (like folders)
CREATE SCHEMA app;
CREATE SCHEMA auth;
CREATE SCHEMA analytics;

-- Create table inside a schema
CREATE TABLE app.users ( id UUID PRIMARY KEY, name TEXT );
CREATE TABLE auth.sessions ( token TEXT PRIMARY KEY );

-- Set search path (default schema to look in)
SET search_path TO app, public;

-- Show current search path
SHOW search_path;

-- Drop a schema and everything in it

-- List all schemas

CREATE TABLE — Full Syntax
CREATE TABLE syntax
sql
CREATE TABLE products (
  -- Primary Key (UUID preferred in modern apps)
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  -- Text columns
  name          TEXT NOT NULL,
  slug          TEXT UNIQUE NOT NULL,
  description   TEXT,

  -- Numeric columns
  price         NUMERIC(10,2) NOT NULL CHECK (price >= 0),
  stock         INTEGER NOT NULL DEFAULT 0 CHECK (stock >= 0),

  -- Foreign key
  category_id   UUID REFERENCES categories(id) ON DELETE SET NULL,

  -- Status with enum
  status        TEXT DEFAULT 'active' CHECK (status IN ('active','inactive','archived')),

  -- JSONB for flexible data
  attributes    JSONB DEFAULT '{}',

  -- Audit columns (essential)
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Add a table-level constraint (compound unique)
ALTER TABLE products
  ADD CONSTRAINT unique_product_per_store UNIQUE (store_id, slug);
ALTER TABLE — Modifying Structure
ALTER TABLE
sql
-- Add a column
ALTER TABLE products ADD COLUMN weight_kg NUMERIC(8,3);

-- Drop a column
ALTER TABLE products DROP COLUMN weight_kg;

-- Rename a column
ALTER TABLE products RENAME COLUMN slug TO url_slug;

-- Change column type (careful with existing data!)
ALTER TABLE products ALTER COLUMN stock TYPE BIGINT;

-- Set a default value
ALTER TABLE products ALTER COLUMN status SET DEFAULT 'active';

-- Drop default
ALTER TABLE products ALTER COLUMN status DROP DEFAULT;

-- Add NOT NULL constraint
ALTER TABLE products ALTER COLUMN name SET NOT NULL;

-- Rename the table
ALTER TABLE products RENAME TO catalog_items;

-- Drop table (with all dependent objects)
DROP TABLE products CASCADE;

-- Drop only if it exists (safe)
DROP TABLE IF EXISTS products;
📌 Notes — Schema Versioning

In real projects, never run raw ALTER TABLE on production manually. Use migration tools like Flyway, Liquibase, Prisma Migrate, or Supabase migrations. This keeps schema changes version-controlled and repeatable.

DML — CRUD Operations

INSERT
INSERT examples
sql
-- Single row insert
INSERT INTO users (username, email, age)
VALUES ('alice', 'alice@example.com', 28);

-- Multi-row insert (faster than multiple single inserts)
INSERT INTO users (username, email)
VALUES
  ('bob',   'bob@example.com'),
  ('carol', 'carol@example.com'),
  ('dave',  'dave@example.com');

-- INSERT ... RETURNING (get back the inserted row)
INSERT INTO users (username, email)
VALUES ('eve', 'eve@example.com')
RETURNING id, created_at;

-- INSERT from SELECT
INSERT INTO archive_users (username, email)
SELECT username, email FROM users WHERE is_active = FALSE;

-- UPSERT: insert or update on conflict
INSERT INTO users (email, username)
VALUES ('alice@example.com', 'alice_new')
ON CONFLICT (email)
DO UPDATE SET
  username = EXCLUDED.username,
  updated_at = NOW();

-- ON CONFLICT DO NOTHING (skip duplicates)
INSERT INTO users (email, username)
VALUES ('bob@example.com', 'bob')
ON CONFLICT (email) DO NOTHING;
SELECT — Querying Data
SELECT examples
sql
-- Basic select
SELECT * FROM users;
SELECT id, username, email FROM users;

-- WHERE filtering
SELECT * FROM users
WHERE is_active = TRUE
  AND age BETWEEN 18 AND 35
  AND email LIKE '%@gmail.com';

-- IN / NOT IN
SELECT * FROM users WHERE id IN ('uuid1', 'uuid2', 'uuid3');

-- NULL checks
SELECT * FROM users WHERE deleted_at IS NULL;
SELECT * FROM users WHERE phone IS NOT NULL;

-- ORDER BY, LIMIT, OFFSET (pagination)
SELECT * FROM products
ORDER BY created_at DESC
LIMIT 20 OFFSET 40;   -- page 3 (0-indexed)

-- Aggregates
SELECT
  COUNT(*) AS total_users,
  AVG(age) AS avg_age,
  MIN(age) AS youngest,
  MAX(age) AS oldest,
  SUM(balance) AS total_balance
FROM users
WHERE is_active = TRUE;

-- GROUP BY + HAVING
SELECT
  status,
  COUNT(*) AS count,
  SUM(total) AS revenue
FROM orders
GROUP BY status
HAVING COUNT(*) > 5
ORDER BY revenue DESC;

-- DISTINCT
SELECT DISTINCT country FROM users ORDER BY country;
UPDATE & DELETE
UPDATE and DELETE
sql
-- Basic UPDATE
UPDATE users
SET is_active = FALSE, updated_at = NOW()
WHERE id = 'some-uuid';

-- UPDATE with RETURNING
UPDATE products
SET price = price * 1.10   -- 10% price increase
WHERE category_id = 'cat-uuid'
RETURNING id, name, price;

-- UPDATE from another table (UPDATE ... FROM)
UPDATE orders o
SET customer_name = u.username
FROM users u
WHERE o.user_id = u.id;

-- Soft delete (preferred pattern)
UPDATE users
SET deleted_at = NOW()
WHERE id = 'some-uuid';

-- Hard delete
DELETE FROM users WHERE id = 'some-uuid';

-- DELETE with RETURNING
DELETE FROM sessions
WHERE expires_at < NOW()
RETURNING id, user_id;

-- TRUNCATE (fastest way to delete all rows)
TRUNCATE TABLE temp_data;
TRUNCATE TABLE orders RESTART IDENTITY CASCADE;
⚠️ Golden Rule
Always add a WHERE clause to UPDATE and DELETE. Before running on production, run the same WHERE with a SELECT first to confirm what you'll affect. Wrap in a transaction so you can ROLLBACK if needed.

Constraints

Constraints enforce data integrity at the database level — the last line of defense regardless of what the application does.

All Constraint Types
Constraints reference
sql
CREATE TABLE employees (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),  -- PK: unique + not null
  email       TEXT UNIQUE NOT NULL,                         -- UNIQUE + NOT NULL
  username    TEXT NOT NULL,                                 -- NOT NULL
  salary      NUMERIC(10,2) CHECK (salary > 0),             -- CHECK constraint
  dept_id     UUID REFERENCES departments(id),             -- FOREIGN KEY (inline)
  manager_id  UUID REFERENCES employees(id),              -- Self-referencing FK
  role        TEXT DEFAULT 'employee'                       -- DEFAULT value
);

-- Named constraints (best practice for easier error messages)
CREATE TABLE orders (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    UUID NOT NULL,
  total      NUMERIC(10,2),
  quantity   INTEGER,

  -- Named FK constraint
  CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES users(id),

  -- Named CHECK
  CONSTRAINT chk_positive_total CHECK (total >= 0),
  CONSTRAINT chk_positive_qty  CHECK (quantity > 0),

  -- Compound UNIQUE
  CONSTRAINT uq_user_order_ref UNIQUE (user_id, reference_code)
);
Foreign Key ON DELETE / ON UPDATE Behaviors
ActionWhat HappensUse When
RESTRICTError if parent has childrenDefault safety — prevents orphans
CASCADEDelete/update children automaticallyComments/likes tied to a post — delete post → delete all
SET NULLSet FK column to NULLOptional relationship — product still exists if category deleted
SET DEFAULTSet FK to its default valueRare — reassign to a "default" parent
NO ACTIONLike RESTRICT but deferredWhen you want deferred constraint checking
FK actions
sql
-- CASCADE: deleting user deletes all their orders
CONSTRAINT fk_orders_user FOREIGN KEY (user_id)
  REFERENCES users(id)
  ON DELETE CASCADE
  ON UPDATE CASCADE

-- SET NULL: keep product even if category deleted
CONSTRAINT fk_product_category FOREIGN KEY (category_id)
  REFERENCES categories(id)
  ON DELETE SET NULL

-- Add FK to existing table
ALTER TABLE orders
  ADD CONSTRAINT fk_orders_user
  FOREIGN KEY (user_id) REFERENCES users(id)
  ON DELETE CASCADE;

📌 Notes

Window Functions

Window functions perform calculations across a set of rows related to the current row, without collapsing them into groups. They're one of PostgreSQL's most powerful features for analytics.

Syntax & Core Functions
Window function syntax
sql
-- General syntax:
-- function_name() OVER (PARTITION BY col ORDER BY col ROWS/RANGE frame)

-- ROW_NUMBER: rank within each partition
SELECT
  username,
  department,
  salary,
  ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rank_in_dept
FROM employees;

-- RANK vs DENSE_RANK (ties)
SELECT
  username, salary,
  RANK()       OVER (ORDER BY salary DESC) AS rank,        -- 1,2,2,4
  DENSE_RANK() OVER (ORDER BY salary DESC) AS dense_rank  -- 1,2,2,3
FROM employees;

-- LAG / LEAD: access previous/next row values
SELECT
  month,
  revenue,
  LAG(revenue, 1) OVER (ORDER BY month) AS prev_month_revenue,
  revenue - LAG(revenue, 1) OVER (ORDER BY month) AS growth
FROM monthly_revenue;

-- Running total (cumulative sum)
SELECT
  created_at::DATE AS date,
  COUNT(*) AS daily_signups,
  SUM(COUNT(*)) OVER (ORDER BY created_at::DATE) AS cumulative_users
FROM users
GROUP BY created_at::DATE;

-- Moving average (7-day)
SELECT
  date,
  revenue,
  AVG(revenue) OVER (
    ORDER BY date
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ) AS moving_avg_7d
FROM daily_revenue;

-- NTILE: split into N buckets (e.g. quartiles)
SELECT
  username, total_spent,
  NTILE(4) OVER (ORDER BY total_spent) AS quartile
FROM user_stats;

-- FIRST_VALUE / LAST_VALUE
SELECT
  department, username, salary,
  FIRST_VALUE(salary) OVER (
    PARTITION BY department ORDER BY salary DESC
  ) AS top_salary_in_dept
FROM employees;

CTEs & Subqueries

Common Table Expressions (CTEs)
CTE syntax and examples
sql
-- Basic CTE (WITH clause)
WITH active_users AS (
  SELECT id, username, email
  FROM users
  WHERE is_active = TRUE AND deleted_at IS NULL
)
SELECT u.username, COUNT(o.id) AS order_count
FROM active_users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.username;

-- Multiple CTEs chained
WITH
  monthly_orders AS (
    SELECT
      DATE_TRUNC('month', created_at) AS month,
      SUM(total) AS revenue
    FROM orders
    WHERE status = 'delivered'
    GROUP BY 1
  ),
  with_growth AS (
    SELECT
      month, revenue,
      LAG(revenue) OVER (ORDER BY month) AS prev_revenue
    FROM monthly_orders
  )
SELECT
  month,
  revenue,
  ROUND((revenue - prev_revenue) / prev_revenue * 100, 2) AS growth_pct
FROM with_growth;

-- Recursive CTE: traverse a hierarchy (org chart, category tree)
WITH RECURSIVE category_tree AS (
  -- Base case: top-level categories
  SELECT id, name, parent_id, 0 AS depth, name::text AS path
  FROM categories
  WHERE parent_id IS NULL

  UNION ALL

  -- Recursive case: children
  SELECT c.id, c.name, c.parent_id,
         ct.depth + 1,
         ct.path || ' > ' || c.name
  FROM categories c
  JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT path, depth FROM category_tree ORDER BY path;
Subqueries
Subquery patterns
sql
-- Scalar subquery (returns single value)
SELECT username,
  (SELECT COUNT(*) FROM orders WHERE user_id = u.id) AS order_count
FROM users u;

-- EXISTS subquery (fast membership check)
SELECT * FROM users u
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.user_id = u.id AND o.total > 500
);

-- IN with subquery
SELECT * FROM products
WHERE category_id IN (
  SELECT id FROM categories WHERE name = 'Electronics'
);

-- Derived table (subquery in FROM)
SELECT dept, avg_salary
FROM (
  SELECT department AS dept, AVG(salary) AS avg_salary
  FROM employees
  GROUP BY department
) dept_stats
WHERE avg_salary > 60000;
📌 CTE vs Subquery

Use CTEs when: the same result is referenced multiple times, readability matters, or you need recursion. Use subqueries for simple one-time use. In PostgreSQL 12+, CTEs are inlined by default (same performance as subqueries). Use WITH ... AS MATERIALIZED to force materialization when needed.

Transactions

Transactions group multiple SQL statements into a single unit — either all succeed or all fail (atomicity). This is fundamental for data integrity.

Transaction Syntax
Transactions
sql
-- Bank transfer example
BEGIN;   -- or START TRANSACTION

  UPDATE accounts
  SET balance = balance - 500
  WHERE id = 'sender-id';

  UPDATE accounts
  SET balance = balance + 500
  WHERE id = 'receiver-id';

  -- Check no one went negative
  DO $$
  BEGIN
    IF EXISTS (SELECT 1 FROM accounts WHERE balance < 0) THEN
      RAISE EXCEPTION 'Insufficient funds';
    END IF;
  END
  $$;

COMMIT;  -- make permanent if all good
-- or ROLLBACK; to undo everything

-- SAVEPOINT: partial rollback
BEGIN;
  INSERT INTO orders (...) VALUES (...);
  SAVEPOINT after_order;

  INSERT INTO payments (...) VALUES (...);
  -- if this fails, we can rollback to savepoint only:
  ROLLBACK TO SAVEPOINT after_order;

COMMIT;

⚠️ Deadlocks
Deadlocks occur when two transactions each hold a lock the other needs. PostgreSQL detects and resolves them by killing one transaction. Prevent them by: always acquiring locks in the same order, keeping transactions short, using SELECT ... FOR UPDATE SKIP LOCKED for job queues.

Index creation
sql
-- Basic B-tree index
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- Composite index (column order matters!)
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
-- ↑ Can be used for queries on (user_id) or (user_id, status)
--   but NOT for queries on (status) alone

-- Unique index
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- Partial index (index only a subset of rows)
CREATE INDEX idx_orders_pending ON orders(created_at)
  WHERE status = 'pending';
-- Much smaller and faster — only indexes pending orders

-- Expression / functional index
CREATE INDEX idx_users_email_lower ON users(LOWER(email));

CREATE INDEX idx_users_metadata ON users USING gin(metadata);

CREATE INDEX idx_products_fts ON products

-- PL/pgSQL function with logic
CREATE OR REPLACE FUNCTION transfer_funds(
  p_from_id  UUID,
  p_to_id    UUID,
  p_amount   NUMERIC
)
RETURNS BOOLEAN
LANGUAGE plpgsql
AS $$
DECLARE
  v_balance NUMERIC;
BEGIN
  -- Check balance
  SELECT balance INTO v_balance
  FROM accounts WHERE id = p_from_id FOR UPDATE;

  IF v_balance < p_amount THEN
    RAISE EXCEPTION 'Insufficient funds: balance is %', v_balance;
  END IF;

  -- Deduct from sender
  UPDATE accounts SET balance = balance - p_amount WHERE id = p_from_id;

  -- Add to receiver
  UPDATE accounts SET balance = balance + p_amount WHERE id = p_to_id;

  RETURN TRUE;

EXCEPTION WHEN OTHERS THEN
  RAISE;   -- re-raise the exception
  RETURN FALSE;
END;
$$;

-- Call the function
SELECT transfer_funds('from-uuid', 'to-uuid', 100.00);

-- Function returning a table (like a view with parameters)
CREATE OR REPLACE FUNCTION get_user_orders(p_user_id UUID, p_limit INTEGER DEFAULT 10)
RETURNS TABLE(order_id UUID, total NUMERIC, status TEXT, created_at TIMESTAMPTZ)
LANGUAGE SQL STABLE
AS $$
  SELECT id, total, status, created_at
  FROM orders
  WHERE user_id = p_user_id
  ORDER BY created_at DESC
  LIMIT p_limit;
$$;

Triggers

Triggers automatically execute a function in response to a table event (INSERT, UPDATE, DELETE). They're perfect for audit logging, auto-updating timestamps, enforcing complex business rules, and data synchronization.

-- Step 1: Create trigger FUNCTION
-- (must return trigger type)

-- 1A. Auto-update updated_at (most common trigger)
CREATE OR REPLACE FUNCTION update_updated_at_column()

BEGIN

-- Audit log: record every change to a table
CREATE TABLE audit_log (
  id          BIGSERIAL PRIMARY KEY,
  table_name  TEXT,
  operation   TEXT,     -- INSERT, UPDATE, DELETE
  old_data    JSONB,
  new_data    JSONB,
  changed_by  TEXT,     -- current_user
  changed_at  TIMESTAMPTZ DEFAULT NOW()
);

CREATE OR REPLACE FUNCTION audit_trigger_fn()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
  INSERT INTO audit_log (table_name, operation, old_data, new_data, changed_by)
  VALUES (
    TG_TABLE_NAME,
    TG_OP,                                            -- INSERT/UPDATE/DELETE
    CASE WHEN TG_OP != 'INSERT' THEN to_jsonb(OLD) END,
    CASE WHEN TG_OP != 'DELETE' THEN to_jsonb(NEW) END,
    current_user
  );
  RETURN COALESCE(NEW, OLD);
END;
$$;

-- Attach to any table
CREATE TRIGGER orders_audit
  AFTER INSERT OR UPDATE OR DELETE ON orders
  FOR EACH ROW EXECUTE FUNCTION audit_trigger_fn();

-- Keep a cached comment count on posts (performance optimization)

RETURNS TRIGGER

pg_cron is a PostgreSQL extension that lets you schedule SQL statements to run on a schedule — just like Unix cron, but inside your database.

pg_cron setup and usage

-- Run every night at 2am: clean expired sessions
SELECT cron.schedule(
  'clean-expired-sessions',

);

SELECT cron.schedule(
  'refresh-stats-mv',
  '*/5 * * * *',
  $$REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_revenue_mv$$
);

-- Run at midnight on the 1st of each month: archive old data

  'monthly-archive',
  '0 0 1 * *',

);

  '0 8 * * 1-5',

);

Roles & Privileges

PostgreSQL uses a unified role system for both users and groups. Roles can own objects, have login privileges, and be granted privileges on specific database objects.

Creating & Managing Roles
Role management
sql
-- Create a login role (user)
CREATE ROLE app_user LOGIN PASSWORD 'strongpassword';

-- Create a group role (no login)
CREATE ROLE readonly;
CREATE ROLE readwrite;
CREATE ROLE admin;

-- Add user to group role
GRANT readonly TO app_user;

-- Role attributes
CREATE ROLE superadmin
  LOGIN
  PASSWORD 'pass'
  SUPERUSER           -- bypass all permission checks
  CREATEDB            -- can create databases
  CREATEROLE          -- can create roles
  CONNECTION LIMIT 10  -- max concurrent connections
  VALID UNTIL '2025-12-31';  -- expiry

-- Alter a role
ALTER ROLE app_user PASSWORD 'newpassword';
ALTER ROLE app_user CONNECTION LIMIT 20;

-- Drop a role
DROP ROLE IF EXISTS app_user;

-- List all roles
SELECT rolname, rolsuper, rolcreatedb, rolcanlogin, rolconnlimit
FROM pg_roles
ORDER BY rolname;
GRANT & REVOKE
Granting privileges
sql
-- Grant database access
GRANT CONNECT ON DATABASE myapp TO readonly;

-- Grant schema usage
GRANT USAGE ON SCHEMA public TO readonly;

-- Grant table privileges
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO readwrite;

-- Grant on specific table
GRANT SELECT (id, username, email) ON users TO readonly;  -- column-level

-- Grant sequence (for auto-increment / serial)
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO readwrite;

-- Grant function execution
GRANT EXECUTE ON FUNCTION get_user_order_count(UUID) TO readonly;

-- Auto-grant on future tables (crucial!)
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO readonly;

ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO readwrite;

-- Revoke privileges
REVOKE DELETE ON users FROM readwrite;

-- Check what privileges a role has
SELECT grantee, table_name, privilege_type
FROM information_schema.role_table_grants
WHERE grantee = 'readonly';

Row Level Security (RLS)

RLS lets you control which rows a user can see or modify — not just which tables. It's the key to building secure multi-tenant applications and is a cornerstone of Supabase's security model.

RLS Fundamentals
Enabling & basic policies
sql
-- Step 1: Enable RLS on a table
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
-- Once enabled, users see ZERO rows unless a policy allows it

-- Step 2: Create policies

-- Policy: users can only see their own orders
CREATE POLICY users_own_orders
  ON orders
  FOR ALL          -- applies to SELECT, INSERT, UPDATE, DELETE
  TO app_user       -- which role this policy applies to
  USING (user_id = current_setting('app.user_id')::UUID);
  -- USING: filters rows for SELECT/UPDATE/DELETE

-- Separate INSERT check
CREATE POLICY users_insert_own_orders
  ON orders
  FOR INSERT
  TO app_user
  WITH CHECK (user_id = current_setting('app.user_id')::UUID);
  -- WITH CHECK: validates NEW row data on INSERT/UPDATE

-- Admins can see everything
CREATE POLICY admin_all_orders
  ON orders
  FOR ALL
  TO app_admin
  USING (TRUE);    -- no restriction

-- Set the app user context before queries
SET app.user_id = 'some-user-uuid';
SELECT * FROM orders;  -- only that user's orders returned
RLS with Supabase Auth
Supabase RLS patterns
sql
-- Supabase uses auth.uid() function for the logged-in user's UUID

-- Example: profiles table — users can only see/edit their own
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users can view own profile"
  ON profiles FOR SELECT
  USING (auth.uid() = user_id);

CREATE POLICY "Users can update own profile"
  ON profiles FOR UPDATE
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

CREATE POLICY "Users can insert own profile"
  ON profiles FOR INSERT
  WITH CHECK (auth.uid() = user_id);

-- Public read, owner write pattern (e.g. blog posts)
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Anyone can read published posts"
  ON posts FOR SELECT
  USING (status = 'published');

CREATE POLICY "Authors can manage own posts"
  ON posts FOR ALL
  USING (auth.uid() = author_id)
  WITH CHECK (auth.uid() = author_id);

-- Role-based: check user's role from a profiles table
CREATE POLICY "Admins can do everything"
  ON orders FOR ALL
  USING (
    EXISTS (
      SELECT 1 FROM profiles
      WHERE user_id = auth.uid()
        AND role = 'admin'
    )
  );

-- Organisation-scoped access (multi-tenant)
CREATE POLICY "Users access own org data"
  ON projects FOR ALL
  USING (
    org_id IN (
      SELECT org_id FROM org_members
      WHERE user_id = auth.uid()
    )
  );

-- View / drop policies
SELECT policyname, cmd, qual, with_check
FROM pg_policies
WHERE tablename = 'orders';

DROP POLICY IF EXISTS users_own_orders ON orders;

-- Bypass RLS for a role (e.g. migrations, superuser tasks)
ALTER ROLE app_migrations BYPASSRLS;
📌 RLS Performance Tip

Index the columns used in RLS policies (e.g. user_id, org_id). Without indexes, every RLS check does a sequential scan. Also, policies are evaluated per-row — keep USING expressions simple and fast.

Backup & Recovery

Data loss is catastrophic. Understand and implement multiple layers of backup — because the question is not if you'll need a restore, but when.

pg_dump — Logical Backups
pg_dump commands
bash
# Backup a single database (SQL format)
pg_dump -U postgres -d myapp -f myapp_backup.sql

# Backup in custom format (faster, supports parallel restore)
pg_dump -U postgres -d myapp -F c -f myapp_backup.dump

# Backup with compression
pg_dump -U postgres -d myapp | gzip > myapp_$(date +%Y%m%d_%H%M%S).sql.gz

# Backup specific tables only
pg_dump -U postgres -d myapp -t users -t orders -f partial_backup.sql

# Backup only schema (no data)
pg_dump -U postgres -d myapp --schema-only -f schema_only.sql

# Backup only data (no schema)
pg_dump -U postgres -d myapp --data-only -f data_only.sql

# Parallel backup (faster for large DBs, custom format required)
pg_dump -U postgres -d myapp -F d -j 4 -f myapp_parallel_backup/

# Backup ALL databases
pg_dumpall -U postgres -f all_databases.sql

# ──── RESTORE ────
# Restore from SQL file
psql -U postgres -d myapp_new -f myapp_backup.sql

# Restore from custom format
pg_restore -U postgres -d myapp_new -F c myapp_backup.dump

# Restore with parallel workers
pg_restore -U postgres -d myapp_new -F d -j 4 myapp_parallel_backup/

# Restore from gzip
gunzip -c myapp_20240115.sql.gz | psql -U postgres -d myapp_new
Automated Daily Backup with Cron
Backup script + cron
bash
#!/bin/bash
# /opt/scripts/pg_backup.sh

DB_NAME="myapp"
DB_USER="postgres"
BACKUP_DIR="/var/backups/postgres"
RETENTION_DAYS=30
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="$BACKUP_DIR/${DB_NAME}_${DATE}.dump"

mkdir -p "$BACKUP_DIR"

# Create backup
pg_dump -U "$DB_USER" -F c -f "$BACKUP_FILE" "$DB_NAME"

# Remove backups older than retention period
find "$BACKUP_DIR" -name "*.dump" -mtime +$RETENTION_DAYS -delete

echo "Backup completed: $BACKUP_FILE"

# Add to crontab: crontab -e
# 0 2 * * * /opt/scripts/pg_backup.sh >> /var/log/pg_backup.log 2>&1

✅ Choose PostgreSQL E-Commerce / Marketplace

Complex product catalogs, orders with line items, inventory management, payment records, coupon systems — all require ACID transactions, relational integrity, and complex queries. PostgreSQL's JSONB handles variable product attributes. Full-text search works for product search.

Multi-tenant data isolation via RLS, complex permission systems, audit logging, subscription billing, usage metering — PostgreSQL handles all of this natively. Row Level Security is perfect for tenant isolation without application-layer complexity.

✅ Choose PostgreSQL Financial / Fintech

Money handling demands ACID compliance, no rounding errors (NUMERIC type), immutable audit trails, and serializable transactions for concurrent operations. PostgreSQL's reliability makes it the default in banking and fintech.

✅ Choose PostgreSQL Healthcare / Compliance-heavy

HIPAA, GDPR, SOC2 compliance requires fine-grained access control, complete audit trails, encryption, and data integrity guarantees. PostgreSQL's mature security features, RLS, and column-level encryption (pgcrypto) cover all of these.

⚠️ Consider Alternatives Pure Real-time Messaging / Chat

For storing billions of messages with high write throughput and time-series queries, Cassandra or specialized solutions may scale better. That said, Supabase Realtime + PostgreSQL handles thousands of concurrent users fine for most apps.

⚠️ Consider Alternatives Pure Caching / Session Store

For sub-millisecond key-value access (session tokens, rate limiting, pub/sub), Redis is better. Use PostgreSQL for durable data and Redis as a cache layer in front of it.

❌ Not the Best Choice Analytics / Data Warehouse at Scale

For petabyte-scale analytics with complex aggregations across billions of rows, columnar databases like BigQuery, Snowflake, or ClickHouse are purpose-built. Use PostgreSQL for OLTP (transactional) workloads; use a dedicated OLAP store for heavy analytics.
