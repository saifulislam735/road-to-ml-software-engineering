§ 01 — The Big Picture

From Your App to Shopify Scale

You have a working e-commerce app. Here's exactly how it evolves into a platform that hosts thousands of stores — each decision and what it unlocks.

Stage 0 — You Are Here

Single-tenant e-commerce app

One database, one admin, one frontend, one backend. Your app serves exactly one store — yours. The codebase is simple, fast to build, but impossible to sell to other businesses as-is.

Stage 1 — Add store_id everywhere

Shared database, shared schema

You add a store_id UUID column to every table. Every query appends WHERE store_id = $ctx. You now host multiple stores on one database. This is the most important structural change — everything else builds on it.

Stage 2 — Subdomain routing

Dynamic subdomains per store

A wildcard DNS record (*.yourplatform.com → your-server) routes every subdomain to you. Your server reads the Host header and looks up the store. Merchants get their-store.yourplatform.com instantly.

Stage 3 — Custom domains

Merchants bring their own domain

Merchants add a CNAME record pointing to you. You verify ownership, provision a TLS certificate via Let's Encrypt, and route traffic to their store. Each custom domain gets a unique SSL cert automatically.

Stage 4 — Theme system

Dynamic storefront rendering

Themes are JSON config stored in your database — not code. Your renderer reads the JSON and generates the HTML. Merchants use a visual editor to change colors, layouts, and sections. No code is ever written by merchants.

Stage 5 — Payment isolation

Per-store payment credentials

Each store connects their own Stripe account (or SSLCommerz / bKash for BD markets). Your platform handles the routing — detect which store is checking out, decrypt their credentials, initiate the charge on their behalf. Money flows directly to them.

Stage 6 — Shopify scale

Platform marketplace, apps, webhooks

App ecosystem, Liquid-like templating, storefront API for headless builds, webhooks per store, revenue sharing. This is where you have hundreds of thousands of stores and need a dedicated infra team.

Shopify was built exactly this way — starting as a single store (for snowboards) and gradually becoming the platform. Tobi Lütke literally extracted the store engine into a framework (Merb → Rails) and opened it up.

🏗️ Infrastructure reality

Shopify runs on Google Cloud Platform (GCP) with a mix of bare-metal servers co-located in data centers. They use MySQL (Vitess sharded) as primary database, Redis for caching/sessions, Kafka for event streaming. At 2024 scale: 1.75 million merchants, petabytes of data.

🗄️ Database architecture

Shopify uses a technique called "pod architecture" — they shard the database into hundreds of pods, each containing a slice of stores. A store always lives in one pod. This is how they went from one MySQL instance to handling Black Friday spikes.

🌐 Domain handling

Shopify uses Cloudflare's "Cloudflare for SaaS" product for custom domain SSL at scale. Each custom domain gets a TLS cert via ACME/Let's Encrypt automatically within minutes of CNAME verification.

💡 Key insight

Shopify's entire storefront rendering went headless — Hydrogen (React), Oxygen (hosting), Storefront API. The "theme" is just a React app that calls their GraphQL API. You can replicate this pattern at any scale.

The core mental model: you are not building an e-commerce store. You are building a store factory.

§ 03 — Core Architecture

Multi-tenancy Design

The foundational architectural decision. How you store and isolate data for multiple merchants sharing one platform. This decision affects every query you write forever.

Start here

Shared DB, Shared Schema

One database. One set of tables. store_id on every row.

  • ✓ Cheapest to operate
  • ✓ One migration for all stores
  • ✓ Easy cross-store analytics
  • ✗ Must enforce isolation in code
  • ✗ Noisy neighbor problem
Scale tier

Shared DB, Separate Schemas

One Postgres DB. Each tenant gets their own schema namespace.

  • ✓ Better logical isolation
  • ✓ Schema-level RLS built in
  • ✗ N migrations per deployment
  • ✗ Complex query routing
Enterprise only

Database per Tenant

Each merchant gets a dedicated Postgres instance.

  • ✓ Maximum isolation
  • ✓ Independent backups/restores
  • ✗ Very expensive at scale
  • ✗ N DBs to manage/monitor
Recommended: Shared DB, Shared Schema
This is how Shopify, Stripe, Slack, and virtually every SaaS platform started. The pattern is called "pool model" tenancy. Add Postgres Row Level Security (RLS) as an automatic safety net — even if your application code forgets to filter by store_id, the database itself will block cross-tenant access.

The store_id Rule — Implementation

middleware/tenant.ts — Request context injection 
// This runs on EVERY request. Never skip it.
export const tenantMiddleware = async (req, res, next) => {
  const host = req.headers['host'];

  // Extract store from subdomain or custom domain
  let store = await db.stores.findFirst({
    where: {
      OR: [
        { custom_domain: host },
        { subdomain: extractSubdomain(host) }
      ]
    }
  });

  if (!store) return res.status(404).json({ error: 'Store not found' });

  // Inject store context into the request object
  // ALL downstream code uses req.storeId — NEVER trust client-supplied IDs
  req.storeId = store.id;
  req.store = store;
  next();
};

// In every database query, ALWAYS scope by storeId:
const products = await db.products.findMany({
  where: {
    store_id: req.storeId,  // ← THIS IS NOT OPTIONAL
    status: 'active'
  }
});

// Postgres RLS as safety net (belt + suspenders):
CREATE POLICY tenant_isolation ON products
  USING (store_id = current_setting('app.current_store_id')::uuid);

Database Architecture & Schema

The complete schema for a multi-tenant e-commerce platform. Every table, every relationship, every index that matters — with the reasoning behind each decision.

Row Level Security is your last line of defense. Even if your application code has a bug and forgets to add WHERE store_id, Postgres will block cross-tenant access.

SQL — Enable RLS on all tenant tables
-- Enable RLS on every tenant-scoped table
ALTER TABLE products ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders   ENABLE ROW LEVEL SECURITY;
ALTER TABLE customers ENABLE ROW LEVEL SECURITY;
-- ... repeat for all tenant tables

-- Create policies that enforce tenant isolation
CREATE POLICY products_tenant_isolation ON products
  AS PERMISSIVE
  FOR ALL
  TO app_user
  USING (
    store_id = current_setting('app.current_store_id', true)::uuid
  );

-- Your app sets this before every query:
-- SET LOCAL app.current_store_id = '<uuid>';

-- Super-admin bypasses RLS (for platform admin only)
CREATE POLICY superadmin_bypass ON products
  AS PERMISSIVE
  FOR ALL
  TO superadmin_user
  USING (true);  -- no restriction

Without the right indexes, every query that filters by store_id does a full table scan. At 10,000 stores with 10,000 products each, that's 100M rows per scan.

SQL — Critical indexes for multi-tenant performance
-- Composite indexes: store_id FIRST, then the filter column
-- This matters: (store_id, status) ≠ (status, store_id)

CREATE INDEX idx_products_store_status
  ON products (store_id, status)
  WHERE status = 'active';  -- partial index = even faster

CREATE INDEX idx_orders_store_created
  ON orders (store_id, created_at DESC);

CREATE INDEX idx_orders_store_status
  ON orders (store_id, status);

-- Domain lookup — must be instant
CREATE UNIQUE INDEX idx_stores_subdomain
  ON stores (subdomain);

CREATE UNIQUE INDEX idx_stores_custom_domain
  ON stores (custom_domain)
  WHERE custom_domain IS NOT NULL;

-- Customers lookup by email within a store
CREATE UNIQUE INDEX idx_customers_store_email
  ON customers (store_id, email);

-- Query planner verification:
EXPLAIN ANALYZE
  SELECT * FROM products
  WHERE store_id = 'uuid-here' AND status = 'active';

§ 05 — Domain System

Subdomains & Custom Domains

How to give every merchant their own subdomain instantly, and how custom domains work — from DNS records to auto-provisioned TLS certificates. This is one of the most technically interesting parts of SaaS.

How wildcard subdomains work

1

One DNS wildcard record

In your DNS provider (Cloudflare, Route53), add: *.yourplatform.com → A → YOUR_SERVER_IP. This single record makes EVERY possible subdomain resolve to your server — store1.yourplatform.com, store2.yourplatform.com, anything.yourplatform.com. You set this once and never touch it again.

2

Wildcard SSL certificate

Get a wildcard TLS certificate: *.yourplatform.com. This single cert covers every subdomain. Use Let's Encrypt with DNS-01 challenge (Certbot + Cloudflare API). Renews automatically every 90 days. Cost: free.

3

Your server reads the Host header

Every HTTP request arrives with a Host: their-store.yourplatform.com header. Your server extracts the subdomain: their-store. Queries the database: SELECT * FROM stores WHERE subdomain = 'their-store'. Instant — this is a unique indexed column, sub-millisecond lookup.

4

Merchant signup = instant subdomain

When a merchant signs up and picks their store name, you just insert a row in the stores table with their chosen subdomain (validated: lowercase alphanumeric + hyphens only, no reserved names like admin, api, www). Their store is live at their-name.yourplatform.com within seconds, zero DNS changes needed.

Caddy config — Wildcard subdomain routing
# Caddyfile — handles *.yourplatform.com AND custom domains
# Caddy auto-provisions wildcard SSL via DNS-01 challenge

*.yourplatform.com {
    tls {
        dns cloudflare {env.CF_API_TOKEN}  # DNS-01 for wildcard
    }
    reverse_proxy localhost:3000 {
        header_up Host {host}  # Pass Host header to app
    }
}

# Custom domains are handled dynamically by the app
# Caddy's on_demand_tls provisions certs as domains are hit
:443 {
    tls {
        on_demand  # Auto cert for ANY domain that hits this server
        ask https://yourplatform.com/tls-check?domain={tls_servername}
    }
    reverse_proxy localhost:3000
}

// Caddy calls this to check if a domain is allowed
// GET /tls-check?domain=shop.theirdomain.com
app.get('/tls-check', async (req, res) => {
  const domain = req.query.domain;

  const store = await db.stores.findFirst({
    where: {
      custom_domain: domain,
      domain_verified: true  // ← only verified domains get certs
    }

  // 200 = Caddy provisions the cert
  // 4xx = Caddy rejects — no cert for unknown domains
  return store ? res.sendStatus(200) : res.sendStatus(403);

// Verify domain ownership via DNS TXT lookup
const verifyDomain = async (domain, storeToken) => {
  const records = await dns.resolveTxt(`_saas-verify.${domain}`);
  const flat = records.flat();
  return flat.includes(storeToken);
};

§ 06 — Dynamic Rendering

Dynamic Storefront System

How each store looks completely different while running on your single platform. Themes as data, visual editors, and on-demand site generation — from simple to headless.

The core idea: a "theme" is not CSS or HTML files. It is a JSON document describing the structure and configuration of the storefront.

themes table — config column (JSON)
{
  "version": "2.1",
  "colors": {
    "primary": "#1a1a2e",
    "accent": "#e94560",
    "background": "#ffffff"
  },
  "typography": {
    "heading_font": "Playfair Display",
    "body_font": "Lato",
    "base_size": 16
  },
  "sections": [
    {
      "type": "hero_banner",
      "settings": {
        "title": "Premium Fashion",
        "subtitle": "New arrivals weekly",
        "background_image": "stores/uuid/hero.jpg",
        "cta_text": "Shop Now",
        "overlay_opacity": 0.4
      }
    },
    {
      "type": "product_grid",
      "settings": {
        "columns": 3,
        "show_prices": true,
        "collection_id": "featured"
      }
    }
  ]
}
Your renderer takes this JSON, fetches the referenced data (products for the grid, image URLs for the banner), and generates the final HTML. Merchants never write code — they just set values in a visual editor that writes JSON.

Rendering pipeline — request to HTML

1

Request arrives with Host header

Browser requests shop.theirdomain.com/products. Middleware resolves this to store_id = 'abc-123'.

2

Cache check

Check Redis: storefront:abc-123:/products. Cache hit = return HTML immediately (sub-5ms). Cache miss = proceed to render.

3

Fetch theme + page data

Load published theme JSON from DB. Load page data (products for /products, single product for /products/slug). One round trip to DB, parallelized.

4

Render sections

Walk the sections array. For each section, call the section renderer: renderSection(sectionType, settings, data). Returns HTML fragment. Concatenate.

5

Inject store CSS variables

Wrap in layout template, inject CSS variables from theme colors, load correct Google Fonts for typography settings. Return full HTML document.

6

Cache & return

Store rendered HTML in Redis with TTL (5 minutes for product pages, 30 minutes for homepage). Invalidate cache when merchant publishes changes.

Deploy-yourself model — headless storefront

For merchants who want to host on their own server, you generate a complete Next.js project pre-configured with their store credentials.

Merchant clicks "Export Store"

You generate a ZIP of the Next.js template with their credentials baked in. Or: provide a one-click "Deploy to Vercel" button that clones your template repo and sets env vars via Vercel API.

2

Their deployed site calls your API

Every page in their Next.js site uses your Storefront API: GET /v1/products?store_key=pk_live_abc. Your API returns their products. Data stays centralized — they just control the rendering layer.

3

The public API key can only READ their store's public data. It cannot access orders, customer PII, or admin operations. The secret API key never leaves your servers. Even if someone extracts the public key from the deployed site, they can only read product catalogs.

§ 07 — Money Flow

Payment System Architecture

Per-store payment credentials, routing logic, and how to support Stripe, SSLCommerz, bKash, Nagad, and any future gateway — without changing your core checkout code.

Key principle: Your platform is a router, not a payment processor. You never hold merchant funds. The money flows from customer → payment gateway → merchant's own account. You just orchestrate using their credentials.

The plugin pattern — each payment gateway is a module implementing the same interface. Adding a new gateway = one new file.

payments/interface.ts — Gateway contract
// Every payment gateway must implement this interface
interface PaymentGateway {
  initiatePayment(order: Order, credentials: Credentials): Promise<PaymentSession>;
  verifyPayment(sessionId: string, webhookData: any): Promise<PaymentResult>;
  refund(transactionId: string, amount: number): Promise<RefundResult>;
}

// The router selects the right implementation
const getGateway = (provider: string): PaymentGateway => {
  switch(provider) {
    case 'stripe':        return new StripeGateway();
    case 'sslcommerz':   return new SSLCommerzGateway();
    case 'bkash':         return new BkashGateway();
    case 'nagad':         return new NagadGateway();
    default: throw new Error(`Unknown gateway: ${provider}`);
  }
};

// Checkout flow — same for ALL gateways
const checkout = async (req) => {
  const { provider, credentials } = await getStorePaymentMethod(req.storeId);
  const decrypted = decrypt(credentials);       // AES-256 decrypt
  const gateway = getGateway(provider);
  return gateway.initiatePayment(req.order, decrypted);
};

Payment gateways send webhook events when payments complete, fail, or are disputed. You must route these to the right store.

Webhook routing — per-store endpoints
// Each store gets a unique webhook URL with their store_id:
// https://api.yourplatform.com/webhooks/stripe/STORE_ID
// https://api.yourplatform.com/webhooks/sslcommerz/STORE_ID

app.post('/webhooks/stripe/:storeId', async (req, res) => {
  const { storeId } = req.params;

  // Load this store's Stripe webhook secret
  const pm = await db.payment_methods.findFirst({
    where: { store_id: storeId, provider: 'stripe' }
  });
  const secret = decrypt(pm.webhook_secret);

  // Verify signature — reject if tampered
  const event = stripe.webhooks.constructEvent(
    req.rawBody,
    req.headers['stripe-signature'],
    secret  // ← MERCHANT'S webhook secret, not yours
  );

  // Process event scoped to this store
  switch(event.type) {
    case 'payment_intent.succeeded':
      await markOrderPaid(event.data.object, storeId);
      break;
    case 'charge.dispute.created':
      await handleDispute(event.data.object, storeId);
      break;
  }

  res.json({ received: true });
});

§ 08 — Security Design

Security Architecture

Multi-tenant security is fundamentally different from single-tenant. One misconfiguration can expose every customer's data. Here is the complete defense-in-depth model.

The unique threats of a multi-tenant platform — things that don't exist in a single-store app.

⚠ Tenant data leak

Critical. A query bug that forgets WHERE store_id returns data from all tenants. Defense: Postgres RLS, middleware enforcement, query auditing.

⚠ Credential theft

Critical. Your DB contains every merchant's payment API keys. If stolen, attackers can drain every merchant's Stripe account. Defense: AES-256 encryption at rest + access in memory only.

! Subdomain takeover

If a merchant deletes their store but still owns the subdomain slug, and DNS still points to your server — someone else can claim that slug. Defense: soft-delete + subdomain lockout period.

! Noisy neighbor DoS

One store receives a flood of traffic, consuming all server resources and starving other stores. Defense: per-store rate limiting at the API gateway level.

→ Merchant XSS via themes

If you let merchants write raw HTML/JS, a malicious merchant can inject scripts that steal customer payment data from other stores. Defense: structured JSON themes only — never raw HTML input.

→ Super-admin impersonation

An attacker who gains super-admin access has access to ALL stores' data. Defense: separate auth system, IP whitelist, mandatory MFA, audit logs on every action.

Four completely separate authentication contexts. They must never share sessions, tokens, or user tables.

A

Merchant auth (admin dashboard)

Staff login. JWT contains user_id + store_id + role. Role = owner | admin | editor | viewer. Token valid only for the store it was issued for. Refresh tokens stored in DB, revocable. OAuth providers (Google, GitHub) supported.

B

Customer auth (storefront)

Per-store customer tables. customers table has store_id column. Email+password or social login. JWT identifies a customer within a specific store — a customer account at Store A does not work at Store B.

C

API key auth (storefront API)

For headless storefronts. Two keys: pk_ (public, read-only, embedded in frontend) and sk_ (secret, server-side only, full access). Public key visible to everyone = only exposes public catalog data. Secret key = never in browser code.

D

Super-admin auth (platform admin)

IP-restricted endpoint. Completely separate JWT issuer. Mandatory TOTP MFA. Every action is audit-logged with the admin's identity. Consider hardware security keys (YubiKey) for this auth. Never on the same subdomain as merchant admin.

crypto/encrypt.ts — AES-256-GCM encrypt/decrypt
import { createCipheriv, createDecipheriv, randomBytes } from 'crypto';

const ALGORITHM = 'aes-256-gcm';
const KEY = Buffer.from(process.env.ENCRYPTION_KEY, 'hex'); // 32 bytes from Secrets Manager

export const encrypt = (plaintext: string): string => {
  const iv = randomBytes(12);  // unique per encryption
  const cipher = createCipheriv(ALGORITHM, KEY, iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const tag = cipher.getAuthTag();  // authentication tag
  // Store as: iv:tag:ciphertext (all hex)
  return `${iv.toString('hex')}:${tag.toString('hex')}:${encrypted.toString('hex')}`;
};

export const decrypt = (stored: string): string => {
  const [ivHex, tagHex, dataHex] = stored.split(':');
  const decipher = createDecipheriv(ALGORITHM, KEY, Buffer.from(ivHex, 'hex'));
  decipher.setAuthTag(Buffer.from(tagHex, 'hex'));
  return decipher.update(dataHex, 'hex', 'utf8') + decipher.final('utf8');
};

Rate limiting must be per-store, not per-IP. An attacker behind a CDN can make requests from millions of IPs.

Rate limiting middleware — per store_id
import { RateLimiterRedis } from 'rate-limiter-flexible';

const storefrontLimiter = new RateLimiterRedis({
  storeClient: redisClient,
  points: 1000,        // requests per window
  duration: 60,        // per 60 seconds
  keyPrefix: 'rl_store',  // key = rl_store_STORE_ID
});

const checkoutLimiter = new RateLimiterRedis({
  storeClient: redisClient,
  points: 20,   // much stricter for checkout
  duration: 60,
  keyPrefix: 'rl_checkout',
});

export const rateLimitByStore = async (req, res, next) => {
  try {
    const limiter = req.path.startsWith('/checkout') ? checkoutLimiter : storefrontLimiter;
    await limiter.consume(req.storeId);  // keyed to store, not IP
    next();
  } catch {
    res.status(429).json({ error: 'Rate limit exceeded', retryAfter: 60 });
  }
};

§ 09 — Infrastructure

Infrastructure & Scaling

Every service layer from the reverse proxy down to object storage — what to use at each stage, and the tradeoffs of each choice.

🔀 Reverse Proxy

Caddy (recommended to start) — auto SSL, zero config, handles wildcard + custom domains. Move to Nginx when you need fine-grained config. Use Cloudflare in front of everything for DDoS protection.

⚡ Cache Layer

Redis for session storage, rate limiting counters, and storefront HTML cache. Use Upstash (serverless Redis) to start — pay per request, no server management. Move to ElastiCache when you need predictable latency.

📦 Object Storage

Cloudflare R2 for product images and assets — zero egress fees, S3-compatible API. Serve via R2's public URL or a custom subdomain (media.yourplatform.com). Each store's files live under stores/{store_id}/ prefix.

📬 Background Jobs

BullMQ + Redis for async work: order confirmation emails, webhook processing, invoice generation, cache invalidation. Each job carries store_id in its payload — jobs are never cross-tenant.

📧 Transactional Email

Resend or Postmark for order confirmations, password resets. Emails are sent in the context of the store — from the merchant's domain (via DKIM/SPF you configure on their behalf), not yours.

🔍 Observability

Grafana + Prometheus for metrics. Sentry for error tracking (filter by store_id). Axiom for log aggregation. Add a store_id field to every log line — this lets you diagnose per-store issues instantly.

// Cache key pattern: {namespace}:{store_id}:{resource_identifier}
// ALWAYS include store_id — never cache cross-tenant

const CACHE_KEYS = {
  storefront: (storeId: string, path: string) =>
    `sf:${storeId}:${path}`,                      // Rendered HTML — 5min TTL

  product:  (storeId: string, slug: string) =>
    `prod:${storeId}:${slug}`,                    // Product data — 10min TTL

  theme: (storeId: string) =>
    `theme:${storeId}`,                           // Theme JSON — 30min TTL

  domain: (hostname: string) =>
    `domain:${hostname}`,                         // Domain → store_id — 1hr TTL

  session: (token: string) =>
    `sess:${token}`,                              // User session — 24hr TTL
};

// Invalidation: when merchant publishes changes
const invalidateStore = async (storeId: string) => {
  const pattern = `sf:${storeId}:*`;
  const keys = await redis.keys(pattern);
  if (keys.length) await redis.del(...keys);
};

Every product image uploaded by every merchant gets stored in object storage and served via CDN — never your server disk.

media/upload.ts — Image upload with store isolation
import { S3Client, PutObjectCommand } from '@aws-sdk/client-s3';

// Cloudflare R2 is S3-compatible — same SDK
const r2 = new S3Client({
  region: 'auto',
  endpoint: process.env.R2_ENDPOINT,
  credentials: { accessKeyId: ..., secretAccessKey: ... }
});

export const uploadMedia = async (file: Buffer, storeId: string, filename: string) => {
  // Key includes store_id — each store's files are namespaced
  const key = `stores/${storeId}/media/${nanoid()}-${filename}`;

  // Validate file type — NEVER trust Content-Type header
  const type = await detectMimeType(file);  // magic bytes check
  if (!['image/jpeg', 'image/png', 'image/webp'].includes(type)) {
    throw new Error('Invalid file type');
  }

  await r2.send(new PutObjectCommand({
    Bucket: 'platform-media',
    Key: key,
    Body: file,
    ContentType: type,
    // No public ACL needed — R2 serves via CDN URL
  }));

  return `https://media.yourplatform.com/${key}`;
};

Scaling patterns for a multi-tenant platform — the bottlenecks appear in a specific order as you grow.

0–100 stores

Single server handles everything

One app server, one Postgres instance (managed), one Redis instance (Upstash). The bottleneck here is developer time, not compute. Spend zero time on scaling infrastructure.

100–1K stores

Database connection pooling becomes critical

Each HTTP request opens a DB connection. At 100 concurrent requests across many stores, you hit Postgres connection limits (~100 default). Add PgBouncer or use Neon/Supabase's built-in pooling. This is usually the first real bottleneck.

1K–10K stores

Read replicas + horizontal app scaling

Add a Postgres read replica for storefront API reads (product listings, pages). All writes still go to primary. Add more app server instances behind a load balancer. Add Redis cluster for session storage.

10K+ stores

Database sharding — the hard problem

A single Postgres instance has limits (~10TB, ~100K QPS with good hardware). At this scale, you shard: group stores into "shards" or "pods", each pod has its own Postgres instance. A routing layer maps store_id → pod. This is what Shopify, GitHub, and Stripe all do. Tools: Vitess, Citus, or manual sharding.

§ 10 — Going Live

Deployment Models

How to deploy your platform itself, how to let merchants deploy their storefronts, and how CI/CD works when you have thousands of stores to consider on every release.

📦 Containerize everything

Your app server, background workers, and any auxiliary services run as Docker containers. Same container in dev, staging, and production. No "works on my machine" issues. Docker Compose locally, Kubernetes or ECS in production.

🔄 Blue/Green deployments

Never take your platform down for a deployment. Run two identical environments (blue = live, green = new version). Deploy to green, run smoke tests, switch load balancer to green. Instant rollback = switch back to blue.

📊 Feature flags

New features that could affect stores roll out progressively. Enable for 1% of stores, watch metrics, then 10%, then 100%. Use a feature flag service (LaunchDarkly, Unleash, or a simple DB table) keyed by store_id.

🌍 Environments

Development (local), Staging (production clone, no real merchant data), Production. Every PR deploys to a preview environment. Never test against production. Staging uses production-like traffic via load testing tools.

Two modes for merchants: hosted (you run it) and self-hosted (they deploy it). Both are valid product offerings at different price points.

✓ Hosted model (default)

  • Merchant signs up → store is instantly live
  • You handle all uptime, SSL, scaling
  • One-click theme changes take effect immediately
  • Easier to upsell (charge for features, not hosting)
  • You control the experience end-to-end

→ Self-hosted model (premium)

  • Merchant gets a Next.js project + your API
  • They deploy to Vercel/Netlify/their own server
  • Data still in your database — you're still the API
  • Appeals to tech-savvy merchants with custom needs
  • You earn on API calls, not hosting

CI/CD for a multi-tenant platform has extra considerations — a bad deploy affects every store simultaneously.

1

Automated test suite

Every PR runs: unit tests (business logic), integration tests (DB queries with real Postgres), tenant isolation tests (verify store_id enforcement), security tests (verify RLS, auth boundaries).

2

Preview environments

Each PR gets a preview URL with a fresh database seeded with test stores. QA happens here, never in production. Use Neon's database branching — each PR gets a branch of the staging DB, instantly, for free.

3

Canary releases

Route 5% of traffic to the new version. Watch error rates, latency p99, and business metrics (checkout completion). Auto-rollback if error rate spikes. Graduate to 100% if metrics are clean after 30 minutes.

4

Database migrations — zero downtime

Never use destructive migrations in a running system. Pattern: add new column (nullable) → deploy code that writes to both → backfill old rows → make column required → remove old code. This is called expand/contract and never requires downtime.

The expand/contract migration pattern — how to change your database schema without downtime or data loss.

migrations/example — Adding a column safely
-- WRONG: Renaming a column in a live system
-- ALTER TABLE products RENAME COLUMN name TO title;
-- ^ This breaks all running app servers immediately

-- RIGHT: Expand/contract over 3 releases

-- RELEASE 1: Add the new column (nullable)
ALTER TABLE products ADD COLUMN title TEXT;

-- RELEASE 2: App writes to BOTH columns, reads from old
-- Also backfill: UPDATE products SET title = name WHERE title IS NULL;

-- RELEASE 3: App reads from new column, stops writing to old
-- RELEASE 4: Drop old column (after confirming it's unused)
ALTER TABLE products DROP COLUMN name;

-- Zero downtime. No locks. No data loss.
-- Each release can be rolled back independently.
