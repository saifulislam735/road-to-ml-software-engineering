Module 2 · Concept

Protocols — the languages servers speak

A protocol is a set of rules two computers agree to follow when communicating. Four protocols run your entire streaming platform. Understand all four.

What it is: A TCP-based protocol created by Macromedia (now Adobe). OBS uses it to push video to your server. Still the universal standard for live stream ingest in 2025.

Port: 1935 — you must open this in your firewall. Cloudflare cannot proxy port 1935, so your RTMP subdomain must be DNS-only (gray cloud).

Direction: One-way only. OBS → your server. Viewers never use RTMP.

Why TCP? TCP guarantees every packet arrives in order. A small delay is acceptable on the broadcaster side. On the viewer side, UDP would be better — which is why viewers use HLS/HTTP instead.

What you put in OBS:

OBS → Settings → Stream
Service: Custom
Server: rtmp://rtmp.yoursite.com/live
Stream Key: abc123def456 ← unique per user, from your database

Breaking down the URL: rtmp:// = use RTMP protocol. rtmp.yoursite.com = your VPS (DNS-only, bypasses Cloudflare). /live = the nginx-rtmp application name. The stream key is appended after by OBS automatically.

What it is: Apple's streaming format. Video is split into small 2-second .ts segment files. A .m3u8 playlist file lists the newest segments. The browser fetches and plays them continuously.

Why HTTP? Uses regular port 443 (HTTPS). Works through every firewall. CDNs cache it natively. No special software — just file downloads over the web.

Latency: 15–30 seconds by default. This is normal and acceptable for sports streaming. The 2-second segments plus a 3-segment buffer = ~6-second minimum lag, plus encoding and network time.

What a playlist file looks like:

m3u8720p.m3u8 — auto-updated every 2 seconds by FFmpeg
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:2
#EXT-X-MEDIA-SEQUENCE:152   ← keeps incrementing as new segments arrive

#EXTINF:2.000,
720p_0152.ts    ← 2-second video chunk, delivered over HTTPS
#EXTINF:2.000,
720p_0153.ts
#EXTINF:2.000,
720p_0154.ts    ← newest segment — HLS.js fetches this next

HLS.js polls this file every 2 seconds, sees new segments, fetches and plays them. That's the entire mechanism of live streaming at the browser level.

What it is: A persistent TCP connection where both browser and server can send messages at any time — without the browser needing to ask first.

How it differs from HTTP: HTTP is like a letter — client sends, server responds, done. WebSocket is like a phone call — both sides can talk whenever.

Used for: Live chat, viewer count updates, stream-is-live notifications, real-time scores.

javascriptRaw WebSocket (we'll use Socket.io which wraps this)

What it is: Regular HTTP with TLS encryption. Your website, API, and HLS segment delivery all run over HTTPS.

Why HTTPS matters for streaming: Browsers block mixed content. If your player page is HTTPS but the HLS files are HTTP, the browser will refuse to load the video segments. Everything must be HTTPS.

How you get it: Let's Encrypt (free, auto-renewing) via Certbot. We set this up in Module 9. Cloudflare also provides a layer of TLS for browser → Cloudflare traffic.

Video fundamentals — codecs, bitrate, ABR

Raw 1080p video is 10GB per minute. You'll stream it at 4MB per minute. Codecs make this possible. Here's what you actually need to know before configuring FFmpeg.

OBS outputs H.264 by default. FFmpeg encodes H.264 with -c:v libx264. Every browser plays it. Zero configuration needed. Don't overthink codecs until you're at scale.

⚠ Keyframe interval = 2 is non-negotiable

HLS cuts your video into 2-second segments at keyframe boundaries. If OBS sends keyframes every 10 seconds (the default), segments get cut in the middle of a frame group. Viewers see broken video, stuttering, and buffering. Set it to 2 seconds and never change it.

You transcode one input into multiple quality levels. HLS.js automatically picks the best one for each viewer's connection. This is what Netflix, Twitch, and YouTube all do.

Module 6 · Implementation

Nginx + RTMP — the complete configuration

Nginx does two completely separate jobs in your streaming setup: it receives RTMP from OBS (port 1935) and serves web content over HTTPS (port 443). One config file, two distinct blocks.

Important: how FFmpeg gets launched

The exec directive in nginx-rtmp calls FFmpeg when a stream starts. On Ubuntu's packaged nginx-rtmp (libnginx-mod-rtmp), this works with a shell script wrapper — we'll use that approach. Nginx spawns a shell script; the script launches FFmpeg. This is more reliable and easier to debug than inline FFmpeg arguments.

Step 1 — Write the nginx.conf

nginx/etc/nginx/nginx.conf — replace entire file
worker_processes auto;
error_log /var/log/nginx/error.log warn;
pid /var/run/nginx.pid;

# Load the RTMP module (installed via libnginx-mod-rtmp)
include /etc/nginx/modules-enabled/*.conf;

events {
    worker_connections 1024;
    use epoll;
}

###################################################
#  RTMP BLOCK — port 1935 — receives from OBS
###################################################
rtmp {
    server {
        listen 1935;
        chunk_size 4096;
        max_message 1M;

        application live {
            live on;
            record off;

            # Verify stream key before allowing — your API must be running
            # Returns 2xx = allow, 4xx = reject
            on_publish http://127.0.0.1:4000/api/stream/auth;
            on_publish_done http://127.0.0.1:4000/api/stream/end;

            # Launch FFmpeg via shell script when stream starts
            # $name = the stream key OBS sent
            exec /home/stream/scripts/start_ffmpeg.sh $name;
        }
    }
}

###################################################
#  HTTP BLOCK — ports 80 and 443
###################################################
http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;
    sendfile on;
    tcp_nopush on;
    keepalive_timeout 65;
    gzip on;
    client_max_body_size 50M;

    # Redirect all HTTP → HTTPS
    server {
        listen 80;
        server_name yoursite.com www.yoursite.com rtmp.yoursite.com;
        return 301 https://$host$request_uri;
    }

    # Main HTTPS server
    server {
        listen 443 ssl;
        server_name yoursite.com www.yoursite.com;

        # SSL certs — certbot fills these in Module 9
        ssl_certificate /etc/letsencrypt/live/yoursite.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/yoursite.com/privkey.pem;
        ssl_protocols TLSv1.2 TLSv1.3;
        ssl_ciphers HIGH:!aNULL:!MD5;

        # Serve HLS files — .m3u8 playlists and .ts segments
        location /hls/ {
            alias /var/www/hls/;
            types {
                application/vnd.apple.mpegurl m3u8;
                video/mp2t ts;
            }
            add_header Cache-Control no-cache;
            add_header Access-Control-Allow-Origin *;
            add_header Access-Control-Allow-Methods GET;
        }

        # Static website files
        location / {
            root /var/www/stream;
            index index.html;
            try_files $uri $uri/ /index.html;
        }

        # Proxy to Node.js API (port 4000)
        location /api/ {
            proxy_pass http://127.0.0.1:4000;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }

        # WebSocket proxy for Socket.io live chat
        location /socket.io/ {
            proxy_pass http://127.0.0.1:4000;
            proxy_http_version 1.1;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection "upgrade";
            proxy_set_header Host $host;
            proxy_read_timeout 86400;
        }
    }
}

Step 2 — Write the FFmpeg launch script

This script is called by Nginx when OBS starts streaming. It creates the output directory, generates the master playlist, and starts FFmpeg.

bash/home/stream/scripts/start_ffmpeg.sh
#!/bin/bash
# Called by Nginx RTMP when OBS starts streaming
# $1 = stream key (passed by Nginx as $name)

STREAM_KEY="$1"
HLS_DIR="/var/www/hls/${STREAM_KEY}"
LOG_FILE="/var/log/ffmpeg/${STREAM_KEY}.log"

# Create output directory for this stream
mkdir -p "${HLS_DIR}"
chmod 755 "${HLS_DIR}"

# Write master HLS playlist (lists all quality levels)
# HLS.js reads this first to discover available bitrates
cat > "${HLS_DIR}/master.m3u8" << 'MASTER'
#EXTM3U
#EXT-X-VERSION:3

#EXT-X-STREAM-INF:BANDWIDTH=4200000,RESOLUTION=1920x1080,NAME="1080p"
1080p.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=2628000,RESOLUTION=1280x720,NAME="720p"
720p.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=864000,RESOLUTION=854x480,NAME="480p"
480p.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=432000,RESOLUTION=640x360,NAME="360p"
360p.m3u8
MASTER

# Start FFmpeg: read RTMP, output 4 HLS quality levels simultaneously
# -nostdin: don't try to read stdin (running as background process)
# -re: not needed for live input, but -rtsp_transport tcp helps stability
ffmpeg -nostdin \
    -i "rtmp://127.0.0.1/live/${STREAM_KEY}" \
    \
    -vf scale=1920:1080 -c:v libx264 -b:v 4000k -maxrate 4400k -bufsize 8000k \
    -c:a aac -b:a 128k -ar 44100 \
    -g 60 -keyint_min 60 -sc_threshold 0 \
    -preset veryfast -profile:v high \
    -hls_time 2 -hls_list_size 5 -hls_flags delete_segments \
    -hls_segment_filename "${HLS_DIR}/1080p_%04d.ts" \
    -f hls "${HLS_DIR}/1080p.m3u8" \
    \
    -vf scale=1280:720 -c:v libx264 -b:v 2500k -maxrate 2750k -bufsize 5000k \
    -c:a aac -b:a 128k -ar 44100 \
    -g 60 -keyint_min 60 -sc_threshold 0 \
    -preset veryfast -profile:v high \
    -hls_time 2 -hls_list_size 5 -hls_flags delete_segments \
    -hls_segment_filename "${HLS_DIR}/720p_%04d.ts" \
    -f hls "${HLS_DIR}/720p.m3u8" \
    \
    -vf scale=854:480 -c:v libx264 -b:v 800k -maxrate 880k -bufsize 1600k \
    -c:a aac -b:a 96k -ar 44100 \
    -g 60 -keyint_min 60 -sc_threshold 0 \
    -preset veryfast \

Module 7 · Implementation

FFmpeg — understanding every flag

The FFmpeg command in Module 6 has ~20 flags. You don't need to memorize them, but you need to understand what each one does so you can debug and tune it.

-i specifies the input source. FFmpeg reads the RTMP stream from Nginx on localhost. We use 127.0.0.1 instead of localhost because DNS resolution of localhost can fail under certain conditions — the IP is always reliable.

There is no authentication at this RTMP-to-RTMP hop (Nginx → FFmpeg) because it's all on localhost. The stream key validation happens at the OBS → Nginx hop via on_publish.

Scales the video to the target resolution. OBS sends 1080p, FFmpeg scales to 720p/480p/360p for the lower quality streams. The scaling happens in software using the "scale" video filter.

If the input is already the right resolution (OBS sends 720p and target is 720p), FFmpeg still applies the filter but it's a no-op — no quality loss, negligible CPU cost.

-c:v libx264 — use H.264 for video encoding.

-b:v 2500k — target bitrate: 2500 kilobits per second.

-maxrate 2750k — maximum peak bitrate. Prevents sudden spikes. Usually 10% above -b:v.

-bufsize 5000k — rate control buffer: 2× the bitrate. This is the window over which bitrate is averaged. Larger = smoother but higher latency.

-g 60 — keyframe interval: every 60 frames. At 30fps, this is every 2 seconds. HLS segments must start at keyframes.

-keyint_min 60 — prevents FFmpeg from inserting extra keyframes at scene changes. Keeps segment boundaries clean.

-sc_threshold 0 — disables scene change detection for keyframe insertion. Without this, scene changes trigger unexpected keyframes that break 2-second segment alignment.

H.264 presets control the trade-off between encoding speed and compression efficiency:

PresetCPU usageQuality at same bitrateUse for live?
ultrafastLowestPoorOnly if CPU is really limited
superfastVery lowOKAcceptable
veryfastLowGoodRecommended
fasterMediumBetterIf CPU allows
mediumHighBest for liveUsually too slow

-hls_time 2 — each segment is 2 seconds. The playlist lists 5 segments = 10 seconds of buffer available to the player.

-hls_list_size 5 — keep only the last 5 segments in the playlist. Older segments are removed from the list.

-hls_flags delete_segments — delete the actual .ts files for segments that are removed from the playlist. Without this flag, your disk will fill up within hours. The old .ts files accumulate continuously.

javascriptmiddleware/authenticate.js
const jwt = require('jsonwebtoken');

/**
 * Middleware: verify JWT token in Authorization header.
 * Sets req.user = { id, username } on success.
 * Usage: router.get('/protected', authenticate, handler)
 */
function authenticate(req, res, next) {
  const header = req.headers['authorization'];
  if (!header || !header.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'No token provided' });
  }

  const token = header.slice(7);
  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.user = decoded;
    next();
  } catch (err) {
    res.status(401).json({ error: 'Invalid or expired token' });
  }
}

module.exports = authenticate;

    const user = rows[0];

    // Create stream config for this user
    await pool.query(
      'INSERT INTO streams (user_id, title) VALUES ($1, $2)',
      [user.id, `${username}'s Stream`]
    );

    // Issue JWT
    const token = jwt.sign(
      { id: user.id, username: user.username },
      process.env.JWT_SECRET,
      { expiresIn: '30d' }
    );

    res.status(201).json({ token, user });

  } catch (err) {
    if (err.code === '23505') { // unique violation
      return res.status(409).json({ error: 'Username or email already taken' });
    }
    console.error('[Auth] Register error:', err);
    res.status(500).json({ error: 'Registration failed' });
  }
});

    );

    // Don't send password_hash to client
    const { password_hash, ...safeUser } = user;
    res.json({ token, user: safeUser });

  } catch (err) {

    res.status(500).json({ error: 'Login failed' });

Stream auth — the endpoints Nginx calls

These endpoints are called by Nginx — not by your frontend. When OBS connects, Nginx POSTs to /api/stream/auth. When OBS disconnects, it POSTs to /api/stream/end.

Nginx sends form-encoded data, not JSON

Nginx on_publish sends: name=STREAMKEY&addr=IP&flashver=...&app=live as application/x-www-form-urlencoded. That's why express.urlencoded() in server.js is essential. Without it, req.body.name is undefined and all streams get rejected.

/**
 * POST /api/stream/auth
 *
 * Called by Nginx on_publish when OBS starts streaming.
 * Nginx sends form body: name=STREAM_KEY&app=live&...
 *
 * Return 2xx → Nginx allows the stream.
 * Return 4xx → Nginx rejects and disconnects OBS.
 */
router.post('/stream/auth', async (req, res) => {
  const streamKey = req.body?.name;

  console.log(`[Stream] Auth attempt - key: ${streamKey}, ip: ${req.ip}`);

  if (!streamKey || streamKey.trim() === '') {
    console.log('[Stream] Rejected: no stream key');
    return res.status(400).send('Stream key required');
  }

  try {
    // Find user with this stream key
    const result = await pool.query(`
      SELECT
        u.id AS user_id,
        u.username,
        u.stream_key,
        u.chat_color,
        s.id AS stream_id,
        s.title,
        s.category
      FROM users u
      JOIN streams s ON s.user_id = u.id
      WHERE u.stream_key = $1
        AND u.is_active = true
      LIMIT 1
    `, [streamKey]);

    if (result.rows.length === 0) {
      console.log(`[Stream] Rejected: unknown key ${streamKey}`);
      return res.status(401).send('Invalid stream key');
    }

    const { user_id, username, stream_id, title, category } = result.rows[0];
    const startedAt = new Date().toISOString();

    // Store live status in Redis (TTL 24h as safety net)
    await redis.setEx(`live:${streamKey}`, 86400, JSON.stringify({
      user_id, username, stream_id, title, category, startedAt
    }));

    // Update database
    await pool.query(
      'UPDATE streams SET is_live = true, started_at = $1, ended_at = NULL WHERE id = $2',
      [startedAt, stream_id]
    );

    console.log(`[Stream] ✓ Accepted: @${username} (key: ${streamKey})`);

    // Return 200 → Nginx allows the stream
    res.status(200).send('OK');

  } catch (err) {
    console.error('[Stream] Auth error:', err);
    return res.status(500).send('Server error');
  }
});

      await redis.del(`viewers:${streamKey}`);
      await redis.del(`chat:${streamKey}`);
    }

    const streamDir = path.join(HLS_DIR, streamKey);
    if (fs.existsSync(streamDir)) {
      fs.rmSync(streamDir, { recursive: true, force: true });
    }

    console.log(`[Stream] ✓ Ended: ${streamKey}`);
    res.status(200).send('OK');

  } catch (err) {
    console.error('[Stream] End error:', err);
    res.status(500).send('Error');
  }
});

Live chat — Socket.io implementation

Socket.io handles real-time bidirectional communication. Viewers connect to a "room" per stream. Messages go to everyone in that room. Viewer counts update on join/leave.

javascriptsocket/chat.js — complete Socket.io handler

const pool  = require('../config/db');

// Chat name colors — assigned to each viewer session
const COLORS = [
  '#60a5fa', '#a78bfa', '#34d399', '#f87171',
  '#fb923c', '#e879f9', '#38bdf8', '#a3e635'
];

// Basic bad-word filter (extend this list)
const BANNED_WORDS = ['spam', 'scam']; // add your list

function containsBannedWord(text) {
  const lower = text.toLowerCase();
  return BANNED_WORDS.some(w => lower.includes(w));
}

/**
 * Exported as a function that receives the Socket.io server instance.
 * Called once from server.js: require('./socket/chat')(io)
 */
module.exports = function initChat(io) {

  io.on('connection', async (socket) => {
    const { streamKey, username } = socket.handshake.query;

    // Validate required parameters
    if (!streamKey) {
      socket.disconnect();
      return;
    }

    const room       = `stream:${streamKey}`;
    const displayName = (username || 'Guest').slice(0, 20);
    const color = COLORS[Math.floor(Math.random() * COLORS.length)];

    // Join the stream's room
    socket.join(room);

    // Increment viewer count in Redis + broadcast to room
    const viewerCount = await redis.incr(`viewers:${streamKey}`)
      .catch(() => 0);
    io.to(room).emit('viewerCount', viewerCount);

    // Also update DB (best effort, don't block on failure)
    pool.query(
      'UPDATE streams SET viewer_count = $1, viewer_peak = GREATEST(viewer_peak, $1) WHERE user_id = (SELECT id FROM users WHERE stream_key = $2)',
      [viewerCount, streamKey]
    ).catch(() => {});

    // Send chat history (last 50 messages)
    const history = await redis.lRange(`chat:${streamKey}`, -50, -1)
      .catch(() => []);
    socket.emit('chat:history', history.map(m => {
      try { return JSON.parse(m); } catch { return null; }
    }).filter(Boolean));

    // Handle incoming chat message
    socket.on('chat:message', async ({ message }) => {
      if (!message || typeof message !== 'string') return;

      const trimmed = message.trim();
      if (trimmed.length === 0 || trimmed.length > 200) return;

      if (containsBannedWord(trimmed)) {
        socket.emit('chat:error', 'Message not allowed');
        return;
      }

      const msg = {
        id:        Date.now() + Math.random(),
        username:  displayName,
        message:   trimmed,
        color,
        timestamp: new Date().toISOString()
      };

      // Store in Redis list (keep last 100)
      await redis.rPush(`chat:${streamKey}`, JSON.stringify(msg))
        .catch(() => {});
      await redis.lTrim(`chat:${streamKey}`, -100, -1)
        .catch(() => {});

      // Broadcast to all viewers in this stream's room
      io.to(room).emit('chat:message', msg);
    });

    // Viewer disconnects
    socket.on('disconnect', async () => {
      const count = await redis.decr(`viewers:${streamKey}`)
        .catch(() => 0);
      const safeCount = Math.max(0, count);

      // Correct Redis if it goes negative (edge case)
      if (count < 0) await redis.set(`viewers:${streamKey}`, 0).catch(() => {});

      io.to(room).emit('viewerCount', safeCount);
    });
  });

  console.log('[Socket.io] Chat handler initialized');
};

Short answer: not required to start, but it becomes very valuable as you grow. Here's an honest comparison so you can decide when to make the switch.

Docker · Concept

Docker concepts — images, containers, compose

Docker has four concepts you need to understand before looking at any config file. Everything else follows from these.

A Docker image is a snapshot of a filesystem and its startup command. It's like a class in programming — it's the template, not the running thing. Images are built from a Dockerfile — a text file with instructions.

Example: the official node:20-alpine image contains Alpine Linux + Node.js 20. You build on top of it by adding your code. The result is your own image: streamsite-api.

Images are immutable. You never modify a running image — you build a new one and redeploy.

A container is a running instance of an image — like an object created from a class. It's an isolated process with its own filesystem, network, and process space.

You can run many containers from the same image. If a container crashes, you start a new one from the same image in seconds. Nothing is lost from the image itself.

Containers are ephemeral by default — if you restart a container, any files written inside it are gone. That's why databases use volumes (persistent storage mounted into containers).

A Docker volume is a directory on your host machine that's mounted inside a container. Data written there persists even when the container stops or is deleted.

In your streaming setup, volumes are used for:

  • /var/www/hls — HLS segments written by FFmpeg, served by Nginx
  • /var/lib/postgresql — PostgreSQL database files
  • /etc/letsencrypt — SSL certificates
  • /var/log/ffmpeg — FFmpeg logs

Docker Compose lets you define and run multiple containers together in a single docker-compose.yml file. One command — docker compose up -d — starts your entire stack.

Compose also handles:

  • Networking: Containers in the same compose file can reach each other by service name. Your API connects to PostgreSQL at postgres:5432 — not localhost.
  • Dependency order: depends_on ensures Postgres starts before the API.
  • Environment variables: Each container gets its own env vars from a .env file.
  • Restart policy: restart: unless-stopped replaces PM2 for auto-restart.

Node.js API — Dockerfile

The API Dockerfile is straightforward. It starts from the official Node.js Alpine image, copies your code, installs production dependencies, and starts the server.

api/Dockerfile

dockerfileapi/Dockerfile
# ── Stage 1: Dependencies ─────────────────────────
FROM node:20-alpine AS deps
WORKDIR /app

# Copy package files first (Docker layer cache optimization)
# If package.json didn't change, npm ci is skipped in rebuilds
COPY package*.json ./
RUN npm ci --omit=dev

# ── Stage 2: Final image ─────────────────────────
FROM node:20-alpine

# Don't run as root inside the container
RUN addgroup -g 1001 -S nodejs && \
    adduser -S nodeapp -u 1001

WORKDIR /app

# Copy deps from stage 1
COPY --from=deps /app/node_modules ./node_modules

# Copy application code
COPY --chown=nodeapp:nodejs . .

# Create directories the app needs
RUN mkdir -p /var/log/api /data/hls && \
    chown -R nodeapp:nodejs /var/log/api /data/hls

USER nodeapp

EXPOSE 4000

# Health check — Docker will mark container unhealthy if this fails
HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
  CMD wget -qO- http://localhost:4000/api/health || exit 1

CMD ["node", "server.js"]

Two-stage build — why it matters

The deps stage installs npm packages. The final image copies only the installed node_modules from that stage — not the npm cache, not the source of npm itself in its full form. Result: a smaller final image. More importantly, if package.json hasn't changed between builds, Docker reuses the cached node_modules layer — rebuilds take seconds instead of minutes.

Update config files for Docker networking

In Docker Compose, containers reach each other by service name. Your config/db.js and config/redis.js don't need changes — they read from DATABASE_URL and REDIS_URL in the .env file, which already has postgres and redis as hostnames.
