What is the internet?

The Internet is not a location or a company. It is a global system of interconnected networks united by shared rules.

Core definition

The Internet is a packet-switched, decentralized network of networks, united by the TCP/IP protocol suite. Every device participates because it speaks the same language: IP. That shared protocol — enforced by nothing except mutual adoption — is what makes global communication possible.

It has no central server. No single entity owns it. If one path breaks, traffic reroutes automatically through other paths.

The web is not the internet

The World Wide Web (HTTP/HTTPS pages in browsers) is one application that runs on top of the Internet. Email, SSH, gaming, VoIP, and file transfers are other applications that also use the Internet. The Internet is the highway; the Web is one type of vehicle.

Physical transmission of data

All digital data is binary. To send it, we encode 1s and 0s as variations in voltage, light intensity, or electromagnetic field strength.

Copper wire (Ethernet)

Ethernet encodes data as voltage variations. High voltage (+5V) = binary 1, low voltage (0V) = binary 0. Modern Gigabit Ethernet uses PAM-5 encoding across 4 twisted wire pairs — 2 bits per symbol per pair.

+5V ─┐ ┌─────┐ ┌── Bit: 1 0 1 1 0 1 │ │ │ │ 0V └────┘ └────┘ ← clock period (1 ns for 1 GbE) →

The 100 m limit exists because resistance converts electrical energy to heat, and capacitance blurs bit boundaries. Beyond 100 m, the signal degrades below reliable detection threshold.

Fiber optic (light)

A glass strand thinner than a hair carries pulses of light via total internal reflection — the core has a higher refractive index than the cladding, so light bounces down the fiber rather than escaping.

DWDM (Dense Wavelength Division Multiplexing) puts 80+ different wavelengths on one fiber simultaneously. Each wavelength is an independent data stream. One fiber can carry 8+ Tbps total.

Type Core size Max distance Use case
Single-mode 8–10 μm 1000+ km All long-haul & submarine
Multimode OM4 50 μm 300 m Data center, campus

WiFi (radio waves)

WiFi uses OFDM — the channel is split into hundreds of narrow subcarriers. WiFi 6 uses 1024-QAM, encoding 10 bits per symbol by varying both amplitude and phase across 1024 distinct states.

CSMA/CA governs channel access: before transmitting, a device listens for silence, waits a random backoff period, then transmits. This prevents constant collisions in shared air.

Network hardware

The physical devices that move data through the network — each operating at a specific OSI layer.

Router (Layer 3 — Network)

A router receives IP packets, consults its routing table to find the best next hop for the destination IP address, and forwards the packet out the correct interface. Routers connect different networks together.

Routing table lookup for dst=203.0.113.5: 203.0.113.0/24 → eth1 (via 10.1.2.1) ← longest match, wins 203.0.0.0/8 → eth2 (via 10.1.3.1) 0.0.0.0/0 → eth0 (default route) Result: forward out eth1

Switch (Layer 2 — Data Link)

A switch connects devices within the same LAN. It builds a MAC address table by recording which source MAC arrives on which port. When a frame arrives, it forwards to the known port — or floods to all ports if unknown. Modern switches are full-duplex: each device gets its own dedicated bandwidth in both directions.

Firewall

A stateful firewall tracks TCP connection state — it allows established sessions to receive responses while blocking unsolicited inbound connections. Rules specify which source/destination IP and port combinations are permitted. Next-Generation Firewalls (NGFW) operate at Layer 7: they can inspect application content, block specific apps by name, and perform TLS inspection.

Load balancer

Distributes incoming traffic across multiple servers. Layer 4: forwards by IP and port. Layer 7: routes by URL path, hostname, or cookie value — also terminates TLS. Algorithms: Round Robin, Least Connections, IP Hash (for session stickiness), Weighted.

Modem

Modulates (converts digital data to analog signal) and demodulates (converts analog back to digital). A DSL modem converts Ethernet packets to a signal that travels over copper telephone wire. A cable modem converts for coaxial cable TV infrastructure. It is the bridge between your home network and the ISP's access network.

IP addressing & NAT

Every device needs an address so packets know where to go. IP addresses are the Internet's postal system.

IPv4

32-bit addresses written as 4 decimal octets: 192.168.1.1. Provides ~4.3 billion addresses — exhausted globally in 2011. A subnet mask divides the address into network and host portions.

192.168.1.100/24 Network: 192.168.1.0 (first 24 bits fixed) Host: .100 (last 8 bits = 256 addresses) Broadcast: 192.168.1.255 Usable range: .1 to .254 (254 hosts)

Private ranges (RFC 1918) — not routable on the public Internet:

10.0.0.0/8 → 10.x.x.x 172.16.0.0/12 → 172.16.x.x to 172.31.x.x 192.168.0.0/16 → 192.168.x.x

IPv6

128-bit addresses written as 8 groups of 4 hex digits: 2001:0db8:85a3::8a2e:0370:7334. Provides 3.4×10³⁸ addresses — effectively unlimited. Eliminates the need for NAT. Built-in IPsec. Global adoption is now ~45–50% of Google traffic.

NAT (Network Address Translation)

NAT lets many devices share one public IP. Your router rewrites outbound packets to use its public IP and a unique port, keeps a mapping table, and routes responses back to the correct internal device.

Your laptop: 192.168.1.5:52341 → [NAT] → 203.0.113.1:52341 Your phone: 192.168.1.8:61234 → [NAT] → 203.0.113.1:61234 ↑ same public IP, different port numbers

MAC addresses & ARP

MAC addresses are 48-bit hardware identifiers burned into every network interface: 00:1A:2B:3C:4D:5E. Used for Layer 2 (local) communication only — never routed across the Internet.

ARP (Address Resolution Protocol) maps IP to MAC. When your device wants to send to 192.168.1.1, it broadcasts "Who has 192.168.1.1?" and the router replies with its MAC address. The result is cached in the ARP table.

DHCP

DHCP (Dynamic Host Configuration Protocol) automatically assigns network config. The DORA process: Discover (broadcast) → Offer (server proposes IP) → Request (client accepts) → Acknowledge (server confirms). You receive: IP address, subnet mask, default gateway, DNS server address, lease time.

DNS — the internet's phone book

DNS translates domain names (google.com) into IP addresses (142.250.80.46). Without it, you'd need to memorize IPs for every site.

DNS hierarchy

. (Root — 13 logical servers, 1500+ physical via anycast) /|\ .com .org .net .io (TLD servers — e.g. Verisign runs .com) / google.com (authoritative nameserver — Google controls this zone) / www.google.com A record → 142.250.80.46

Full DNS lookup walkthrough for google.com

1

Browser checks its own DNS cache. Cache miss.

2

OS checks /etc/hosts and the OS resolver cache. Cache miss.

3

OS sends query to the configured recursive resolver (e.g. 1.1.1.1 or 8.8.8.8).

4

Resolver queries a root server: "Where is .com?" — receives address of Verisign's TLD servers.

5

Resolver queries Verisign's TLD server: "Where is google.com?" — receives address of Google's authoritative nameservers.

6

Resolver queries Google's authoritative server: "What is the A record for google.com?" — receives 142.250.80.46.

7

Resolver returns the IP to the OS. OS gives it to the browser. Both cache per the TTL value (e.g. 300 seconds for Google).

Routing & BGP

How does a packet navigate from your laptop to a server in Tokyo? Routing. How do networks tell each other what they can reach? BGP.

Autonomous Systems (AS)

An Autonomous System is a collection of IP prefixes under control of one organization with a single routing policy. Each AS gets a globally unique ASN. Well-known examples: AS15169 (Google), AS16509 (Amazon AWS), AS13335 (Cloudflare), AS32934 (Meta), AS8075 (Microsoft).

The Internet is ~76,000 ASes exchanging routing information with each other via BGP. Your home ISP is an AS. So is Google, your university, and large enterprises.

BGP: Border Gateway Protocol

BGP is the routing protocol of the Internet. It runs over TCP port 179. ASes use BGP to advertise which IP prefixes they own and can route to. BGP is path-vector: each advertisement includes the full sequence of ASes a packet must traverse — this prevents routing loops.

AS 65001 (your ISP) advertises to peer AS 65002: Prefix: 203.0.113.0/24 AS_PATH: [65001] AS 65002 re-advertises to AS 15169 (Google): Prefix: 203.0.113.0/24 AS_PATH: [65002, 65001] Google now knows: to reach 203.0.113.0/24, go to AS 65002, which will then route to AS 65001.

TCP / UDP / ICMP

Transport layer protocols define how data is packaged and delivered between two endpoints across the Internet.

TCP — Transmission Control Protocol

TCP provides reliable, ordered, error-checked delivery. Connection-oriented: a 3-way handshake establishes the session before data flows. Lost packets are retransmitted. Flow control prevents overwhelming receivers. Congestion control backs off when the network is saturated.

3-way handshake: Client → Server: SYN (seq=1000) Server → Client: SYN-ACK (seq=5000, ack=1001) Client → Server: ACK (ack=5001) [Connection established] Teardown: FIN → FIN-ACK → FIN → FIN-ACK (4-way)

UDP — User Datagram Protocol

UDP is connectionless and has no delivery guarantee — no handshake, no acknowledgment, no retransmission. If a packet is lost, the application must handle it or ignore it. Used where speed matters more than perfection: DNS queries, video streaming, gaming, VoIP, and HTTP/3 (QUIC). UDP header is only 8 bytes vs TCP's 20 bytes minimum.

ICMP — Internet Control Message Protocol

ICMP carries network control messages — not user data. It operates at Layer 3 with no ports. Used by ping (echo request/reply, types 8 and 0), traceroute (TTL exceeded, type 11), and path MTU discovery. Every router that drops a packet due to TTL expiry sends an ICMP Time Exceeded back to the source — this is how traceroute reveals each hop.

traceroute google.com Sends packets with TTL=1, then TTL=2, then TTL=3... Each router decrements TTL by 1. When TTL hits 0: router sends ICMP "Time Exceeded" back. Source records that router's IP and RTT, increments TTL.

Packet switching

The Internet breaks data into packets (up to 1500 bytes, the Ethernet MTU). Each packet is routed independently. They may take different paths and arrive out of order — TCP reorders them. One network path simultaneously carries packets from millions of conversations, unlike circuit switching (which dedicates a path per call, like traditional telephony).

OSI model & TCP/IP model

Layered models explain why networking works. Each layer solves one specific problem and presents a clean interface to the layers above and below it.

Why layers exist

Separation of concerns. An HTTP developer doesn't need to know whether their data travels over WiFi, fiber, or 5G. A WiFi engineer doesn't need to know whether the traffic is HTTP or FTP. Each layer trusts the layer below and provides a clean API upward. This is why a TCP socket works identically over cable, DSL, 4G, or satellite — the transport layer doesn't care about the physical medium.

Encapsulation: data traveling down the stack

(bits on the wire) At destination: each layer strips its header and passes payload up until the application receives the HTTP text.

TLS / HTTPS & encryption

HTTPS = HTTP running inside a TLS tunnel. TLS provides authentication, confidentiality, and integrity for any TCP connection.

TLS 1.3 handshake

1

ClientHello: client sends supported cipher suites, TLS version, random nonce, and a Diffie-Hellman key share (its public key).

2

ServerHello: server selects cipher suite, sends its own DH key share and its certificate (containing the server's public key, signed by a CA).

3

Key derivation: both sides independently compute identical session keys using their DH private key combined with the other's public key. No key material is ever transmitted over the network.

4

Certificate verification: client checks the server's certificate is signed by a trusted CA and matches the domain name. Prevents MITM attacks.

5

Finished: both sides confirm handshake integrity with a MAC. Encrypted data exchange begins. TLS 1.3 completes in 1 round-trip (TLS 1.2 required 2).

Certificates and certificate authorities

A TLS certificate is a signed document stating "this public key belongs to google.com". The signature comes from a Certificate Authority (CA) — a trusted third party such as DigiCert, Let's Encrypt, or GlobalSign. Your browser ships with ~150 trusted root CAs. If a certificate chains to one of these roots, the browser trusts it. The domain in the certificate must exactly match the domain being visited.

Encryption algorithms in TLS 1.3

Purpose Algorithm Why
Key exchange ECDHE (Curve25519) Perfect forward secrecy — unique key per session
Authentication ECDSA or RSA Signs the certificate to prove identity
Bulk encryption AES-256-GCM Symmetric cipher with hardware acceleration
Integrity SHA-384 HMAC Detects tampering with each record

Scenario: WiFi laptop → website (HTTPS)

Every step from typing https://google.com to seeing the page — traced through every layer and infrastructure component.

1

Browser parses URL: scheme=https, host=google.com, path=/. Needs the IP address for google.com.

2

DNS lookup: browser cache miss → OS cache miss → query sent to recursive resolver (1.1.1.1). Full walk: root server → .com TLD (Verisign) → google.com authoritative → returns 142.250.80.46. Cached per TTL (~300s).

3

TCP handshake to 142.250.80.46:443. OS creates socket, sends SYN. Path: WiFi NIC → 802.11 radio frame → access point → Ethernet → home router (NAT rewrites src IP to public IP) → DSL/fiber modem → ISP POP → backbone → Google's network. SYN-ACK returns. ACK sent. TCP established.

4

TLS 1.3 handshake: ClientHello → ServerHello + certificate → both derive session keys via ECDHE → Finished messages. ~1 round-trip. All subsequent data is encrypted with AES-256-GCM.

5

HTTP/2 GET request sent encrypted: headers (Host, Accept, User-Agent) compressed with HPACK. Google's load balancer terminates TLS, routes to an HTTP server cluster.

6

Server generates HTML response. Streams back through: data center switch → load balancer → Google backbone → IXP or direct peering → ISP backbone → DSLAM/CMTS → home router (NAT maps response to your laptop's private IP) → WiFi → NIC.

7

Browser receives response: TCP reassembles segments in order → TLS decrypts → HTTP/2 decompresses → HTML parsed → DOM built → CSS applied → JS executed → sub-requests for images/fonts/APIs follow the same entire process.

Scenario: mobile data → website

The same journey, but your signal starts at a cellular base station instead of a WiFi access point.

1

Radio link: your phone's modem connects to the nearest 4G base station (eNodeB) using licensed spectrum. The radio channel uses OFDMA subcarriers. Signal digitized and modulated (e.g. 64-QAM or 256-QAM depending on signal strength).

2

RAN to core: base station sends traffic via fiber backhaul to the Evolved Packet Core (EPC). Your session passes through the Mobility Management Entity (MME) for authentication, Serving Gateway (SGW) for local routing, and Packet Data Network Gateway (PGW) which assigns you a public IP and connects to the Internet.

3

Public IP assignment: many carriers use CGNAT (Carrier-Grade NAT) — you share one public IP with thousands of other subscribers, with different port ranges assigned per user. This is an additional NAT layer beyond your phone's own NAT.

4

Internet path: from the PGW, your traffic enters the carrier's IP backbone, routes through their peering/transit connections to reach the destination AS — identical to the WiFi scenario from step 3 onward.

5

Key differences from WiFi: higher air latency (4G: 30–50 ms to tower vs ~1 ms to WiFi AP), CGNAT means you may not be reachable for incoming connections, and handover between cells adds occasional brief interruptions managed transparently by the EPC.

Scenario: messaging app (end-to-end encrypted)

Sending a WhatsApp or Signal message — tracing encryption, servers, push notifications, and delivery.

1

On-device encryption: Signal Protocol (used by both WhatsApp and Signal) encrypts the message with the recipient's public key before it ever leaves your device. The server never sees plaintext content — only encrypted blobs.

2

Transport to server: encrypted message travels over a persistent TCP connection (WebSocket or XMPP-like protocol) with TLS to the messaging provider's servers. Path: device → WiFi/4G → ISP → backbone → CDN/load balancer → messaging server in a data center.

3

Server handling: if recipient is online, server relays message immediately. If offline, server stores the encrypted message. The server sees only: sender ID, recipient ID, timestamp, message size, and the encrypted payload — never the content.

4

Push notification: server sends a push notification via Apple Push Notification Service (APNs) for iOS or Google Firebase Cloud Messaging (FCM) for Android. These services wake the app in the background without revealing the message content.

5

Recipient decryption: only the recipient's private key (stored exclusively on their device, never uploaded) can decrypt the message. Even if the messaging company's servers are compromised, the message content remains unreadable.

Scenario: cross-ocean file download

Downloading a 1 GB file from a server on another continent — every hop traced.

1

GeoDNS: CDN providers return different IPs based on where your resolver is. You likely get routed to a CDN PoP in your country, not the origin server — even if the origin is across the ocean. This is the single biggest optimization in global content delivery.

2

CDN edge connection: your TCP session terminates at the nearest CDN PoP (~5–20 ms away). The CDN has a persistent, pre-warmed, high-bandwidth TCP connection to the origin — far more efficient than one long thin pipe across an ocean.

3

TCP slow start & congestion control: TCP begins at a small congestion window (~10 segments), doubles every RTT (slow start), until it detects packet loss, then backs off. Over a 150 ms RTT intercontinental path, maximum throughput is limited by: window_size ÷ RTT. This is the bandwidth-delay product problem.

4

If no CDN (direct): US East Coast to Europe travels: client → US backbone → landing station (e.g. Manasquan Beach, NJ) → submarine fiber cable (~6,700 km, 33 ms one-way) → landing station (e.g. Widemouth Bay, UK) → UK backbone → destination ISP → server. Round-trip ~70–90 ms just for propagation.

5

Data center: request hits load balancer → reverse proxy checks object cache → cache miss fetches from object storage (e.g. S3, Ceph) → streams back. Data is chunked and pipelined: multiple TCP segments in flight simultaneously per the congestion window size.

6

Completion: TCP ACKs confirm every segment. Any dropped packet triggers selective retransmission (SACK). TLS MAC verifies integrity of each record. Application may also verify with a SHA-256 checksum of the complete file.

Linux networking commands & Wireshark

Practical tools to observe and troubleshoot every concept covered in this document.

DNS debugging

dig google.com # Full DNS query with all details dig google.com A # Only A (IPv4) records dig google.com AAAA # IPv6 address records dig @1.1.1.1 google.com # Query Cloudflare's resolver directly dig +trace google.com # Full walk: root → TLD → authoritative nameserver host google.com # Simple forward and reverse lookups

Route tracing

traceroute google.com # Reveal each hop (uses UDP by default) traceroute -T google.com # Use TCP SYN — bypasses some firewalls traceroute -I google.com # Use ICMP echo packets mtr google.com # Real-time traceroute with per-hop packet loss % ip route get 8.8.8.8 # Which interface/route for a specific destination?

Active connections & ports

ss -tuln # All listening TCP/UDP sockets ss -tnp # Active TCP connections with process names ss -s # Socket statistics summary ss -o state established # Only established TCP connections

Packet capture with tcpdump

tcpdump -i eth0 # All traffic on eth0 tcpdump -i any host 8.8.8.8 # Filter by IP address tcpdump -i eth0 port 443 # HTTPS traffic only tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0' # SYN packets (new connections) tcpdump -w /tmp/capture.pcap # Save to file for Wireshark tcpdump -r /tmp/capture.pcap # Read saved capture file
